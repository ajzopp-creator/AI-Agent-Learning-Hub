Most people spend more effort writing the perfect /goal prompt than the task itself deserves. Boris Cherny's advice cuts that step out entirely: let the model set its own /goal, because it will likely write a better prompt than you would anyway.

The simplest way to do this is to just describe the outcome and ask for the /goal directly. Tell Claude what you want, ask it to write the optimal /goal prompt including success criteria, constraints, and checkpoints, and copy what comes back. No editing required.

A more careful version architects before running. Use /plan first so Claude maps the full approach, then ask it to convert that plan into a /goal. You get a plan you can actually review, plus a /goal that reflects the real scope of the work instead of a guess at it.

The most thorough version is a context dump. Hand Claude everything, the codebase, the docs, your Memory.md, and ask what /goal prompts it would build from that context. This is the version that surfaces loops you did not know you needed, because it is working from your actual history instead of one task description.

Every version works for the same reason. Claude knows its own capabilities better than you do, it writes measurable success criteria you would have forgotten, it adds guardrails and checkpoints automatically, and it scopes the task correctly instead of too broad or too narrow. Each one it writes also teaches you what good prompting actually looks like.

The power move is making this automatic. Add one line to your project instructions: whenever a task gets described, ask first whether to write the /goal prompt before starting. Every future task offers you an agent-written loop without you having to remember to ask.

Bookmark this and try the simplest trigger first: write me the /goal prompt for this.
