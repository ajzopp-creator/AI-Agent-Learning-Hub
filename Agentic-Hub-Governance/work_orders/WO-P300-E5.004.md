## WHY

2026-07-22 night: a real `ingest-mined` run (no `--promote`) hit a cold
M-079 "pre" (live-catalog) walk-forward cache -- the cache is keyed to
catalog content fingerprint (M-099), and this morning's real promote
(10,757->14,812 patterns, via `ingest-mined --promote` ->
`catalog_merge_pipeline.py`'s `promote_staging_to_live()`) never
refreshes it. On a cache miss, the code falls back to a full, serial,
uncached `run_walk_forward()` over the ENTIRE live catalog -- no
estimate, no confirmation, no visible progress. Ran silently overnight
(8.8 hours, real CPU confirmed via `Get-Process`, not hung/crashed) and
was killed by Tony rather than let continue indefinitely.

WO-P300-E4.005 already measured this exact scenario precisely: full
serial rescore cost is `0.7836ms x corpus_size`, integrated over N
patterns (corpus growing ~1:1 with index) -- **~12.5 hours at
N=10,738** (2026-07-19 measurement). At tonight's N=14,812, the same
formula integrates to **~24 hours**. `EVAL_PARALLEL_ENABLED=False` is
correct as tested (2026-07-19, parallel measured SLOWER at every worker
count/batch size on that corpus) -- not being revisited here without
new evidence at current scale.

**The real gap:** WO-P300-E4.006's topk_state_cache fixed this exact
O(N^2) cost for the "post" (staging, new-patterns-only) side. It does
nothing for a cold "pre" (live) cache -- which is exactly what a cache
miss falls back to the ORIGINAL, pre-E4.006, pre-optimization full-
rescore path. The 2026-07-15 problem that motivated all of this
optimization work is still fully reachable, on a specific trigger
(any `ingest-mined` run whose first invocation after a promote needs a
fresh "pre" batch) that nothing has closed.

**Tony's direct instruction (2026-07-22):** a full rescore must never
run automatically. It must estimate its own duration and require
explicit confirmation before proceeding. 24 hours is not acceptable as
a default outcome of running a normal command. More research is needed
before committing to a specific fix for the underlying cost -- the
confirmation gate is the immediate, unconditional requirement regardless
of which deeper fix (if any) gets built.

## PART A -- Research the real fix (NOT decided, explicitly deferred)

Candidate approaches, none chosen yet:

1. **Refresh the "pre" cache at promote time.** `promote_staging_to_live()`
   writes a fresh walk-forward cache entry for the new live state as
   part of promotion, so the next `ingest-mined` run always finds a
   warm cache. Real risk: this doesn't eliminate the O(N^2) cost, it
   just MOVES it to promote time -- promote could become the new
   multi-hour (or multi-day, at growing N) operation instead. Needs
   real investigation into whether that's actually better, not assumed.
2. **Extend E4.006's incremental machinery to the "pre" side.** If
   `topk_state_cache` already stores enough per-pattern state (top-K
   neighbors + distances) to reconstruct a walk-forward batch without a
   fresh full DTW pass, a cold "pre" cache might be rebuildable
   incrementally too, not just the "post" side. Needs a real look at
   whether `topk_state_cache`'s stored data is sufficient for this, or
   whether walk-forward eval needs something structurally different
   (outcome labels, not just similarity rankings) that isn't cached
   there.
3. **Diff-and-extend instead of all-or-nothing hit/miss.** Since "pre"
   (live catalog) only changes via promotes, which ADD patterns rather
   than altering existing ones, a cache "miss" after a promote is really
   "N new patterns since the last good cache," not "nothing is known."
   An incremental extend-the-old-cache approach (similar in spirit to
   the "post" side's own incremental design) might avoid re-deriving
   the untouched majority of the corpus. Most promising candidate on
   its face, but not evaluated -- flagged as a starting hypothesis, not
   a conclusion.

**Not in scope for this research pass:** re-litigating
`EVAL_PARALLEL_ENABLED` without new evidence at current corpus scale
(WO-P300-E4.005 already settled this at the last-tested size); corpus
sampling/capping (already rejected, WO-P300-E4.004 out-of-scope
inheritance, changes the statistics by construction).

## PART B -- Estimate + confirmation gate (buildable now, does not wait on Part A)

Regardless of which Part A fix (if any) eventually lands, a full
uncached rescore must never proceed silently. Scope:

- On a cache miss in `_run_pre_batch()`, compute `corpus_size` and an
  estimated duration using the measured constant from WO-P300-E4.005
  (`0.7836ms x corpus_size`, integrated -- flag this constant as an
  approximation that may drift; not re-measured for this WO).
- Print/log the estimate clearly (corpus size, estimated hours, which
  WO this references) and **refuse to proceed by default** -- exit
  non-zero with an actionable message, do not attempt a live interactive
  prompt buried inside a subprocess (a "Press Enter" prompt inside
  redirected output is exactly the kind of thing that could go unseen
  the same way this incident did -- fail closed and visible instead).
- Require an explicit, conscious opt-in to actually run it -- e.g. a
  `--confirm-full-rescore` flag on `ingest-mined` that must be passed
  deliberately, separate from the normal invocation. Exact mechanism
  (flag vs. env var vs. something else) is the file-plan's call, not
  decided here.
- `P_300_RunBulkAddPattern.ps1` already checks `$LASTEXITCODE` and
  pauses on error (`[ERROR] ... Press Enter to close`) -- reuse that
  existing, already-visible convention rather than inventing a new one.

## PART A RESEARCH FINDING -- candidate 2 validated, 2026-07-23

Investigated candidate 2 (reconstruct the M-079 "pre" walk-forward batch
from `topk_cache` instead of a fresh serial DTW pass) at Tony's
direction. Real evidence, not theory:

**Why it should work:** traced `domain/eval_scoring.py`'s `score_one()`
exactly. It does exactly one expensive thing -- `similarity.rank_by_
distance()` against the full date-filtered corpus, to find each
pattern's top-20 by DTW distance. Everything else is cheap: `aggregator.
catalog_baseline_win_rates()` is pure label aggregation (mean
`is_profitable` across corpus labels, no distance computation at all,
confirmed by reading it directly), and classification is simple
threshold comparison. `domain/topk_cache.py` already stores exactly
this expensive part -- `TOP_K_MATCHES=20` exact, same date-filtered
corpus logic (`_corpus_pids_before` mirrors `score_one`'s own
`_corpus_pids`) -- and is correctly, comprehensively maintained at
every real promote via `application/promote_topk.py`, wired into
`catalog_merge_pipeline.py`'s `promote_staging_to_live()`. This
morning's real promote log IS this mechanism running for real
("topk_cache populated on staging: 4055 new pids, 10698 existing pids
rechecked"). If a "pre" batch reconstruction read `topk_cache` instead
of recomputing DTW, it would skip the entire O(N^2) cost -- turning a
~24h computation into cheap dictionary reads + label aggregation.

**Coverage, checked directly against the live catalog (2026-07-23):**
confirmed in code first -- `application/add_pattern_pipeline.py`
(single-pattern AddPattern, Pipeline A) has zero references to `topk`
anywhere; only the bulk-merge/promote paths populate it. Real query
against `072226catalog.db`: 14,812 pattern_instances, 14,806 distinct
pids in `topk_cache`, gap of exactly 6. All 6 gap pids share
anchor_date=2021-08-10 -- confirmed via a second query that this is the
catalog's absolute EARLIEST anchor_date system-wide (0 patterns exist
with an earlier date), so their would-be corpus is empty by
construction. `topk_cache` correctly has 0 rows for a degenerate-corpus
pattern (`domain/topk_cache.py`'s `_rank_topk()` returns `[]` when
`candidate_pids` is empty) -- this is the SAME degenerate-corpus case
`score_one()` already handles explicitly today (`degenerate_corpus=True`,
empty `top_k_pids`, baseline computed over an empty corpus which
`aggregator.py`'s own docstring says returns 0.0 for an unlabeled
horizon). Not a coverage bug, not an AddPattern-shaped hole -- the gap
is exactly as large as it should be and no larger.

**Conclusion:** candidate 2's premise holds up under real, direct
verification, not just plausibility. The data topk_cache-based
reconstruction would need already exists, is already correctly
maintained (paid for at promote time, which already happens), and its
one edge case is already a solved problem elsewhere in the same
codebase. This is now a real, evidence-backed recommendation for Part A,
not one of three untested candidates -- candidates 1 and 3 remain
unbuilt and, per the earlier discussion, less promising (candidate 3
specifically contradicted by the measured 0% reuse fraction on the
sibling "post" side; candidate 1 is a UX/predictability question, not a
performance fix).

**Not yet done -- still requires Tony's go-ahead before any code is
written, per this WO's own Acceptance Criteria:** writing the actual
reconstruction function (read topk_cache per pattern instead of calling
`similarity.rank_by_distance()`, explicitly handle the zero-rows-means-
degenerate-corpus case, assemble a `WalkForwardResult`/`WalkForwardBatch`
matching `score_one()`'s output shape exactly so nothing downstream
needs to change), and wiring it into `_run_pre_batch()`'s cache-miss
path as an alternative to the current full-rescore fallback.
