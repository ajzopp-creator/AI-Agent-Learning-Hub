## WHY

PEH stages two files at fixed paths and calls them "Ephemeral -- overwritten each
handoff":

```
Agentic-Hub-Governance\verify\run_this.py
Agentic-Hub-Governance\verify\run_this_context.txt
```

Two defects follow from that.

**1. No completion signal.** `run_this.py` prints PASS/FAIL to stdout and writes
nothing. Once Tony runs it in Claude Code, the staged file on disk is byte-identical
to a file that was never run. Nothing on disk records that a handoff was consumed,
when, or with what result. The skill's own v1.3 rule says the durable signal is
"a file actually on disk, checked with Test-Path" -- PEH does not follow its own rule.

**2. Fixed filename collides across projects.** Any two projects handing off on the
same day overwrite each other silently, and because of defect 1 there is no way to
tell afterward whether the clobbered handoff had already been run.

**Observed 2026-08-04, P_020 session.** A P_020 handoff was staged the previous
evening. On return, `verify\run_this.py` was found holding a *P_300* handoff written
that morning at 11:28 for the WO-P300-E5.002/E5.005 independent review. Writing the
P_020 handoff would have destroyed it.

Determining whether the P_300 handoff had already run required forensics rather than
a lookup, and the answer came back only probable, not certain:

- The script writes no artifacts, so there was nothing direct to check.
- Test files invoked as `__main__` are never bytecode-cached, so `__pycache__` said
  nothing about the tests themselves.
- The only signal was `verify_ingestion.cpython-312.pyc` under P_300 rewritten at
  12:08 -- 40 minutes after the handoff was staged. Suggestive of a run.
- The other four modules' `.pyc` files were stale (7/28, 7/30), which is equally
  consistent with "ran fine, already cached" and with "never ran," since a `.pyc`
  is only rewritten when its source changes.

A one-line `Test-Path` should have answered this. Instead it took three tool calls
and still ended in a hedge.

**Blast radius.** PEH is hub-wide and is the standing fallback whenever the MCP relay
stalls -- which per the skill's own trigger note is roughly 9 out of 10 Python calls.
Silent loss of a staged independent-review handoff is a governance failure, not just
an inconvenience: WO_COMPLETION_GATE closures depend on those runs actually happening
and being attributable.

## PROPOSED FIX (P_000 to confirm approach)

1. **Timestamped filenames.** Stage as `run_this_<PROJECT>_<YYYYMMDD_HHMMSS>.py` and
   matching `_context.txt`. Collisions become impossible; provenance is readable from
   the filename.
2. **Completion marker.** `run_this_*.py` writes a sibling `.done` file on exit
   containing timestamp, PASS/FAIL, and exit code. This is the durable on-disk signal
   v1.3 already requires everywhere else.
3. **Pre-stage check.** Before staging, PEH scans `verify\` for any `run_this_*.py`
   with no matching `.done` and surfaces it to Tony rather than proceeding silently.
4. **Handoff prompt update.** The verbatim prompt names the specific timestamped file
   instead of the generic path.
5. **Retention rule.** Decide how long completed handoff pairs persist before
   archiving -- `verify\` currently holds ~100 loose files back to 2026-07-05 and has
   no cleanup rule at all.

## OPEN QUESTIONS (resolve with Tony when picked up)

1. Does the `.done` marker get written by `run_this.py` itself (self-contained, but
   every generated script must remember to do it) or by a shared helper the script
   imports (consistent, but adds a dependency to a file that is supposed to be
   standalone)?
2. Should an un-consumed handoff older than N days be auto-flagged at session INIT,
   or only checked at stage time?
3. Does `verify\` need subfolders per project, or is a timestamped flat name enough?
