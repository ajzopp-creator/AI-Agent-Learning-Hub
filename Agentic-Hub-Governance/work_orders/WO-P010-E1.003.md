# WO-P010-E1.003 -- Daily Posture Pipeline Must Fail Loud, Not Silent

**Status:** PENDING
**Owner:** P_010
**Affects:** P_400, P_115, P_300, P_020
**Depends On:** WO-P010-E1.002 (root cause this WO is reacting to)
**Related:** WO-P010-E1.002

---

## WHY

E1.002 sat broken 4 trading days (7/14-7/17) with zero surfaced warning.
`P_010_daily_posture_v5.py` threw `ERROR: File not found` to its own log
every morning, then the note writer and intraday script both proceeded
anyway on stale data as if nothing happened. Nobody saw a problem until a
mtime/internal-timestamp mismatch got noticed by accident during a P_400
session. That's the actual failure -- not the typo, the silence around it.

## PROBLEM

Current pipeline has no fail-loud path:
- `P_010_daily_posture_v5.py` errors to a log file only. Log files are
  never checked unless someone goes looking.
- Downstream steps (note writer, intraday check) don't check whether the
  morning run actually succeeded before consuming
  `P_010_RiskConfig.json` -- they just read whatever's there.
- `P_010_RiskConfig.json`'s `timestamp` field is the only real staleness
  signal, and nothing compares it against today's date automatically.
- Guardian bat (`P_010_Start_Guardian.bat`) watches for sync/API errors
  but does not appear to check for a failed morning run vs. a skipped one
  (SKIP_TODAY.flag) -- both currently look identical downstream.

## PROPOSED FIX (not yet built, needs Tony sign-off on approach)

1. `P_010_daily_posture_v5.py`: on any exception (file-not-found or
   otherwise), do not let the batch chain continue silently. Options,
   pick one:
   a. Non-zero exit code + `.bat` wrapper checks it and halts before
      calling the note writer / intraday step.
   b. Write an explicit `MORNING_RUN_FAILED.flag` file the intraday
      script and Guardian both check for before proceeding.
2. Guardian (or the daily batch itself) fires a `windows-mcp:Notification`
   toast on failure -- title "P_010 Morning Run FAILED", message = the
   exception line. Tool already available, no new dependency.
3. Note writer and intraday script both add a same-day `timestamp` check
   against `P_010_RiskConfig.json` before running -- if stale, note
   writer should either skip with a visible banner or mark the note
   `[STALE POSTURE -- MANUAL REVIEW]` instead of writing clean HALF/FULL/
   OFF as if it were fresh.
3. Downstream consumers (P_400 STEP 0, P_115/P_300 screens) already check
   `timestamp` per project-context skills -- keep that as a second layer,
   not the only layer. The point of this WO is source-level alerting, not
   pushing the check further downstream every time.

## ADDENDUM (2026-07-17, same-day manual re-run)

Confirmed a second, related noise problem while manually re-running the
pipeline to close out E1.002: `P_010_run_intraday_vp_check.bat` printed
both `[SUCCESS] Intraday VP validation completed.` AND, immediately after,
`[ERROR] Intraday check failed with exit code 0` -- despite the run being
genuinely clean (JSON written correctly, P_010_RiskConfig.json updated
correctly, morning_risk_mode/intraday_signal/final risk_mode all
consistent and correct: HALF -> DOWNGRADE -> OFF). Exit code 0 is a
success code; the wrapper's errorlevel check appears inverted or
otherwise wrong, so it prints ERROR on success.

This is the same category of problem this WO already exists to fix: a
false ERROR on a good run trains the operator to distrust/ignore
`[ERROR]` output, which defeats the point of the fail-loud alerting this
WO proposes. Any alerting/notification mechanism built under item 2 above
MUST NOT fire on this false positive -- fix the errorlevel check in
`P_010_run_intraday_vp_check.bat` (or wherever the exit code is set/read)
as part of this WO, not as an afterthought.

Added to VERIFY: re-run intraday check on a known-good pass, confirm no
`[ERROR]` line prints alongside `[SUCCESS]`.
