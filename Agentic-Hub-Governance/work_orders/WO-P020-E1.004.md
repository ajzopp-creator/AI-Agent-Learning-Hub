# WO-P020-E1.004 -- paper_import.py Missing Exit Records

**Status:** COMPLETE
**Owner:** Claude
**Affects:** P_020
**Depends On:** --

---

## WHY

paper_import.py (built 2026-04-28) inserts every trade row with
status="closed" when the source CSV shows an exit, but never writes a
corresponding row to the exits table. Confirmed 2026-07-05: all 28 trades
imported from the 6/1-7/5 paper batch have status='closed' and zero exit
rows (source='tos_paper_csv'). Because v_trade_summary computes
realized_pnl and outcome (WIN/LOSS/SCRATCH) entirely from the exits table,
every one of these trades reads as $0 P&L and SCRATCH regardless of its
real exit price -- even though the exit price, exit date, and quantity
exited are sitting right in the source CSV row.

This is not a new bug from this session -- it's an existing gap in a
script that had only been exercised once before (a single synthetic test
trade, per the Future Enhancements log). Confirmed by contrast: the 130
pre-existing paper trades with source='tos_import' (used from
January/February onward, before paper_import.py existed) have 119 real
exit rows between them via a different, working ingestion path.

A regression test already exists and is committed, intentionally failing:
test_closed_trades_have_exits in
projects/P_020_AJZStrategies_PerformanceAnalysisSystem/tests/test_p020_known_bugs.py.
This WO is done when that test passes.

---

## SCOPE

1. paper_import.py -- for each row with an exit price present in the
   source CSV (Exit #1 / # Exited / Exit Date, and Exit #2 / # Exited2 /
   Exit Date3 where present), build and insert a matching exits table row
   (exit_number, exit_date, qty_exited, exit_price, exit_commissions,
   exit_pnl, hold_days) alongside the trades row, inside the same
   write_trades() transaction.

2. exit_pnl calculation must match the convention already used elsewhere
   in the schema: (exit_price - entry_price) * qty_exited * multiplier
   (multiplier = 100 for options, 1 for stock), sign-adjusted for
   direction (short reverses the sign).

3. Backfill: re-run against the 28 already-committed trades (safe --
   dedup is keyed on the trades table, not exits; inserting exits for an
   existing trade_id is additive, not a duplicate trade).
