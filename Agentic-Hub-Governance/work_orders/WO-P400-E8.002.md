# WO-P400-E8.002 -- Earnings Calendar "Confirmed Clear" Default Isn't Actually Checked Against Today's Gate Window (Enhancement, Open-Scope)

**Status:** OWNER_DONE
**Owner:** P_400
**Affects:** infrastructure\earnings_calendar_cache.py (`is_stale()`), config.py (`EARNINGS_CALENDAR_MAX_STALENESS_DAYS`), application\earnings_lookup.py (consumes the staleness signal indirectly via the warning path only -- the "confirmed clear" default itself has no staleness gate at all)
**Depends On:** none
**Related:** WO-P400-E5.002 (original cache build), WO-P400-E6.004 (both revisions -- introduced the "absence = confirmed clear" default this WO is about)

---

## WHY

Found live 2026-09-14, P_400 session, while answering Tony's question "why
would we ever block anything if we don't even have an approximate date" for
NFLX/EHC/SELF (none in the earnings calendar cache).

WO-P400-E6.004 (2026-08-19) made "symbol absent from the earnings calendar
cache" mean **confirmed clear** (`next_earnings_date=None`, evaluated
normally, not skipped) rather than a hard fail. This is sound *by design*:
the cache's pull window (`EARNINGS_CALENDAR_LOOKAHEAD_DAYS`/
`_LOOKBACK_BUFFER_DAYS`, config.py, 7/5 days) was deliberately narrowed to
match MACRO's actual gate (`EARNINGS_WINDOW_FORWARD_DAYS`/`_BACKWARD_DAYS`,
3/2 days) -- absence from a pull that narrow is meant to mean "nothing in
the window that matters."

**The gap: that inference is only true while today still falls inside the
original pull's captured range.** The pull window is anchored to
`cache.pulled_date`, not to "today" at lookup time. For "absence = clear"
to validly cover today's actual `[today-2, today+3]` gate window, today
must fall within roughly `[pulled_date-3, pulled_date+4]` of the pull --
call it a 3-4 day effective validity period. `is_stale()` instead checks
against `EARNINGS_CALENDAR_MAX_STALENESS_DAYS = 35`, a constant set for a
different purpose (Tony's 2026-08-08 "fixed-monthly-schedule, don't
spot-check" call, made before E6.004's narrow-window redesign existed) and
never reconciled against it.

**Live evidence:** cache pulled 2026-08-19, checked 2026-09-14 -- 26 days
old, still well under the 35-day staleness threshold (no warning fires),
but the pull's actual captured range (`[08-14, 08-26]` roughly) has zero
overlap with today's real gate window (`[09-12, 09-17]`). Any symbol
missing from the cache right now would be reported "confirmed clear" while
never actually being checked against today's window at all -- the 26-day
gap happened to be harmless for NFLX/EHC/SELF only because their real
dates (independently confirmed via web search) are 36+ days out regardless
of which window was checked.

## Approach Taken (built 2026-09-15 -- Option 1 below, with the skip fallback)

## Proposed Approach (original framing, preserved as filed 2026-09-14)

Two independent problems, likely two fixes:

1. **Gate the "confirmed clear" default itself**, not just the general
   staleness warning, on cache age vs. the pull window's actual effective
   validity (a few days, derived from `LOOKAHEAD_DAYS`/`LOOKBACK_BUFFER_DAYS`
   minus the gate's own `FORWARD_DAYS`/`BACKWARD_DAYS` margin) -- e.g. a new
   `is_clear_default_valid(cache)` check in `earnings_calendar_cache.py`,
   consumed by `earnings_lookup.py`'s missing-symbol branch specifically,
   separate from the existing `is_stale()` (which can keep its 35-day
   "please refresh soon" purpose for the *sector*-lookup / general-freshness
   use case -- sector data isn't safety-critical the way the clear-default
   is).
2. **When that check fails** (cache too old for today's window), fall back
   to the pre-E6.004 behavior for that symbol only: either skip it (as
   Revision 1 of E6.004 did) or raise, forcing the manual Bucket B path --
   not a full batch-2b abort either way (don't regress E6.004's actual fix,
   the whole-batch-abort bug).

## Acceptance Criteria (draft -- refine at build time)

- [x] A cache pulled outside its effective validity window no longer
      returns "confirmed clear" for a missing symbol; behavior for that
      case (skip vs. raise) matches E6.004's per-symbol (not per-batch)
      scope. -- Skip chosen (matches E6.004), via `SOURCE_GATE_UNCERTAIN`
      tag + `batch_2b_scoring.py` skip, not a raise.
- [x] A cache pulled *within* its effective validity window is unaffected
      -- no regression to E6.004's actual fix (the whole-batch-abort bug
      stays fixed). -- Unchanged confirmed-clear path covered by
      `test_symbol_absent_from_cache_is_confirmed_clear` (updated to pin
      `is_valid_for_current_gate=True` explicitly).
- [x] `is_stale()`'s existing 35-day behavior (general refresh nudge, used
      for sector-lookup freshness) is preserved as-is or explicitly
