## WHY

Tony asked to analyze P_210's total win/loss dollars. The dashboard showed
4 wins / 4 losses, $10,789.99 won against $11,370.99 lost, net -$581.00.
Cross-checked against the real Schwab statement (`2026-09-19-AccountStatement_
NDX.csv`, user-provided): every P_210 trade is a 2-leg vertical credit
spread, one order per day. The true picture is 3 wins ($115/$109/$105,
each a spread that expired worthless) and 1 loss (-$910.00, the 9/18
spread that settled ITM) -- **3W/1L, not 4W/4L**, net unchanged at -$581.00.

Root cause: `schwab_mapper.py`'s `_aggregate_by_order()` correctly keys
fills by `(order_id, full_symbol)` (WO-P020-E1.017) so each leg becomes
its own correctly-priced `trades` row -- but nothing then regroups legs
that share an `order_id` back into one reporting unit. Every downstream
win/loss/R/Kelly calculation counted each leg as an independent trade.
This is not NDXP- or P_210-specific -- any system trading `VERTICAL`/
multi-leg spreads live hits the same over-counting.

A working, tested equivalent already existed for PAPER: WO-P020-E1.002
built `spread_legs` (normalized child table) + `SpreadLeg` schema +
`paper_spread_import.py`, which writes ONE parent `trades` row (asset_
type='spread') per spread position. That path parses TOS's text
DESCRIPTION field (`spread_leg_parser.py`), which the live Schwab JSON
pull has no equivalent of -- live returns one transaction row per leg,
linked only by a shared `orderId`. Rather than force live data through a
text-parsing pipeline built for a different data shape, this WO adds a
lighter-weight, JSON-native equivalent: tag legs sharing an `orderId`
with a common `spread_group_id`, and net them at the reporting layer.
Each leg's own entry/exit computation (already correct, confirmed against
the real statement) is untouched -- only how legs are COUNTED changes.

## FIX (as built)

1. **`trades.spread_group_id`** (new nullable TEXT column) -- shared key
   across every leg-trade of one multi-leg order. NULL for a standalone
   single-leg trade (all existing behavior unchanged).
2. **`domain\spread_grouper.py`** (new, pure logic) -- `assign_spread_groups()`
   groups OPENING fills by `order_id`; any order_id covering 2+ distinct
   `full_symbol`s gets every fill in that group tagged
   `spread_group_id = f"SG_{order_id}"`. No named-strategy text parsing
   needed -- a shared live Schwab `orderId` across different contracts is,
   by construction, one multi-leg order.
3. **`schwab_mapper.py`** -- calls `assign_spread_groups(entries)` right
   after splitting entries from exits, before `allocate_exits()`. Fully
   additive: one new import, one new function call, one new log line.
4. **`ingest_pipeline.py`** -- `_build_trade()` reads
   `spread_group_id=raw.get("spread_group_id")` into the `Trade` object.
5. **New view `v_trade_summary_grouped`** (`db_client.py`) -- built on top
   of `v_trade_summary` (never duplicates its pnl/outcome logic), groups
   by `COALESCE(spread_group_id, 'T'||trade_id)`, sums `realized_pnl`
   across the group's legs, and rescoring `outcome` (WIN/LOSS/SCRATCH/OPEN)
   from the GROUP's net P&L instead of trusting any single leg's outcome.
   `realized_R` is a qty-weighted average of the legs' own R (NULL
   propagates correctly when any leg lacks `risk_amount` -- the current
   real-world case for every spread trade, live or paper).
6. **`stats_export.py`** -- `export_summary_by_system`,
   `export_r_distribution`, `export_monthly_summary` now read from
   `v_trade_summary_grouped` instead of `v_trade_summary`. Three-line
   change (FROM clause only) -- no other logic touched.
   `export_equity_curve` / `export_drawdown` were NOT changed -- they sum
   daily cash flow by date, not trade-count win/loss, so per-leg
   granularity there was never wrong.
7. **`migration_add_spread_group_id.py`** (new, idempotent) -- `ALTER
   TABLE` guarded by a column-exists check; both views DROPped and
   rebuilt from `db_client.py`'s own SQL constants every run, so the
   migration can never drift from what a fresh `init-db` produces.
8. **`backfill_p210_spread_groups_20260919.py`** (new, one-off,
   dry-run-by-default) -- tags the 8 pre-existing P_210 legs (ingested
   before this WO existed) into their 4 real spread groups, matched by
   `open_date` against the Schwab statement. Refuses to run if any target
   trade already has `spread_group_id` set or isn't `system='P_210'` --
   fails loud rather than silently overwriting.

correctness, so the fix should be scoped to reporting, not to
restructuring already-correct ledger data.
