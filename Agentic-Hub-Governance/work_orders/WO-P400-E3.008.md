# WO-P400-E3.008 -- Test Suite Has Two Non-Hermetic Tests: Hardcoded Stale Date, Live-Folder Dependency
**Status:** CLOSED
**Owner:** P_400
**Affects:** (none -- internal P_400 only; test_screen.py, test_read_signals.py)
**Depends On:** None
**Acks:** N/A

## WHY

Found 2026-07-08 during independent review of WO-P400-E3.006. Full `pytest`
run in `P_400_TradeOrderManagement\python\` showed 186 passed, 5 failed,
4 skipped -- not the clean suite the E3.006 close assumed. Root-caused
both failure clusters; neither is a regression from E3.006 (which only
touched vault_schemas.py / record_writer.py / record_commands.py / cli.py /
eval_cache.py, none of which these tests exercise).

**Cluster 1 -- test_screen.py (4 failures: test_clean_signal_passes,
test_pass_rr_exactly_at_minimum, test_fresh_signal_no_stale_warn,
test_screen_all_pass_first).**
The shared `_screen()` test helper (and several call sites) hardcode
`signal_date_str="2026-07-02T10:00:00"` as the "fresh, not-stale" signal
date. `domain\screen.py` computes staleness against live `datetime.now()`
(`cal_days = (now - signal_dt).days`, `age_days = int(cal_days / 1.4)`,
compared to `SIGNAL_AGE_MAX_TRADING_DAYS = 3`). On 2026-07-05 (when this
was last verified green) that date was 3 calendar days old -> age_days=2,
under the limit. Today, 2026-07-08, it's 6 calendar days old ->
age_days=4, over the limit -- every test using that fixture date now
gets an unwanted SIGNAL_STALE warning and flips PASS->WARN. This is not a
one-time fluke; the same tests will fail again a few days from now no
matter what, because the fixture is an absolute date compared against a
moving clock.

**Cluster 2 -- test_read_signals.py::test_live_packets_parse (1 failure).**
This test calls `load_v2_signals(SIGNALS_DIR)` where `SIGNALS_DIR` is the
live Obsidian vault signals folder (`config.py`: `VAULT_ROOT /
"TradeOrderManagement" / "signals"`) and asserts `result.valid` is
non-empty. It is not a hermetic unit test -- it passes or fails based on
whatever unprocessed live signal packets happen to be sitting in the
vault at the moment `pytest` runs. Right now that folder is empty
(everything's been processed/zipped per the SIGNALS_PROCESSED_DIR
workflow), so the test fails. It has nothing to do with code correctness.

Neither cluster blocks E3.006 (which is real, verified, and correctly
CLOSED) -- but both will keep throwing false negatives into every future
`pytest -q` run, which is exactly the kind of noise that leads to real
regressions getting waved through as "oh that's just the flaky ones."

## SCOPE

1. `test_screen.py` -- replace hardcoded absolute `signal_date_str`
   fixture values with dates computed relative to `datetime.now()` at
   test run time (e.g. `(datetime.now() - timedelta(days=1)).isoformat()`
   for the "fresh" case), so the suite stays green regardless of what day
   it runs. Applies to `_screen()`'s default and the call sites in
   `test_clean_signal_passes`, `test_pass_rr_exactly_at_minimum`,
   `test_fresh_signal_no_stale_warn`, `test_screen_all_pass_first`.
2. `test_read_signals.py::test_live_packets_parse` -- stop asserting
   against the live `SIGNALS_DIR`. Tony's call on approach during
   implementation: (a) skip with a clear reason when the live folder is
   empty, keeping it as a live smoke-check when packets happen to be
   present, or (b) replace with a hermetic test using a temp dir seeded
   with a known-good v2 packet fixture (same pattern already used in
   `test_malformed_rejected`), moving any live-folder check to a separate
   manual/CLI diagnostic outside the pytest suite.
3. No changes to `screen.py`, `signal_loader.py`, or any production
   logic -- this is test-fixture hygiene only.

## OUT OF SCOPE

- Any change to the SIGNAL_AGE_MAX_TRADING_DAYS threshold or the
  staleness calculation itself -- not in question here.
- Any change to production SIGNALS_DIR / vault processing workflow.

## ACCEPTANCE CRITERIA

- `pytest -q` in `P_400_TradeOrderManagement\python\` returns 0 failures
  when run today, and would still return 0 failures if run again a week
  from now with no code changes and an empty live signals folder.
- No production file touched -- diff limited to `test_screen.py` and
  `test_read_signals.py`.
- Existing regression coverage (BLOCKED-path, RR-below-min, malformed
  packet rejection, etc.) still asserts the same behavior, just anchored
  to relative dates / hermetic fixtures instead of absolute ones.
