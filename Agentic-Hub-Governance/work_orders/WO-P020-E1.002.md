# WO-P020-E1.002 -- Multi-Leg Spread Support (Paper-First)

**Status:** PENDING
**Owner:** Claude
**Affects:** P_020
**Depends On:** WO-P020-E1.001 (sequenced after -- live data-integrity bug takes
priority since it actively misstates real-money P&L every week; spreads are
not live yet, so no active corruption risk from sequencing second)

---

## WHY

Tony is planning to go live with multi-leg spread trades soon. Current code
cannot represent them correctly:

`schwab_mapper.py` `_extract_instrument()` pulls the *first* non-CURRENCY
instrument item out of a transaction's `transferItems` and returns
immediately. For a multi-leg order (e.g. a vertical call spread), Schwab's
transferItems contains one instrument leg per side of the spread --
the function only ever sees the first leg. The offsetting leg is silently
dropped: not parsed, not logged, not flagged as skipped.

The `trades` table schema already accepts `asset_type = 'spread'`
(see CHECK constraint), but no code path in the mapper currently produces it
-- `_map_asset_type()` only returns 'call', 'put', or 'stock'.

Net effect if traded today: a 2-leg spread would be recorded as a single
naked leg with the wrong qty, wrong cost basis, and no record that the other
leg ever existed.

---

## SCOPE

1. **Design first, before code.** Needs a short working session with Tony to
   decide:
   - How a spread is represented as a trade row -- net debit/credit as
     entry_price, or per-leg pricing.
   - Where leg detail lives -- a new `spread_legs` child table (mirrors the
     `exits` pattern) vs. a JSON column on `trades`. Leaning toward a new
     table for consistency with the existing normalized design, but this is
     Tony's call once he sees both options sketched out.

2. Detect multi-leg orders in `schwab_mapper.py` -- multiple non-CURRENCY
   instrument legs sharing one `orderId`/transaction, instead of stopping at
   the first.

3. Compute net entry_price (debit) / exit_price (credit) from the combined
   legs; set `asset_type = 'spread'`.

4. Validate exclusively against PAPER account pulls first. Hard gate in code:
   spread detection only activates for `account_id` containing `PAPER` until
   Tony has reviewed real output against what TOS shows for the same trades.

5. Remove the live gate only on Tony's explicit confirmation after paper
   validation -- not bundled into this WO's completion.

## ACCEPTANCE CRITERIA

- A known 2-leg PAPER spread trade (Tony will identify a real example from
  his TOS paper account) round-trips through the pipeline producing one
  trade row with correct net entry_price and `asset_type = 'spread'`, plus
  correctly recorded leg detail.
- Live account (AJZ6348) spread orders are NOT processed by the new logic
  until the gate is explicitly removed.
- No regression on existing single-leg call/put/stock parsing.
