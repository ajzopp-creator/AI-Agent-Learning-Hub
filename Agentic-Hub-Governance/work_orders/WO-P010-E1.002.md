# WO-P010-E1.002 -- Morning Posture Script Broken 4 Trading Days (QQQ Grid Filename Mismatch)

**Status:** PENDING
**Owner:** P_010
**Affects:** P_400, P_115, P_300, P_020
**Depends On:** none
**Related:** none

---

## WHY

Found live 2026-07-17 during P_400 INIT, cross-checking a mtime/internal-
timestamp mismatch on P_010_RiskConfig.json.

## PROBLEM

`P_010_daily_posture_v5.py` has errored out every trading morning since
2026-07-14 (4 consecutive trading days: 7/14, 7/15, 7/16, 7/17):

```
ERROR: File not found: ...\data\excel_exports\History Grid (QQQ)_v3.xlsx
```

Root cause: the QQQ grid export on disk is named
`History Grid (QQQ_V3.xlsx` (missing closing parenthesis before `_V3`),
not `History Grid (QQQ)_v3.xlsx` as the script expects. SPY and VXX
exports are named correctly. Malformed file's mtime is 2026-07-16 18:53. CONFIRMED CAUSE (Tony,
2026-07-17): manual rename, done quickly in place of a full overwrite of
the QQQ export -- dropped the closing paren. Not an automated export bug.

Last clean morning run: 2026-07-13 07:30:01 (confirmed via
logs\P_010_Daily_20260713.log and grid_snapshot_latest.json). Every run
since inherits and re-serves this same stale baseline:
- spy_posture, qqq_posture, avg_posture frozen at 7/13 values
- spy_grid_date / qqq_grid_date / vxx_grid_date frozen at 07/10/2026
- morning_risk_mode frozen at FULL

The intraday script (P_010_run_intraday_vp_check.bat, 2 PM) is NOT broken
-- it fetches live SPY/QQQ prices correctly and recomputes
intraday_signal/intraday_reason against the (stale) PRANGE each day,
including today. This is why P_010_RiskConfig.json's file mtime updates
daily even though the underlying morning posture data does not -- masks
the staleness from a casual mtime check. Internal `"timestamp"` field
inside the JSON is the reliable staleness signal, not filesystem mtime.

Secondary, unrelated error firing every run:
`ModuleNotFoundError: No module named 'market_health'` (market_health.cli
invocation inside the daily batch). Not yet scoped -- flagging here so it
isn't lost, may warrant its own WO.

## IMPACT

Every downstream consumer reading P_010_RiskConfig.json for `risk_mode`
sizing (P_400 STEP 0/STEP 4, P_115, P_300 screens) has been sizing off a
market read that is 4 trading days stale, while displaying a filename/
mtime that looks current. HALF risk_mode may or may not still be correct
-- cannot confirm without a clean morning re-run against fresh grid data.

## FIX (proposed, not yet applied)

1. Rename `History Grid (QQQ_V3.xlsx` -> `History Grid (QQQ)_V3.xlsx`
   (restore closing paren; Windows filesystem is case-insensitive so
   `_V3` vs `_v3` is not the blocking issue).
2. Re-run `P_010_daily_posture.bat` manually to confirm a clean write
   (new timestamp, current grid dates, recomputed avg_posture).
3. Verify P_010_RiskConfig.json timestamp advances and matches today.
4. Separately scope the `market_health.cli` ModuleNotFoundError.
5. Consider a Guardian/log-level alert for "File not found" in the daily
   log, since 4 days passed silently with no surfaced warning.

## VERIFY

- P_010_daily_posture.bat completes with no ERROR lines in the day's log
- P_010_RiskConfig.json internal `timestamp` matches run date
- grid dates advance past 07/10/2026
- Downstream P_400/P_115/P_300 sessions confirm risk_mode against the
  fresh read before next live sizing decision
