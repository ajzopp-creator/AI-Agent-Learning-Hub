## Corrected understanding (verified this session, not assumed)

The parent WO framed P_400 as "currently shadow-mode only... this WO is
the trigger to plan the shadow-to-live cutover" and asked for vault writes
to "emit CONFIRMED-tier records at order time." Reading `record_writer.py`
directly found most of this already done:

1. **`signal_source` is already received on every call (never optional)
   and already written to every vault record as `why_code`.** This was
   fixed by WO-P020-E1.007 Part 2 / WO-P400-E6.001 -- the code comment
   there says so explicitly: "why_code stayed null on every vault record
   ever written [before this fix]." It's live now, unconditional, not
   shadow -- every P_400 record (stock, options, spread, PAPER) carries
   `why_code = signal_source` at write time already.
2. **"Shadow mode" is not a P_400 behavior at all.** It's
   `system_resolver.py`'s flag, entirely on the P_020 side -- P_400 has
   always written its data live; P_020 just doesn't yet let that data win
   the resolution chain. That cutover is already WO-P000-E24.001's Scope
   item 2, gated by its own explicit-go-ahead. Nothing for P_400 to do
   here -- it doesn't own the flip.
3. **What's actually still missing:** no `confidence_tier` field. Every
   P_400 vault record is by definition a structured capture event at
   order time (WO-P000-E22.001 Rule 3's own `CONFIRMED` definition names
   "a P_400 vault write" explicitly) -- but nothing currently says so on
   the record itself. One field, same shape as the prior `why_code` fix.
4. **Real overlap found, not duplicated here:** WO-P400-E6.001 Scope item
   2 (NOT STARTED, ~18 files/~1,650 lines, needs per-file go-ahead) plans
   a new SQLite `orders` table carrying `council_verdict`/`why_code`/
   `sig_code`/`source_project` columns -- this is the same territory as
   the Attribution Standard's Signal Source ID + confidence tier. Building
   both independently would produce two incompatible attribution schemes
   on the same data. This WO does not touch E6.001's build -- it records
   the requirement so whoever eventually builds E6.001 Scope item 2
   designs those columns to satisfy this Standard instead of reinventing it.

## Scope

1. Add `confidence_tier` field to `write_p400_record()`'s vault payload
   in `record_writer.py`, hardcoded `"CONFIRMED"` -- every call path
   already guarantees this is a structured capture event at order time,
   no conditional logic needed.
2. Spot-check a small sample of live vault records' `why_code` values
   against what was actually traded, before WO-P000-E24.001 flips P_020's
   shadow mode off -- confirms the data P_020 is about to start trusting
   is actually accurate, not just present. Not a full audit; a sanity
   check ahead of a real behavioral cutover elsewhere.
3. Add a note to WO-P400-E6.001 (its own file, not duplicated here)
   flagging that Scope item 2's planned `orders` table columns
   (`why_code`/`sig_code`/`source_project`) should be designed against
   this Standard's Signal Source ID + confidence tier vocabulary when
   that build actually starts.

## Out of Scope

WO-P400-E6.001's own build (orders table, reconciliation step, Bases
fixes) -- untouched, referenced only. The P_020 shadow-to-live cutover
itself -- that's E24.001's decision to make, not this WO's.
