## WHY

Tony's stated operational goal (2026-07-18): **when adding a new batch of
bulk patterns, it should take under 15 minutes to get to the Eval process**
-- and this is a recurring, long-horizon workflow, not a one-off: 1700
symbols licensed in VP, meaning many BulkAddPattern batches ahead as the
catalog is built out. The post-batch M-079 walk-forward score is the
bottleneck standing between "batch inserted" and "eval-ready."

**Hard constraint, Tony's words: however we get there has to be
statistically correct.** No sampling, no approximation, no shortcut that
changes which patterns land in the top-K or alters any BUY/WATCH/PASS
outcome. Byte-identity with the from-scratch computation is the standard
E4.003/E4.004 already set (parallel==serial identity, incremental==full
identity, both regression-tested); this WO inherits it.

## APPROACH REVIEW -- 2026-07-18 (Fable 5 max-effort session, code-verified)

Reviewed against the actual code (domain/similarity.py, domain/
eval_scoring.py, domain/eval_incremental.py, infrastructure/eval_io.py,
application/incremental_post_batch.py), not re-reasoned from the WO
text. Tony approved all findings + the re-ranking below, 2026-07-18.

**Finding 1 -- the DTW kernel is the dominant cost and the strongest
lever (promoted to #1).** Per pair: 10 features x dtw_distance, each a
pure-Python O(m*n) grid loop (m,n = 5-20 bars) -> ~1,500-4,000
interpreted cell ops. The interpreter, not the math, is ~95%+ of
per-pair cost (estimate; Phase 1 confirms). A loop-faithful numba njit
(same op order, float64, fastmath OFF) returns 50-200x on kernels this
shape (estimate) -- plausibly under the 84ms/pattern budget alone, and
it composes with every other lever. Byte-identity achievable: the
kernel is sequential abs/add/min with no reductions to reorder; the
E4.003 model_dump_json regression harness proves it. Two flags:
(a) numba = NEW p140 dependency, Tony install approval required;
(b) similarity.py is shared with Pipeline B's LIVE path -- byte-identity
means signals cannot change, but the live-imported file gets touched, so
the M-079 walk-forward comparison gate applies before any promote.

**Finding 2 -- pairwise cache is right about ~3x today, wrong at scale;
replaced by a top-K state cache.** Verified against _corpus_pids: a full
rescore computes each earlier-dated pair exactly once, N^2/2 total
(5.79e7 at N=10,761). Cross-run pairwise caching leaves only new-pattern
pairs (~1.9e7 here) -- the ~3x holds. But pairwise persistence is O(N^2)
storage: ~1-2 GB today, ~25 GB+ at N=50k (estimate). Dead end at
1700-symbol scale. Replacement design: cache each pattern's top-K state
(top-K pids + composite distances, O(N*K) storage, megabytes). A new
corpus member enters X's top-K iff its distance beats X's current Kth;
baselines/z-scores recompute from labels (cheap). Same math; per-batch
cost drops from O(N^2) to O(B*N) -- removes the quadratic rather than
shaving a constant.

**Finding 3 -- tie-order fragility (pre-existing; every lever inherits
it).** rank_by_distance sorts by composite ascending with NO explicit
tiebreak; ties resolve by dict construction order of corpus_windows.
Top-K byte-identity is therefore fragile against any refactor that
changes dict build order. Fix = deterministic tiebreak (distance, pid),
but ONLY after a census proves zero exact ties at top-K boundaries on
the real catalog (then formalizing is byte-identical; nonzero ties =
stop-and-review to Tony). Census added to Phase 1 as item (e).

**Finding 4 -- unexplained 3-12x discrepancy between the two real
measurements; Phase 1 must resolve it.** E4.003 (2026-07-16 PEH run):
1848.6s / 3.34e7 pairs = ~55us/pair effective, ~64us/pair implied
serial. The exit-1 diagnostic running 2026-07-18 (its fsync'd log):
2.3s/pattern early, 8.2s/pattern by index ~1090 -- a floor of
214-762us/pair even if those pids' corpora were the full 10,760. Same
math, 3-12x apart. Candidate causes (not asserted): resident DeepSeek
14B / same-box load, window-length mix, corpus-size mix. The
diagnostic's log is 10,738 free per-pattern timing samples; joined
against pid->corpus_size from the staging DB it becomes the full
cost-vs-corpus-size curve. That join is Phase 1 item (f).

**Scale re-scope (Tony-approved 2026-07-18).** At current density
(~26 patterns/symbol, from 8,175/317 last preflight), 1700 symbols ~=
~44k patterns (density assumption stated). Full-rescore work is N^2/2
pairs; at optimistic post-lever constants (25us/pair JIT, 8x effective
parallel -- both estimates) the 900s budget covers N ~= 24k; at
10us/pair + 12x, N ~= 46k. Constant-factor levers alone cap the full
rescore at ~25-45k patterns -- at or below licensed scale. Therefore:
**the <15-min target applies to the per-batch path (O(B*N) via the
top-K state cache); the full from-scratch rebuild becomes a scheduled
(e.g. overnight/weekend) event at scale, not a per-batch step.**

## CANDIDATE LEVERS (re-ranked 2026-07-18 after code review; supersedes
the original same-day ranking; still subject to profiling)

1. **JIT the DTW kernel (numba njit, loop-faithful, fastmath OFF).**
   Promoted from #3: the cost model says interpreted DTW cells dominate
   (Finding 1). 50-200x candidate constant factor (estimate). Byte-
   identity required and testable via the existing E4.003 regression
   harness; any float divergence = stop-and-review, never silent.
   New p140 dependency (install approval) + live-path file flag
   (Finding 1) both apply.
2. **Fix parallel scaling.** Unchanged at #2; true cause unknown --
   candidate causes to discriminate in Phase 1(d): pool-init pickling
   of the three big dicts per worker (Windows spawn, no fork), per-task
   dispatch/result-pickle overhead, CPU utilization / same-box load,
   memory pressure. Even a clean 8x here ~= target at current N.
   **RE-EVALUATED, PARKED (Phase 2c, 2026-07-19):** post-JIT, does not
   beat serial at any tested worker count (2-24) or batch size
   (50-400) on the real staging catalog. Root cause matches this
   list's own candidates -- per-worker startup cost (numba cache
   load + Windows-spawn re-import) confirmed real via a pool-reuse
   test (2.1x faster on an already-warm pool), and that cost appears
   to worsen with concurrent worker count (contention), not just
   accumulate linearly. One unreproduced data point (batch=400 near
   parity, ~1.01x) leaves open whether a larger real-world batch
   could cross over -- not confirmed, not acted on. See WO's PHASE 2c
   RESULTS section for full detail. Do not re-enable
   EVAL_PARALLEL_ENABLED based on this alone.
3. **Top-K state cache (replaces the pairwise (pid_a, pid_b) cache).**
   O(N*K) storage, O(B*N) per-batch compute (Finding 2) -- the lever
   that makes 15 min survive 1700-symbol scale. Correctness
   precondition: tie-order resolved first (Finding 3). Pairwise-cache
   variant demoted: same near-term ~3x, O(N^2) storage dead end --
   build only if the state-cache design fails review.
4. **Cheap pre-filter before full DTW** -- PARKED, unchanged. Risks
   changing top-K membership at the margin; fails the statistical-
   correctness constraint unless proven otherwise. Not in scope unless
   #1-#3 measurably cannot reach target.
5. **Corpus sampling/capping** -- REJECTED, unchanged (E4.004 OUT OF
   SCOPE inheritance). Changes the statistics by construction.

## PHASE 2c RESULTS -- 2026-07-19 (run_this.py, PASS, lever #2 re-evaluated)

Three timing-only experiments against the real staging catalog, all
drawing from a corpus_size-banded pool (2500-4000, 1497 pids available)
so every task costs roughly the same (~221ms/task measured serial rate
-- matches the Phase 2b asymptotic rate of 0.0654ms/pair x ~3250
corpus_size midpoint, confirming the band worked as designed).

**Experiment A -- worker-count sweep, batch=50: no worker count beat
serial. Closest was 2 workers at 1.18x slower (13.08s vs 11.07s
serial); 16/24 workers landed at ~2.8x slower.** Independently
re-derived the overhead structure (not just the ratios) by subtracting
an idealized perfectly-parallelized compute time from each measured
parallel time: residual ("overhead") GROWS with worker count in
absolute terms -- 7.5s@2, 14.0s@4, 26.6s@8, then plateaus ~30.8s@16
and @24. This is NOT simple fixed-cost-per-worker (which would predict
residual scaling roughly linearly with worker count, forever) -- it
looks like a ceiling/contention effect once worker count is high
enough (8+), consistent with concurrent workers contending for a
shared resource at startup (candidate: simultaneous reads of numba's
on-disk JIT cache, or Windows process-spawn contention -- not
investigated further, flagged for anyone touching this again).

**Experiment B -- pool reuse: batch 2 was 2.12x faster than batch 1 on
an already-warm pool (19.51s vs 41.29s, both 100 tasks). One-time
worker-startup cost confirmed real and substantial**, consistent with
Experiment A's contention-flavored residual. Practical caveat not to
overstate: production's `run_walk_forward()` creates+tears-down its
pool inside the function per call -- a persistent, session-scoped pool
only pays off if something in the real call pattern invokes it more
than once per process (e.g. "pre" and "post" batches sharing a pool
within one BulkAddPattern run, if that's ever restructured) -- not
assumed here, just noted as the kind of change this finding would
motivate if pursued.

**Experiment C -- batch-size sweep (real default, 24 workers): no
crossover in 50-400. Ratio trend 3.10x/2.14x/1.51x/1.01x -- approaches
parity at 400 but does not cross it.** Re-checked the absolute (not
just relative) overhead behind that trend: 21.5s/24.3s/22.3s/1.1s --
roughly flat ~22-24s through size=200, then an unexplained near-total
collapse to ~1s at size=400. This does NOT fit a simple fixed-overhead
or per-task-overhead model cleanly (a naive extrapolation from the
50->200 trend predicted ratio~1.23 at 400, not the observed ~1.01) --
treating this as a single-run anomaly, not a confirmed trend, until a
repeat measurement at size=400 (and maybe 300, 500) either reproduces
it or doesn't. Possible confounds not ruled out: OS/disk-cache state
changing over the run's ~600s wall-clock, or genuine but unexplained
parallel-efficiency improvement at this specific batch size. Flagged,
not resolved.

**Honest bottom line: lever #2, as currently scoped (fix the per-call
ProcessPoolExecutor fan-out inside run_walk_forward), does not beat
serial at any tested configuration on this catalog's current size,
with the real default worker count.** The batch=400 near-parity result
is the one data point suggesting it MIGHT cross over at larger
real-world batch sizes, but it's a single unreproduced measurement with
an unexplained shape -- not a basis for re-enabling EVAL_PARALLEL_ENABLED
on its own. Lever #2 stays parked; lever #3 (top-K state cache) remains
the only lever with a clear path to the <15-min target.
