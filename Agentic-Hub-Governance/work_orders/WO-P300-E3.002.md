## WHY -- the actual problem being solved (Tony, 2026-07-12)

Tony's manual cataloging workflow: IntelliScan surfaces N symbols
(crossovers + Williams EMAI + Professional Sentiment). For each, he
pulls a chart, draws the profit-calc line, and checks whether price
action produced a >15% profit or >15% loss within his window --
5-7 minutes per symbol, edge cases longer (window expansion). That
measurement step is arithmetic, not judgment: the grid export already
contains every number needed to compute it exactly. The judgment part
(final is-this-chart-real approval) takes seconds.

**Why the E2.003 bulk merge disappointed, reframed:** the bulk run
selected SETUP-FIRST -- every bar where 9 conditions fired, outcomes
unfiltered (chop, failed launches, everything). Tony's manual process
selects OUTCOME-FIRST -- find the >=15% move, then work back to the
launch bar. Opposite selection rules produce different populations;
pooling the unfiltered one diluted the curated one (68.8% -> 63.6%,
M-079). This WO implements Tony's actual selection rule in code and
keeps him as the approval gate -- so what enters the catalog is the
same population his manual process produces, found automatically.

**Expected effort reduction:** 5-7 min/symbol -> ~15 sec/symbol
(approve/reject a computed row instead of drawing lines).

## DESIGN -- resolved with Tony 2026-07-12

**Screen (outcome-first, both directions FORWARD from the anchor --
confirmed with Tony 2026-07-12):** an anchor bar QUALIFIES if any of
the five existing horizons (h5/h7/h10/h15/h20 -- Tony confirmed:
"within the 5/7/10/15/20h, that's what I was doing manually") shows
forward return >= +15% (riser) or <= -15% (breakdown). Threshold is a
config constant (MINE_MOVE_THRESHOLD = 0.15, decimal per M-020), not
hardcoded.

**Class labels -- CORRECTED 2026-07-12, do not conflate with M-033:**
Tony confirmed his "loss > 15%" screen looks FORWARD -- anchor now,
price breaks down 15%+ AFTER it. This is NOT M-033's pullback
definition, which is a TRAILING decline (15-25% BEFORE the anchor,
anchor = the bottom/basing point, expecting a bounce). The two are
opposite in structure and serve opposite purposes -- pullback is a
buy-the-dip setup, this new class is a breakdown/avoid signal. Riser
hits label as `uptrend` (existing M-033 class, unchanged). Breakdown
hits label as a NEW class, `breakdown` -- distinct in every report/CSV
column, never silently folded into `pullback`. No DB schema change is
needed for this (checked `schemas.py`: `pattern_instances` has no
stored class/type column at all -- uptrend/pullback is an M-033
composition target Tony tracks by eye, not an enforced field), but the
MINE candidates report and CSV must use the correct label so that
tracking stays accurate. M-033's actual pullback pattern (trailing
decline + bounce) is NOT built by this WO -- out of scope, Tony's
manual process for that continues unchanged unless a future WO scopes
it specifically.

**Why `breakdown` still routes through the same M-079 staging-eval
gate as everything else:** adding a differently-selected population to
the live analog pool without testing first is exactly what went wrong
in E2.003. `breakdown` patterns have never been in the live catalog in
any form -- the existing staging eval comparison (already required by
this WO's Phase 2) is the right check for whether they help or hurt
BUY/WATCH/PASS precision, same scrutiny as uptrend gets, no special
carve-out needed since the machinery already generalizes.

**Screening window -- REVERSED 2026-07-12, see M-081:** an earlier
draft of this WO capped screening at the catalog's 20-trading-day
horizon (matching FORWARD_HORIZONS), reasoning a longer find would be
"mismatched" with its own stored forward_labels. Real validation data
showed this would have excluded 16 of Tony's own historical picks --
several of his cleanest winners (LMT +15.4% in 87 trading days, SPY
+15.3% in 89, GOOGL +24.4% in 94). Tony challenged the cap directly
("why would we do that unless h20 is proven not a reliable measure")
and was right: forward_labels are always computed honestly regardless
of selection reason, and whether a wider population helps or hurts
precision is exactly what the M-079 gate above already exists to
measure, not something to pre-decide in code. Screening now extends
to `MINE_MAX_SCREEN_DAYS=180` (~Tony's original "6-9 month" framing).
Every `MineRow`/CSV row carries a `standard_horizon` flag distinguishing
finds within FORWARD_HORIZONS (directly comparable to every other
cataloged pattern) from extended finds -- transparency, not exclusion.

**Scanning algorithm -- REWRITTEN 2026-07-12 (Tony's design), see
M-083:** v1.0-v1.3 screened every bar independently and used a dedup
window to collapse overlapping finds into one launch. Real validation
(LMT 2025-09-02 traced directly) showed this architecture is
structurally wrong during a persistent trend -- nearly every bar
independently qualifies, so no dedup-window VALUE can correctly pick
which one is "the" launch; two genuinely-correct narrow fixes (M-082's
dedup cap included) still left the hit rate far short. Tony proposed
the actual fix directly: a sequential cursor scan per class that JUMPS
PAST the entire window once a match is found (`cursor = match_idx +
horizon_days + 1`), so non-overlap is structural rather than cleaned
up after the fact. Runs independently per class (UPTREND/BREAKDOWN) so
an unrelated breakdown can still be found overlapping in time with an
uptrend elsewhere. Naturally produces multiple anchors through a long
trend, matching how Tony's own ground-truth picks actually cluster.
Honest limitation kept in the code's own docstring: even this cannot
guarantee landing on Tony's exact chart-picked bar within an unbroken
qualifying stretch -- that would need a technical/setup signal (e.g.
the existing 9-condition crossover detector) layered on top, not a
purely outcome-based fix. `domain/pattern_miner.py` v1.4.

**Anchor eligibility (M-022):** every candidate anchor needs >= 20
bars back (setup window) and >= 20 bars forward (labels) -- the same
eligibility the bulk pipeline already enforces. Anchors are
additionally restricted to the post-backfill window (>= 2021-07-14,
the WO-P300-E2.001 Phase 0 boundary) -- a pattern whose predictive
features are blank is useless as a Pipeline B analog regardless of how
big its move was. ("Keep only the earliest bar of a qualifying run"
was the v1.0-v1.3 dedup description -- superseded by the sequencing
rewrite below; a persistent trend now yields multiple anchors via the
cursor-jump mechanism, not one collapsed anchor.)

**VALIDATION -- against Tony's own picks, automated (resolved 2026-07-12):**
Ground truth already exists on disk: the processed-folder monthly zips
(2026-05/06/07) hold every archived AddPattern source file -- 516
pattern files across 308 symbols, symbol + anchor date parseable
directly from filenames (verified via PowerShell zip enumeration,
no extraction needed). Validation exercise: Tony exports fresh grids
for 20 selected multi-pick symbols (~85 ground-truth anchors); the
miner runs against them; every one of Tony's anchors must appear in
the miner's output at the matching launch date (window: +/- 2 bars,
edge tolerance for his eyeball vs computed launch). Misses are bugs.
Extra finds beyond his picks are the expected upside, reviewed for
sanity. Iterate until clean -- Tony does NOT audit rows manually;
the comparison against his own historical picks IS the audit.

**AUDIT AGENT (new component, Tony's design call 2026-07-12):** the
checks that prove meaningful during the validation exercise get
codified into `domain/mine_audit.py` -- a standing pre-ingest gate
that phase 2 runs automatically on every future batch: move really
clears threshold at the claimed horizon (recomputed independently),
anchor is the launch not a mid-run bar, eligibility windows hold,
post-backfill restriction holds, no catalog collision. Once the audit
agent is validated, Tony's per-row CSV approval becomes an optional
spot-check, not a required step -- the agent does in the workflow
what the 20-symbol exercise did once. Exact check list is DEFINED BY
the validation findings, not guessed up front.

**Two-phase, operator gate in the middle:**
- Phase 1 `mine-patterns`: glob `data/bulk/mine/` (NEW folder --
  separate from nightly_scan/, different lifecycle), parse each grid
  via `parse_bulk_file()` (any period -- 2-month live window
  limitation disappears, Tony exports whatever span he wants),
  compute per-bar forward returns with `bulk_labeler`'s exact math,
  apply the screen, write: (a) a human-readable candidates report
  (md), (b) a machine-readable candidates CSV -- ticker, anchor date,
  class (`uptrend`/`breakdown` -- see Class labels above, never
  `pullback`), best horizon, move %, keep column defaulted to YES.
- Audit gate (`mine_audit.py`, once validated): every approved row
  re-verified independently before staging insert. Tony's CSV edit
  is optional spot-check.
- Phase 2 `ingest-mined`: read approved CSV, re-read the source grid
  files for approved anchors only, insert via catalog_merge_io's
  existing bulk->live insert path into a STAGING COPY, run the same
  verify step E2.003 built (collision check, structural counts),
  atomic-promote. Pre-promote backup, same as every catalog write in
  this project.

**M-079 compliance:** first real ingest batch gets a staging
walk-forward eval comparison (staging vs live, run_eval_loop) before
promote -- the same gate that correctly blocked E2.003. Expected to
pass this time because the population is outcome-proven + approved,
but expected != verified; the gate runs.

**No auto-archive in v1:** mined grid files stay in data/bulk/mine/
until ingest completes (phase 2 re-reads them); Tony manages the
folder after. Archive automation can come later if folder hygiene
becomes a burden.
