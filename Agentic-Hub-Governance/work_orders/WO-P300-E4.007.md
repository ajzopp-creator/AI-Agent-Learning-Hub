## WHY

Tonight's real BulkAddPattern batch (mine-patterns -> ingest-mined)
halted on a `TopKTieError`: pid=10960 (CXW, new pattern) ranked two
different historical patterns at an EXACT tie for its rank-20/21
boundary. `domain/topk_cache.py`'s own "Finding 3" rule deliberately
refuses to silently break such a tie -- STOP and report.

Investigation (two rounds -- the first diagnostic's own closing line
wrongly called it "a genuine coincidence" based only on a 0/20 spot-
check rate, without checking whether the tied patterns were duplicates
of each other; corrected on Tony's direct catch) found: the two tied
patterns, pid=26 and pid=437, were both WFG @ 2026-01-08, byte-
identical bars, byte-identical forward labels, imported from two
different xlsx files (`Pattern_20260108_20260126_WFG.xlsx`, 2026-05-21,
vs `Pattern_20260108_20260128_WFG.xlsx`, 2026-07-04) -- the same real
pattern, re-exported from VP with a slightly later end date, silently
double-inserted.

**Root cause:** EC-023 (Pipeline A's ingest guard) only blocks an
EXACT filename match. A re-export with a different end date produces
a different filename and sails straight through. The bulk path
(`catalog_merge_io._pattern_already_exists`, mine_audit's "catalog
collision" check) already had a real `(ticker, anchor_date)` dedup
check -- Pipeline A (`add_pattern_pipeline.py`) never did.

**Catalog-wide scan** (not just the one WFG pair) found exactly 4 such
doubles: WFG (26/437), PLTR (17/36), BOIL (449/487), RRC (353/405) --
all bar-identical and label-identical to their earlier-imported twin.
0/20 other recent patterns showed a rank-20 tie -- the halt itself was
rare, but each of the 4 doubles was a live landmine for any future
pattern that happened to rank close to one of them.

## TWO REAL BUGS FOUND VIA ACTUAL EXECUTION, NOT GLOSSED OVER

1. **FK-ordering bug, caught by the dry run (exactly what it's for):**
   `topk_cache` FK-references `pattern_instances` on BOTH
   `pattern_instance_id` and `matched_pid`. v1.0 wiped `topk_cache`
   AFTER the per-pid delete loop; any surviving `topk_cache` row for a
   REMOVE_PID blocked that pid's `pattern_instances` DELETE with a
   real `sqlite3.IntegrityError`. Fixed in v1.1: wipe moved before the
   loop. `connection_context`'s rollback-on-exception confirmed the
   partial dry-run attempt left no corruption (verified directly, not
   assumed).
2. **PEH harness encoding bug, caught by the live verification:**
   the verification script read the migration's log file as UTF-8;
   Windows PowerShell's `Tee-Object -FilePath` defaults to UTF-16LE
   (confirmed via raw byte inspection: `FF-FE-49-00-4E-00-46-00`, a
   UTF-16LE BOM followed by "INF..."). Reading as UTF-8 produced null-
   byte-interspersed text that still LOOKED clean when printed but
   broke an exact substring check. Not a migration failure -- the
   migration's actual success was already independently confirmed via
   the `.bak` file's preserved original mtime and the live file's
   fresh mtime, both checked directly via the filesystem before the
   log-parsing bug was even diagnosed. Fixed with an encoding retry.
