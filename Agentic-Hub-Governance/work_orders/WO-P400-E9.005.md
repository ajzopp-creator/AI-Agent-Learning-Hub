## WHY

Found 2026-09-26 while checking the AMZN resync from WO-P400-E9.002.
P_020 `orders` row 13 (AMZN 261016C260, REAL, schwab_order_id
1008004303125, 1 contract filled at $7.72) had `qty=0.0`. Row 11 (NFLX,
PAPER, option trade) also has `qty=0.0`. Every stock row has its real
share count.

Traced live against disk:

1. Every option/spread record builder writes `position_size=0` and puts
   the contract count in a separate `option_contracts` field:
   - `infrastructure\record_writer.py` line 182 (`write_options_eval_record`,
     `evaluate --options` path) -- `position_size=0`, line 187
     `option_contracts=contracts`
   - `infrastructure\record_writer.py` line 231 (`write_spread_eval_record`,
     `evaluate --spread` path) -- `position_size=0`, line 235
     `option_contracts=contracts`
   - `application\size_option_standalone.py` line 144 (`size-option`
     path, WO-P400-E8.003) -- `position_size=0`, line 152
     `option_contracts=contracts`
   This is by design for the vault note: `position_size` means shares.
2. All three cache those same fields to eval_cache.
3. `application\record_commands.py` `cmd_record_submit()` line 78 passes
   `position_size=fields["position_size"]` to `write_order_to_p020()`,
   which sends it to P_020 as `qty` (`order_submit_writer.py` line 73). It
   never looks at `option_contracts`.

Result: every option or spread trade recorded through `record` lands in
P_020 with `qty=0`. AMZN's row came from the one-off
`resync_amzn_e9002.py`, which hardcoded `qty=0` (line 28) -- the same
wrong value by a different route.

**Impact today:** limited. P_020's reconciler (`domain\order_reconciler.py`)
takes quantity, fill price, asset_type and put_call from Schwab's order
chain, not from `orders.qty`, so realized P&L is not affected. What is
wrong is the planned-size record itself -- any report or audit reading
`orders.qty` for an option trade sees zero.

**Data already corrected (2026-09-26, Tony's request):** row 13 AMZN
`qty` 0 -> 1, guarded single-row UPDATE (matched on order_id, symbol,
schwab_order_id and qty=0). DB backup:
`P_020_...\data\database\P_020_trades.db.backup_2026-09-26`.
Row 11 NFLX NOT corrected -- see Open Question.

## WHAT

1. `cmd_record_submit()`: pass the contract count for option/spread
   records -- `fields.get("option_contracts")` when present and not None,
   else `fields["position_size"]`. One line plus a comment; the
   `write_order_to_p020()` signature does not change.
2. Update the `position_size` docstring in `order_submit_writer.py`
   (it currently says "Share/contract quantity, same value the vault record
   stores," which is false for options).
3. Tests in `tests\test_record_commands.py`: an option-shaped cache
   (`position_size=0`, `option_contracts=3`) sends qty=3 to P_020; a
   stock-shaped cache (no `option_contracts`) still sends `position_size`
   (existing `test_submit_writes_order_id` stays green).
4. Fix row 11 (NFLX) only after the Open Question is answered. (Done
   2026-09-26 -- see BUILD.)

## Open Question (Tony)

**Planned vs executed quantity.** This fix sends the *sized* contract count
(what the spec said). It does not capture what actually filled. `record`
has no `--qty` flag, so when the fill differs from the spec (skill Must #7:
MRCY specced 7/filled 10; NFLX sized 2 by the real sizer, 4 traded by eye
per WO-P400-E8.003) both the vault note and P_020 keep the specced number.
NFLX row 11 can't be corrected from code alone -- the right value depends
on whether `orders.qty` should mean planned or executed. Recommendation:
keep `orders.qty` = planned (it sits next to `planned_*_price`; Schwab
supplies executed qty at reconcile), and set NFLX to its sized count.
Adding a `record --qty` flag would be a separate WO if wanted.

**ANSWERED 2026-09-26 (Tony): planned size.** `orders.qty` = planned
quantity. Correction to the recommendation above: the "sized count" for NFLX
is NOT 2. NFLX's own vault record
(`trading_journal\TradeOrderManagement\P400\paper\2026-09-14_NFLX.md`)
shows `option_contracts: 4`, `option_method: manual_override_no_auto_sizing`
-- 4 was the recorded plan at trade time. The 2 came from E8.003's
retroactive sizer check and was never the plan. The fixed code would have
written 4, so 4 is the value consistent with "planned size."
