## DESIGN

Move the check off the skill-file/session-memory layer entirely, onto the
same mechanism already proven in WO-P000-E4.001's INIT Execution Bypass
Pattern (P_300 preflight-bat + status-JSON): a script outside the chat
session does the check; INIT reads the result as a fact, not a judgment
Claude re-derives from memory each session.

1. **Script** (working name `lessons_audit.py`, p140):
   - Input: a project's `tasks\lessons.md` (M-series entries).
   - Cross-reference targets: WO_COMPLETION_GATE.md's Completion Gate
     checklist text (Hub-wide, shared), the relevant EC log (P_000
     Section 6, or a project's own if it has one), and that project's
     skill file(s) under `.claude\skills\`.
   - Method (revised 2026-09-04, see DECISIONS LOCKED): LM Studio
     inference (DeepSeek R1 14B, `primary` tier) via the existing
     `integrations\lm_studio` wrapper is the primary classifier -- one
     call per lesson entry, prompted to judge whether the lesson is
     enforced elsewhere against the same cross-reference targets above.
     On `LMStudioClient.chat()` returning `None` (LM Studio unhealthy,
     not running, or no response), fall back to the deterministic
     keyword/string overlap scorer already built at
     `shared_resources\python_utils\lessons_audit\domain.py` (v1.3).
     Output records which method produced each lesson's classification
     -- a fallback run is never presented with the same confidence as
     an LM Studio run. Rationale: the keyword scorer's own v1.3 real run
     still false-flagged all 3 live lessons after three fix iterations
     (see WHY addendum) -- it is retained as a degraded-signal fallback,
     not the primary classifier.
   - New `TASK_ROUTING` entry required in `integrations\lm_studio\config.py`:
     `"lesson_classification": "primary"` (none exists yet).
   - Output: `lessons_audit_status.json` -- per-lesson flag
     (LIKELY_ENFORCED_ELSEWHERE / LIKELY_STILL_LIVE / UNCERTAIN), the
     matched source reference, classification_method (LM_STUDIO /
     KEYWORD_FALLBACK), and a generation timestamp.

2. **Wiring:** INIT (system-doc-initializer) reads
   `lessons_audit_status.json` if present and newer than `lessons.md`'s
   own last-modified time; surfaces flagged entries once per session,
   same posture as Step 1b's Daily Gate Check. Staleness check on the
   JSON itself mirrors Section 3.5's WARNING logic (stale JSON -> ask
   operator to re-run, don't silently trust an old result).

3. **Trigger:** script run manually (Python subprocess via windows-mcp
   hangs -- Hub-wide rule, hand to Tony via Anaconda Prompt, same as
   every other p140 script) -- see DECISIONS LOCKED Decision 2.

4. **Rollout:** pilot on P_000's own `tasks\lessons.md` first (same
   discipline as Section 3.6/3.7's pilot-then-Hub-wide-audit pattern),
   before adopting Hub-wide.

## OUT OF SCOPE

The script only flags. It never auto-edits or auto-deletes a lessons.md
entry. A human (Tony) or a separate session decides whether a flagged
entry actually gets archived/retired -- consistent with
WO_COMPLETION_GATE.md's "Independent Review is not a place to hand off
undone work" principle: the script doesn't get to self-certify its own
flags as correct, either.

**Item 4, Rollout -- COMPLETE (2026-09-04).** Ran against the real P_000 `tasks\lessons.md` (M-001/M-002/M-003). First two attempts failed -- all 3 lessons fell back to keyword scoring, every LM Studio call dying at exactly the client-side chat timeout with only 2-4 reasoning tokens generated. Root-caused, not guessed at:

1. Bumped `HTTP_TIMEOUT_SECONDS` 30->90 in `integrations\lm_studio\config.py` (chat timeout 90s->270s) after confirming via the LM Studio dev console log that all 3 failures hit the 90s wall precisely, and that this mornings P_300 calls on the same model legitimately ran up to 110s. This alone did not fix it -- the third attempt still failed identically at the new 270s ceiling.
2. Task Manager showed GPU 0 at a flat 0% during generation, CPU unremarkable, system-wide UI lag -- not "slow reasoning," barely any compute happening at all. Root cause: two model instances were loaded in LM Studio simultaneously, splitting an 8GB VRAM budget neither could fit in alone. Tony ejected both and reloaded a single instance.
3. Verified the fix in two steps before re-touching the script: (a) Task Manager showed real GPU utilization (28-100%) on the next LM Studio call, (b) the exact M-001 prompt -- reproduced independently byte-for-byte (2301 chars, matching the real runs logged `input_len`) and pasted directly into LM Studios own chat UI -- completed cleanly with a correctly formatted answer, isolating the model/prompt as NOT the problem before spending another real run on the script.
4. Final run: 3/3 lessons classified via LM_STUDIO, zero fallback. All three correctly came back LIKELY_STILL_LIVE -- the LM Studio path did not repeat the v1.3 keyword scorers false-positive failure this whole redesign exists to fix. Output: `projects\P_000_PythonClaudeLocalLLM\tasks\lessons_audit_status.json`.

Correction (2026-09-04, same session): the HTTP_TIMEOUT_SECONDS bump above was partly justified by claiming P_300s successful 108-second call that same morning used the same wrapper/timeout -- checked P_300s actual code afterward and that claim was wrong. P_300 has its own separate client (`P_300\python\infrastructure\llm_client.py`) -- OpenAI-compatible `/v1/chat/completions` endpoint, synchronous `requests`, its own independent 120s timeout -- not this shared wrappers 90s. P_300 succeeding at 108s proves nothing about whether the wrappers original 90s ceiling would have held once VRAM contention was fixed. Well-evidenced conclusion: the confirmed fix is the single-instance reload (GPU utilization returned, manual UI test and full script both succeeded after it). The timeout bump 30->90 is left in place as harmless for other wrapper consumers, but should not be cited as a proven-necessary fix -- it may have been irrelevant to what actually broke.

## RELATED FINDING -- Duplicate LM Studio Client, P_300 (2026-09-04, same session)

Investigating the LM Studio failure above surfaced that P_300's Stage 8
narrator does NOT use the shared `integrations\lm_studio` wrapper this
WO's Rollout depends on. It has its own separate client:
`P_300\python\infrastructure\llm_client.py` -- OpenAI-compatible
`/v1/chat/completions` endpoint, synchronous `requests`, its own
120s timeout, built 2026-05-19 (before the shared wrapper existed in
usable form -- that wrapper's own dev lessons.md shows it was still
being debugged 2026-05-28/30). WO-P000-E14.001 (closed 2026-08-25)
already investigated this exact area consolidating a P_000-local fork
of the shared wrapper back to canonical, and explicitly confirmed
P_300's `llm_client.py` is a separate, deliberate thing, not part
of that duplication -- P_300 does consume part of the canonical wrapper
(`lm_studio_status.py` for health checks) but not the chat-calling
part. That same WO's v3 changelog (2026-08-07, a month before today)
already flagged the shared wrapper's 90s chat timeout as too short for
DeepSeek R1 on this hardware and explicitly warned against a one-line
bump buried in an unrelated WO's diff -- exactly what this WO's own
BUILD PROGRESS section above did, without knowing that warning existed.

Tony's decision (2026-09-04): leave P_300 on its own client as-is.
Not filing a separate migration WO -- revisit only if a real blocking
issue forces it. Recorded here so a future session does not treat the
two-implementation split as an oversight needing a fix; it is a known,
deliberate deferral, not a gap.
