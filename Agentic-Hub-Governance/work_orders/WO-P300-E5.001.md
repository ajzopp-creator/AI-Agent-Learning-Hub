## WHY

Filed 2026-07-17 (evening) during a live-batch-wait discussion of a KB
article ("10 Python Libraries That Made Me Stop Writing Messy Code").
The article's diagnosis on `import-linter`: Python's import system has
no enforcement mechanism, so a clean layer diagram (domain /
infrastructure / application, as documented in P_300's own
architecture doc and `p300-project-context` skill) is honor-system
only -- nothing stops a future session (mine or otherwise) from
importing across a layer boundary because it's the shortest path.

P_300 specifically has named, documented layers already (unlike most
of the other Hub projects, which weren't designed with this split) --
making it the only project where writing real `import-linter`
contracts is a natural fit rather than a forced retrofit. Currently
enforced only by my own review each session and the skill file's
written rules, never by an automated check.

## SCOPE NOTE -- explicitly NOT decided yet

- P_300 only. Not Hub-wide -- other projects (P_010/P_020/P_115/
  P_400/P_800) may not share this same formal layer split; bolting
  contracts onto them is a separate, bigger conversation, not part of
  this WO.
- No CI exists in this environment -- PEH is a manual, operator-
  triggered step. This would become another PEH check run before
  closing a WO, not an automatic gate. Weaker enforcement than the
  article assumes, still real value over pure manual review.
- **First real risk, called out honestly:** the first contract run
  against the existing codebase might not come back clean. This has
  been enforced by eye, not exhaustively -- an actual audit could
  surface real violations nobody's caught yet. Plan must budget for
  that possibility, not assume a trivial add-and-pass.
