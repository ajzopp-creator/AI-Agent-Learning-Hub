## WHY

Filed during WO-P300-E4.003's closure discussion (2026-07-16). E4.003
made the "post" (staging) walk-forward batch faster per-pattern
(parallel scoring), but it still re-scored the ENTIRE staging catalog
every single BulkAddPattern run -- 8175+ existing patterns plus
whatever 0-15 new picks Tony approved that day. Measured real cost:
~30.8 minutes for one full pass at 8175 patterns (WO-P300-E4.003 PEH
run, 2026-07-16), and that number only grows as the catalog grows.

**The insight:** `domain/eval_scoring.py`'s `_corpus_pids()` restricts
each pattern's corpus to patterns with a STRICTLY EARLIER anchor_date
(temporal exclusion, by design). On a normal daily BulkAddPattern run,
every one of that day's approved picks has today's anchor_date --
later than every existing catalog pattern. A later-dated pattern can
never appear in an earlier pattern's corpus. Therefore:

- None of the pre-existing patterns' `WalkForwardResult` can ever
  change by adding today's new picks. Their "post" score is
  mathematically identical to their already-cached "pre" score, every
  single day, by construction -- not an approximation, an identity.
- Only the day's new patterns need real scoring, each one built
  against the full existing corpus (same corpus size as the "pre" run,
  same cost per pattern as any other single pattern).

## DESIGN AS BUILT (2026-07-17, supersedes the 2026-07-16 draft plan)

**File-size collision found during planning, not anticipated in the
original draft:** `domain/eval_scoring.py` and `application/ingest_
mined_pipeline.py` were BOTH exactly 300 lines (the hard limit, zero
headroom) at planning time. The original draft's estimate of editing
`domain/eval_scoring.py` directly (+30 lines) and `application/
ingest_mined_pipeline.py` directly (+40 lines) would have broken the
hard limit on both files. Redesigned to touch neither file's cap:

1. **`domain/eval_incremental.py` (NEW)** -- `assemble_incremental_
   post_batch()` reuses `score_one()` (domain/eval_scoring.py,
   UNCHANGED, imported not reimplemented) for new pids only; pulls
   every unaffected pid's result straight from the cached pre-batch.
   Guardrail: `_validated_pre_results()` helper (split out to keep
   the main function under the 50-line function limit) asserts every
   new pid's anchor_date is >= the latest anchor_date among unaffected
   pids, and that pre_batch is a true superset of the unaffected
   population -- either check failing raises `IncrementalGuardrail
   Error`, never silently trusts a broken assumption.
2. **`application/incremental_post_batch.py` (NEW)** -- thin
   orchestration seam: calls #1, catches `IncrementalGuardrailError`,
   logs a WARNING, falls back to a full `run_walk_forward()` re-score.
   Kept out of `ingest_mined_pipeline.py` specifically because that
   file had zero line-count headroom (Process Boundary Standard: one
   seam owns the incremental-vs-fallback decision).
3. **`application/ingest_mined_pipeline.py` (EDIT v1.4)** -- minimal
   necessary touch: `IngestMinedResult` gains `new_pattern_ids: set
   [int]`; `_ingest_symbol()`/`_ingest_all_symbols()` capture the ids
   `merge_one_pattern()` already returns (previously discarded); the
   5-line full-rescore "post" block swapped for a 3-line call into #2.
   Module docstring/changelog compressed (~14 lines saved) to absorb
   the net addition and land the file at exactly 300 lines, not an
   accepted overage.
4. **`tests/test_eval_incremental.py` (NEW)** -- 3 checks: incremental
   batch byte-identical to a full re-score on a synthetic fixture
   (10 existing + 3 new patterns); guardrail fires on a synthetic
   backdated insert; application-layer fallback returns a correct
   full re-score without letting the exception escape.

**Does NOT touch** `_corpus_pids()`, the AND-gate thresholds,
BUY/WATCH/PASS classification logic, or `domain/eval_scoring.py`/
`infrastructure/eval_io.py` at all (both files' E4.003 acceptance
criteria remain untouched and unaffected) -- purely changes which
patterns "post" scores, not how any individual pattern is scored.

## REAL-WORLD FINDING (2026-07-17) -- premise does not hold for BulkAddPattern

First real production run against a live 8-file BulkAddPattern batch
(ALSN/CGBD/CNSWF/CRH/LECO/LPX/STZ/SW, 799 mined candidates, 794
inserted after audit). The incremental guardrail fired immediately:

```
Incremental post-batch guardrail fired -- falling back to full
re-score: new pid anchor_date 2021-08-18 precedes unaffected pid
anchor_date 2026-06-11
```

**Root cause of the miss: the WO's own WHY section's premise was
wrong.** `mine-patterns` scans a symbol's FULL history (2513 bars,
~10 years) and finds candidates at their real historical chart dates
-- not "today." This run's earliest inserted pattern anchors at
2021-08-18, nowhere near the run date. The guardrail did exactly its
job (caught the violated assumption, fell back safely, zero wrong
data) -- but that means **every real BulkAddPattern batch will hit
this same fallback, every time**, because mined patterns are
historically-dated by construction, not same-day-dated. Manual
Pipeline A (`AddPattern.bat`) likely has the same property -- a
pattern Tony identifies by eye is dated to when the chart setup
actually occurred, not to the day he happens to enter it. Neither of
this project's two real ingestion paths appears to produce genuinely
same-day-anchored inserts; the WO was designed against a premise
("today's approved picks have today's anchor_date") that doesn't
match how either pipeline actually works.

**Practical result:** E4.004 currently provides ZERO real-world
speedup for BulkAddPattern. The code is correct and safe (the
guardrail is exactly why no wrong data resulted -- it fell back to
the full, trustworthy re-score rather than silently reusing a stale
result), but the acceptance criterion it was built to satisfy is not
met by the actual pipeline. This is a scoping failure in the original
WHY, not a bug in the DESIGN AS BUILT.

**RESOLVED 2026-07-17 (same session): redesigned per option (c).**
v1.1 replaces the same-day-only guardrail with a min-new-date
partition: any existing pid dated at or before the earliest new
pid's anchor_date is provably safe to reuse from the cached pre-batch
(no new pid is earlier, so its corpus is unchanged) -- exact for ANY
anchor_date mix, not just same-day. `IncrementalGuardrailError`
narrowed to a true internal-invariant check (pre_batch missing an
expected pid), no longer fires on real data. `domain/eval_
incremental.py` v1.1 (155 lines, includes the M-101 ordering fix
below), `application/incremental_post_batch.py` v1.1 (docstring-only,
79 lines), `tests/test_eval_
incremental.py` v1.1 (239 lines -- swapped the obsolete backdated-
insert guardrail test for a mixed-dates correctness test + a genuine
internal-invariant test).

**Second real bug found and fixed during this build's PEH (M-101):**
the mixed-dates test failed on RESULT ORDER, not scores -- sorting
`reused_results + rescored_results` doesn't reproduce `run_walk_
forward()`'s tie-break order on same-date pids (stable-sort ties
depend on insertion order, and a concatenation of two separately-
built lists doesn't preserve the reference's natural order). Fixed by
building a `results_by_pid` lookup and ordering via the exact same
`sorted(all_metadata.keys(), key=anchor_date)` computation `run_
walk_forward()` uses, instead of sorting the assembled list. No new
test needed -- the existing mixed-dates test's byte-identity
assertion already caught it. Full PEH re-run after the fix: both
suites clean, `test_eval_scoring.py` 5/5 + `test_eval_incremental.py`
4/4.

**Still open, not yet real-world tested:** v1.1 has NOT had a real
BulkAddPattern run yet (today's real batch above ran under v1.0's
same-day-only logic, before this redesign). Per the earlier honest
caveat: today's specific batch (`min_new_date` = 2021-08-18, near
`MINE_MIN_ANCHOR_DATE`) would still have rescored almost everything
even under v1.1 -- the win applies to batches with a more recent
`min_new_date`, not guaranteed on every mine-patterns run. Real
speedup claim remains unverified until a batch with a recent
`min_new_date` runs for real. M-100 (premise) and M-101 (ordering)
added to lessons.md.

## v1.2 BUILD -- "worth it" REUSE-FRACTION THRESHOLD (2026-07-18)

Same session as the independent review above, following Tony's proposal:
if the safe-reuse fraction is below a cutoff, skip the incremental path
entirely and call `run_walk_forward(parallel=True)` directly -- reuses
E4.003's already-proven parallel path instead of paying the incremental
machinery's own overhead on a batch where most existing pids would get
rescored anyway (both real batches to date had 0% reuse).

**Design:** `domain/eval_incremental.py` gained `compute_reuse_fraction()`
-- a cheap (no `score_one()` calls) pre-check that reuses
`_partition_unaffected()` rather than re-deriving the partition logic
(M-082). `application/incremental_post_batch.py`'s `run_incremental_
post_batch()` calls it first; below `config.INCREMENTAL_MIN_REUSE_
FRACTION` (0.5, new constant, `config.py` v1.19), skips straight to a
full `run_walk_forward()` and logs at INFO (a planned choice, distinct
from the guardrail's WARNING-level defensive fallback). Cutoff is a
named config constant, not a hardcoded literal, per Tony's explicit call.

**Tests added (`tests/test_eval_incremental.py` v1.2, 2 new of 6 total):**
`compute_reuse_fraction()` reports the correct fraction against the
existing mixed-dates fixture (5/10 = 0.5); a 0.0 reuse fraction skips
the incremental path entirely, proven (not assumed) by poisoning the
module-level `assemble_incremental_post_batch` reference so any call
fails loudly.

**PEH result (2026-07-18, independent-review session, same session as
the build -- this feature has NOT yet had a separate independent
review of its own):** `test_eval_scoring.py` 5/5 PASSED (unaffected).
`test_eval_incremental.py` 6/6 PASSED (4 pre-existing + 2 new). Both
exit 0.

**Does NOT resolve the still-open 4th Acceptance Criterion above** --
this changes *which* code path a low-reuse batch takes, not the
underlying question of whether either path is meaningfully faster on
a real live batch. Both remain unverified against production.

approaches are O(N^2) or condition-dependent; the top-K cache is not).

**3 of the first 3 Acceptance Criteria remain validly PASSED** (byte-identity
