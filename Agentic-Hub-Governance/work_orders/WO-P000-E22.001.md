## WHY

Two independent failure modes converged on the same root cause: **attribution
gets inferred from context (which chart is on screen, which spreadsheet has a
plausible-looking row) instead of captured at the moment a signal is actually
decided.**

1. **P_115 dilution (documented, not hypothetical):** P_115's own EC log
   records two incidents -- CDNA (2026-08-20) and INCY/MA/V (2026-08-21) --
   where a P_118 signal was misattributed to P_115, because P_118 candidates
   are required to run the P_115 recheck engine/chart, and attribution was
   being read off the chart instead of the actual batch header. P_115's
   performance numbers include an unknown quantity of trades that were never
   really P_115 signals.
2. **P_210 near-miss (2026-09-05, this session):** a real live credit-spread
   loss was ingested with a data-corruption bug that initially recorded it as
   a +$115 gain. Separately, once the data was corrected, the *system
   attribution* still defaulted to `TOS_Import` -- the account has no path
   today for a new signal source (P_210, SNT, or anything not covered by the
   Tracker Dashboard's P_115/P_118-only scope) to be correctly attributed on
   the live account at all.
3. **Registry sprawl:** there is no single file reconciling "real Hub
   Project" vs. "trading signal source" vs. "deprecated shorthand." The Hub
   Project registry (`P_000_SYSTEM_DOCUMENTATION.md` Section 1.4) and P_020's
   `systems` table are different lists for different purposes, and at least
   one live collision exists: the deprecated ThinkLog shorthand `OIL` maps to
   `P_116` (Options Income Launchpad), while the Hub Project registry lists
   `P_110` (TradetheBounce OIL) as an unrelated real project. Same shorthand,
   two different targets.

Left uncorrected, Tony's stated risk is not hypothetical: a losing signal
source can hide inside a profitable-looking one indefinitely, because the
system that would show the losses isn't the system the loss actually landed
in.

## THE RULE

1. **Terminology, fixed by this WO:** a **Signal Source ID** is any value
   valid in P_020's `systems` table (e.g. `P_115`, `P_116`, `SNT`, `P_210`).
   A **Hub Project** is a folder/codebase listed in
   `P_000_SYSTEM_DOCUMENTATION.md` Section 1.4. Every Hub Project that trades
   corresponds to one or more Signal Source IDs, but not every Signal Source
   ID is a Hub Project (`SNT`, `Day`, `INV` never were; `P_116/117/118` are
   buckets inside the P_115 project, not projects themselves). Do not use
   "Project ID" and "Signal Source ID" interchangeably in code, docs, or
   conversation going forward -- this ambiguity is part of how the P_115
   dilution went unnoticed.
2. **Every trade record carries a Signal Source ID and a confidence tier.**
   No trade may be written, displayed, or included in performance analysis
   without both.
3. **Confidence tiers (replaces the old binary attributed/default):**
   - `CONFIRMED` -- attribution came from a structured capture event
     recorded at or near signal time: a P_400 vault write, a P_820 dictated
     tag, or an explicit ThinkLog `[SOURCE][SIG]` tag / batch header written
     at the time the signal was acted on.
   - `INFERRED` -- attribution came from a retroactive match against
     existing records with no direct capture event: Tracker Dashboard
     symbol+date match, or a ThinkLog entry backfilled after the fact.
   - `UNRESOLVED` -- no evidence found. Stored with Signal Source ID =
     `TOS_Import`, excluded from all per-source performance rollups, still
     counted in whole-account totals and balance. Never silently accepted
     as a final answer -- surfaced, not buried.
4. **Attribution may never be inferred from which tool, chart, or engine
   happens to be visible or in use at the time.** This is what caused the
   P_115/P_118 confusion and it is now forbidden by construction, not just
   by convention -- see each project's child WO for its specific enforcement
   mechanism.
5. **Data source and attribution source are tracked separately and never
   conflated.** Per account:
   | Account | Trade data source | Attribution source(s) |
   |---|---|---|
   | Paper | TOS Account Statement CSV | ThinkLog (CONFIRMED if tagged at signal time, INFERRED if backfilled), Tracker Dashboard (INFERRED) |
   | Live (AJZ6348) | Schwab API | P_400 vault (CONFIRMED, once live), P_820 (CONFIRMED -- already live, see 2026-09-06 correction below), Tracker Dashboard (INFERRED, P_115/P_118 only), default (UNRESOLVED) |
   | IRA9885 | Schwab API | ThinkLog override then P_820 (CONFIRMED) -- unchanged, already correct per existing `system_attribution.py` special-case |

## SCOPE

- **Phase 1 -- effective immediately upon this WO's approval, both accounts:**
  every trade ingested from the approval date forward must carry a Signal
  Source ID and confidence tier at write time. No new `UNRESOLVED` trade may
  be added without the exclusion-from-rollup behavior in place first.
- **Phase 2 -- retroactive backfill, 2026-06-01 through the approval date,
  both accounts, same cutoff for paper and live** (paper: Tony's change-control
  reset point; live: aligned to the same date for reporting consistency, not
  because live's data had the same problem -- live's records were always
  structurally sound, only attribution is in question). Each affected project
  re-audits its own historical records against the tier system in its own
  child WO. Genuinely unrecoverable trades are marked `UNRESOLVED`, not
  guessed -- a guess with no evidence is exactly the failure mode this WO
  exists to stop.
- **Out of scope for this WO directly:** any code implementation. This WO
  defines the rule; delegated child WOs (below) implement it per project.
