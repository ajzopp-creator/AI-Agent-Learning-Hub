## WHY

Third instance found live 2026-07-24, same session as E3.010. Recording
MRCY's SUBMITTED paper trade produced:

```
WARNING obsidian_writers.application.write_handler: No VERDICT_MAP entry
for 'APPROVED_WITH_SEVERE_WARNING' (schema=P400_PAPER) -- defaulting to PASS
```

`obsidian_writers\config.py`'s `VERDICT_MAP` (Hub root, editable-install
package) maps P_400 council verdicts to a normalized cross-vault field:

```python
"APPROVED":              "BUY",
"APPROVED_WITH_CAUTION": "WATCH",
"BLOCKED":               "PASS",
"REVIEWED_NO_TRADE":     "PASS",
```

No entry for `APPROVED_WITH_SEVERE_WARNING` (added to P_400's `council.py`
2026-07-20) -- `write_handler.py`'s no-mapping fallback silently defaulted
it to `"PASS"`, which is semantically wrong (`PASS` means no trade; this
was a real trade). The actual P400/P400_PAPER record itself kept the true
verdict string in its own fields -- this gap only affects the normalized
`write_route` field used for cross-vault dashboards/filtering, not the
audit-trail record itself. Not data loss, but a wrong classification on
every SEVERE_WARNING trade until fixed.

Root cause identical to E3.010: a new Council verdict tier was added on
the P_400 side without a corresponding update everywhere else in the
Hub that gates or maps on verdict strings. Three spots hit this same class
of bug in one session (spec cache gate, record_commands.py allow-list,
now this).

## Fix (done same session, pending Ack)

`obsidian_writers\config.py` (Hub root): added
`"APPROVED_WITH_SEVERE_WARNING": "BUY"` to `VERDICT_MAP`, right after the
`APPROVED_WITH_CAUTION` entry. Tony's call (asked directly, not assumed):
`BUY`, not `WATCH` -- treat it like plain `APPROVED` since RISK-role
`SEVERE_WARNING` can never actually block a trade (council.py verdict
assembly rule), so it IS a real trade the same as plain `APPROVED`, just
carrying a risk annotation Tony already saw and acted on before recording.

File's own CHANGELOG docstring updated (v2.5 entry) per this package's
existing convention.
