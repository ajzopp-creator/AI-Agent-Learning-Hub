## Background

Child WO of WO-P000-E22.001 (Attribution Integrity Standard), approved
2026-09-06. That WO identified a live naming collision: the deprecated
ThinkLog shorthand `OIL` maps to `P_116` (Options Income Launchpad), while
the Hub Project registry (`P_000_SYSTEM_DOCUMENTATION.md` Section 1.4)
lists `P_110` (TradetheBounce OIL) as a separate, unrelated project. Same
shorthand, two different targets -- a live source of misattribution risk
this WO exists to close.

## Scope

1. **Inventory.** Search the Hub -- docs, skill files, code comments,
   ThinkLog entries, chat/session references still on disk -- for every
   place `OIL` is used to mean `P_116`. Produce the full list before
   deciding anything; no fix without knowing the blast radius.
2. **Resolution choice (Tony decides, not defaulted).** Either retire the
   `OIL` shorthand for P_116 everywhere it appears (replace with explicit
   `P_116`), or rename `P_110` to remove the collision. Present the
   inventory and the tradeoff -- retiring a shorthand already flagged as
   deprecated is likely lower-impact than renaming an established project
   name referenced across its own docs/scripts/skill file -- and get
   Tony's explicit call before touching any file.
3. **Canonical cross-reference.** Produce one table mapping every Hub
   Project (Section 1.4) to the Signal Source ID(s) it corresponds to, plus
   every standalone Signal Source ID that is not a Hub Project (`SNT`,
   `Day`, `INV`, etc.). Default placement: a new column on
   `P_000_SYSTEM_DOCUMENTATION.md` Section 1.4, per the parent WO's own
   suggestion -- only spin out a separate file if the column genuinely
   doesn't fit.

## Out of Scope

Any code change. This WO is docs/registry only -- no `system_resolver.py`,
no schema, no skill-file wiring beyond the pointer required by the parent

## Subscription <-> In-House Pairing Pattern (Tony, 2026-09-06)

Correction to this WO's original framing: P_116/P_110 is not a naming
collision at all. It's a deliberate Hub pattern -- each external
subscription signal source may have a paired in-house Hub project that
independently implements the same strategy, tracked as a **separate**
Signal Source ID on purpose, specifically so performance can be compared
and the in-house build's fidelity to the subscription's edge can be
measured. Confirmed pairs/candidates:

| Subscription ID | In-house pair | Status |
|---|---|---|
| `P_116` (Options Income Launchpad) | `P_110` (TradeTheBounce OIL) | both exist, now both in `systems` table |
| `SNT` (Sunday Night Trader) | `P_105` | Project ID reserved by Tony, no codebase yet -- registered in `systems` table only, not Section 1.4 (no codebase = nothing to register there yet, per Tony's own condition) |
| `P_210` (OneClickTrading 2PM Income Trade) | none yet | confirmed by Tony as "definitely a subscription service much like P_116 and SNT" -- flagged as a future candidate for the same pattern |

Also corrected this session (Tony, 2026-09-06): `P_910`/`P_920` are not
generic standalone systems -- they're P_115 buckets (Relative Strength
scan and EOD scan respectively), same category as P_116/117/118. `Day`/
`DAY` ties to real Hub Project `P_200` (Day Trading Strategy) rather than
being a true standalone ID. `INV` remains standalone by design -- generic
IRA daily investment/swing tag, no specific system, distinct from `Day`.

**Gap found and fixed:** `P_110` had no `system_id` anywhere in P_020 --
not in `db_seeder.py`'s seed list, not in either `VALID_SYSTEMS` set. If
the whole point of the pairing is measuring in-house-vs-subscription
performance separately, P_110 needed its own code for that separation to
function at all. Fixed this session (see Actions Taken).
