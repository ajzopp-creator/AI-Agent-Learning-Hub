## WHY

Found 2026-07-25 while running the full suite after WO-P020-E1.007:
`test_p020_known_bugs.py::test_wo_e1001_no_unrecorded_closes` fails with
`ValueError: too many values to unpack (expected 2)`.

WO-P020-E1.001 changed `schwab_mapper.map_pull_file()` from returning
2 values to 3 (`account_label, trade_dicts, orphans`) so orphaned exits
could be resolved against the DB instead of silently dropped. The
production caller `application/import_command.py:158` was updated. Two
callers were not.

The consequence is worse than a red test: `test_wo_e1001_no_unrecorded_closes`
is the regression guard for the E1.001 skip-bug itself. It has been
raising on entry rather than asserting, so the bug it exists to catch
has been unguarded since E1.001 landed. A guard that cannot run is not
a guard.

This is the exact failure mode the Hub-wide Regression Test Governance
rule was written to prevent -- a fix that did not update its own test.
Recording it here so the pattern is on file, not just the line fix.

## FIX

Arity-only correction at both stale call sites. No behavior change, no
assertion change.

| File | Line | Before | After |
|---|---|---|---|
| `tests\test_p020_known_bugs.py` | 178 | `_, trade_dicts = sm.map_pull_file(pull)` | `_, trade_dicts, _ = sm.map_pull_file(pull)` |
| `tests\verify_wo_e1001_scope.py` | 86 | `_, trade_dicts = map_pull_file(LATEST_PULL)` | `_, trade_dicts, _ = map_pull_file(LATEST_PULL)` |

`verify_wo_e1001_scope.py` is disposable PEH scratch rather than a
permanent guard, but it fails identically on any re-run, so it is
corrected in the same pass.

## OPEN DECISION (Tony)

The guard now discards `orphans` into `_`. E1.001's actual fix was
two-part: (a) the qty-aware allocator stopped skipping exits, and
(b) orphaned exits started being returned and resolved against the DB
rather than logged-then-dropped. The test currently guards only (a).

Options:
1. Leave as-is -- arity fix only, guard covers (a). Lowest risk.
2. Add one assertion that every returned orphan either resolves to an
   open/partial DB trade or is explicitly reported -- guards (b) too.

**RESOLVED 2026-07-25: Tony chose Option 2.**

"Explicitly reported" defined from the resolver's actual code. For each
orphan, `_resolve_orphans_against_db()` calls
`get_open_trade_for_symbol(conn, account_id, symbol)`, which is SQL-bound
to `status IN ('open','partial')`, then dispositions exactly two ways:

  - row found  -> `attach_orphan_exit()`; counted as resolved when
    outcome == "updated" and new_exits > 0
  - row is None -> `logger.warning("ORPHAN EXIT unresolved: ...")`,
    continue

Nothing else can happen to an orphan. New guard
`test_wo_e1001_orphans_returned_and_dispositionable` asserts three
invariants against that contract:

1. `map_pull_file()` returns a 3-tuple whose third element is a list --
   the exact contract whose drift killed the sibling guard.
2. Every orphan carries `underlying_symbol`, `open_date`, `qty`. A blank
   symbol matches nothing in the DB and degrades to a content-free
   warning -- the original silent-drop bug returning by the back door.
3. Every orphan is dispositionable -- `get_open_trade_for_symbol()`
   returns None (genuine unresolved: warned, not dropped) or a row whose
   status is open/partial. A closed row would attach an exit to an
   already-closed position.

### SEPARATE FINDING -- guards are weaker under pytest

`check(name, kind, passed, detail)` only records a result; it does not
raise. Under pytest a `check(..., False, ...)` still reports PASS --
only an exception fails the test. The E1.001 guard was caught today
solely because it raised ValueError rather than because it asserted.

The new guard uses real `assert` statements alongside `check()` so it
fails under both runners. Existing tests in this file were not converted
-- that is a larger pass and belongs in its own work order.
