'domain.eval_incremental'`. Surfaced 2026-08-07 while adding pytest config

**Ownership correction -- verified before filing, not taken on the
handoff's word.** The handoff that authorized filing this WO

(P_300/P_805) did audit `eval_incremental.py`, but for an unrelated
symptom (`threshold_overrides` parameter propagation, item 3.1) -- closed
as a FALSE POSITIVE, unconnected to this break. Finding 7's own table in
E13.001 never mentions `test_eval_incremental.py` or P_300 at all; it
covers exactly two P_400 files.

The real cause, confirmed via P_300's own `tasks\todo.md` (lines 67-83,
an existing entry predating this WO) and `WO-P300-E4.006` directly:
**WO-P300-E4.006 removed `assemble_incremental_post_batch` and
`IncrementalGuardrailError` outright** (not renamed) as part of a
deliberate v1.x -> v2.0 redesign of the incremental post-batch path -- the

no longer exists; `run_cached_post_batch` / `run_incremental_post_batch`
take the cached path unconditionally now. `application\incremental_post_batch.py`
itself is fully current and correctly wired (confirmed in the same
todo.md entry) -- this is an orphaned test, not a production gap. This is
P_300's own architectural decision surfacing its own test debt, not a
Hub-wide caller-propagation miss, and belongs to P_300, not P_000.

This was already investigated once and explicitly parked (todo.md,
undated entry preceding the 2026-08-07 audit): "Tony's call: park for
