## WHY

Only the OAuth login/token-*acquisition* action centralizes under P_020.
Everything downstream of having a valid token -- P_400's
`fetch_snapshot.py`, `fetch_chain.py`, `schwab_positions.py`,
`schwab_market_data.py`, and P_020's own `schwab_balance_pull.py`/
`P_020_Balance_Snapshot.py` -- stays exactly as built in E4.001/E4.002,
untouched. Each project keeps reading and using its own local token file
directly for every actual data call, same as today.

The only thing that changes: when a project's token needs a fresh grant
(first-time auth, or a dead/invalid refresh token), that login flow runs
through P_020 instead of each project maintaining and running its own
separate login code. P_020 writes the resulting token into that project's
own designated file. After that hand-off, the project goes right back to
operating independently against its own token, unchanged, until it needs
another fresh grant.

This also fixes a smaller, real duplication: P_020 currently still runs its
own original login code (`P_020_Schwab_Auth.py`), separate from the
generalized `shared_resources` module E4.001 built for P_400. Two parallel
implementations of the same login mechanics exist in the Hub right now.
This WO collapses that to one, operated from P_020.

## SCOPE

1. P_020 becomes the operational home for the already-built generalized
   login module (`shared_resources\python_utils\schwab_auth.py`,
   `schwab_client.py`). No new module -- it already takes
   `config_path`/`token_path` as parameters per project.
2. P_020 gets a small CLI command -- e.g. `auth --project P_400` (and
   `--project P_020` for itself) -- that calls `schwab_auth.run_auth()`
   with the target project's own config/token paths and writes a fresh,
   *independent* token for that specific project. Each project's token
   stays its own separate file, its own separate grant -- no copying token
   content between files, no shared file. That distinction matters:
   schwab-py's own docs warn that sharing one token file causes a refresh
   race ("one of them will beat the other to refreshing, locking the
   slower one out") -- this WO doesn't do that. It centralizes who *runs*
   the login flow, not the resulting token itself.
   **SUPERSEDED 2026-08-09 -- see SCOPE AMENDMENT below.** The
   separate-grant requirement in this item is the thing that was wrong.
   Separate token FILES were never the problem; separate GRANTS were.
3. P_400's `cli.py schwab-auth` subcommand removed. Getting a fresh P_400
   token becomes a P_020-run action from here on.
4. P_020 migrates its own login flow onto the shared module too
   (`P_020_Schwab_Auth.py` retired in favor of calling
   `schwab_auth.run_auth()` with P_020's own paths) -- so there's exactly
   one login-flow implementation in the Hub, not two.
5. Everything else is untouched: P_400's `fetch_snapshot.py`,
   `fetch_chain.py`, `schwab_positions.py`, `schwab_market_data.py`, and
   P_020's `schwab_balance_pull.py`/`P_020_Balance_Snapshot.py` keep
   reading their own local token file directly, exactly as today. No new
   runtime dependency between the two projects.

## OUT OF SCOPE

- Any live/subprocess data relay between P_400 and P_020 at fetch time --
  that was the earlier, incorrect version of this WO. Quotes, bars, chains,
  positions are fetched locally by whichever project needs them, same as
  today, using that project's own already-issued token.
- Sharing one token file or one token's content across projects -- still
  exactly the race schwab-py's docs warn against. Each project keeps its
  own independently-granted token; only who *runs the login* moves.

## FOUND LIVE -- 2026-08-09 -- THEORY CONFIRMED

Controlled test run this session, exactly as the 2026-08-08 entry above
specified:

1. **Baseline (10:45:10 AM):** Tony ran `P_020_Schwab_Auth.bat` locally
   (fresh browser login). Token pre-flight check immediately after
   confirmed clean: `[OK] Connected -- 2 account(s) found`. Token file
   timestamp 10:45:10 AM.
2. **P_400 login (~10:49-10:50 AM):** Tony ran `cli.py auth --project
   P_400` from `python\database\`. Callback captured automatically,
   `Authentication successful!`, P_400's own token written and API-tested
   clean (2 accounts).
3. **First P_020 recheck (~11:00 AM, ~15 min after baseline):** pre-flight
   passed clean. **This result was misleading, not a real pass** -- flagged
   live in-session: P_020's access token (30-min lifetime per
   `expires_in: 1800` in the token file) was still within its own window,
   so `client_from_token_file` never needed to hit Schwab's refresh
   endpoint at all. This check exercised the still-valid access token, not
   the refresh token -- it could not have detected revocation even if it
   had already happened.
4. **Real test (~12:00 PM, after P_020's 30-min access-token window had
   fully elapsed, forcing an actual refresh attempt):**
   ```
   [FAIL] Connection failed: unsupported_token_type: 400 Bad Request:
   "Refresh token is invalid, expired or revoked" / invalid_grant
   ```
   Token file timestamp unchanged at 10:45:10 AM -- no successful refresh
   ever landed.

**Conclusion: theory confirmed.** A P_400 login revoked P_020's
independently-issued, still-fresh (about 90 minutes old) refresh token.
Both projects use the same Schwab app registration ("AJZ-Strategies-P020"
on developer.schwab.com) with separate token *files* per Scope item 2 --
the separate-file design is working exactly as built, and it is not
sufficient, because Schwab is revoking at the app-registration level, not
the file level.

**Implication for this WO's Scope:** Scope item 2's "no shared file, no
refresh race" goal is achieved and correct on its own terms -- that was
never the actual failure mode. The real failure mode is one login event
(for either project) silently killing the *other* project's independently
valid token, which no per-file design can prevent while both projects
share one app registration. This WO cannot reach COMPLETE on its original
acceptance criteria alone; the newly added acceptance item above requires
a decision from Tony on direction (e.g. a second, separate Schwab app
registration for P_400; an operational rule to reauth whichever project
will be used next, immediately before use; or documenting this as an
accepted limitation with the Occurrence Log as the ongoing cost record).

**Fix applied same session:** none -- this is a finding, not a fix. Per

## SCOPE AMENDMENT -- 2026-08-09 (Tony's decision)

Scope item 2 required each project to hold its own *independently granted*
token, explicitly forbidding "copying token content between files". That
requirement is reversed as of this date. The new design is:

**One browser login produces ONE grant, which is propagated to every
registered project's token file.**

**Why the original constraint was wrong.** It was derived from schwab-py's
documentation warning that sharing a token file causes a refresh race --
"one of them will beat the other to refreshing, locking the slower one out".
That warning describes two processes refreshing the *same file
concurrently*. It was read as prohibiting a *shared grant*, which is a
different thing. P_020 (weekly, Saturday morning) and P_400 (during trading
sessions) do not run concurrently, so the race the warning describes is not
a live risk here. Meanwhile the risk that IS live -- one login revoking the
other project's still-valid token -- was created by the separate-grant
design, not prevented by it.

**Provenance note.** One login serving all projects was Tony's original
request, and is what this WO's own title says ("P_020 as Sole OAuth Login
Operator"). It was translated into something narrower twice: first into the
fetch-time subprocess relay design (corrected by Tony 2026-07-26, preserved
at WO-P020-E1.010_backup_MISSCOPED_2026-07-26.md), then into the
separate-grant design amended here. Recorded so the pattern is visible, not
to relitigate either session.

**What is NOT amended:** each project still reads its own local token file
for every data call. No runtime dependency between projects. No fetch-time
relay. Out of Scope is unchanged except that its second bullet -- forbidding
shared token content -- is superseded by this amendment.

## IMPLEMENTATION -- 2026-08-09

`python cli.py auth --project ALL` (run from `python\database\`, p140).

One browser login writes P_020's token file, which is then byte-copied to
every other path in `config.AUTH_TOKEN_PATHS` and verified. Registering a
future project is one dict entry -- no code change (Tony: "if any new
project we do it in same process until it gets annoying").

| File | Change |
|---|---|
| `application/schwab_auth_commands.py` | 40 -> 128 lines. Added `cmd_auth_all()` and `_verify_token_file()`. Existing `cmd_auth()` preserved verbatim. |
| `cli.py` | 42 -> 55 lines. `ALL` added to `--project` choices, dispatch added, docstring documents why ALL is the standard path. |

Single-project mode (`--project P_020` / `P_400`) is retained for targeted
reauth, with a docstring warning that using it re-grants and therefore kills
the other projects' tokens -- follow it with ALL, or just use ALL.

**Verification behavior:** each propagated copy is checked for existence,
byte-identity against the source, and JSON parseability before the command
reports success. Partial propagation raises rather than warns -- a silently
missed project is the exact failure mode this command exists to remove.

**Acceptance test:** `Agentic-Hub-Governance\verify\
run_this_P_020_20260809_133000.py`, PASS, 14/14 checks (.done marker
alongside). Covers: both files compiling under `-W error::SyntaxWarning`;
CLI exposing ALL/P_020/P_400 and rejecting unknown keys; propagation across
a *three*-project registry proving n>2 scales; and negative tests proving
the verification guard actually raises on a corrupted or missing copy rather
than passing silently. No browser login and no real token file was touched --
`run_auth` was monkeypatched and all I/O was against temp files.

**Method note:** written with `filesystem:write_file` direct-write, validated
with p140 on Windows. First use of the path proposed in WO-P000-E15.001 --
no sandbox build, no base64, no chunking.

## OPEN -- THE SEVEN-DAY ASSUMPTION -- FALSIFIED 2026-08-18

Tony's operating bet, as originally framed: one login weekly, before the
P_020 weekly update, holding all projects for the documented 7-day
refresh-token window. This depended on Schwab keeping the refresh token
STABLE across its window and rotating only access tokens.

**Original check (2026-08-09):** compare the `refresh_token` string in
`P_020_schwab_token.json` and `P_400_schwab_token.json` after both
projects have refreshed at least once. Same string -> assumption holds.
Different -> shared-grant design fails.

**Result, via the 2026-08-18 occurrence:** Tony confirmed (memory,
corroborated by `P_020_Schwab_Auth.bat` already defaulting to `--project
ALL` as of the 2026-08-12 skill-file snapshot) that the 2026-08-15
(Saturday) grant was ALL mode -- one shared token propagated to both
files. P_020's own routine Saturday-to-Sunday refresh cycle (no explicit
login, no `auth` command involved at all) still left P_400's copy dead by
2026-08-18. **The assumption is falsified, not just unconfirmed:** Schwab
does not keep a shared refresh token stable across ordinary use by one
project. Whichever project's code path happens to trigger an actual
refresh call first silently invalidates the identical copy sitting in
every other project's file -- the exact same failure the 2026-08-09 fix
was built to prevent, just triggered by routine operation instead of an
explicit second login.

**Consequence:** the ALL-mode propagation design (IMPLEMENTATION --
2026-08-09) solves accidental *login* collisions cleanly and permanently --
that part remains correct and worth keeping. It does not, and structurally
cannot, solve routine *refresh* collisions, because those happen entirely
outside any `auth` command, triggered by ordinary API use whenever an
access token expires. No CLI default, no propagation logic, no operational
discipline around when Tony logs in touches this -- the exposure exists
every time either project makes a normal Schwab API call. The only design
that removes it is separate Schwab app registrations per project, which
was already named as an option here and is now the only one that actually
addresses the confirmed failure mode. See the 2026-08-18 acceptance-item
update above -- this decision blocks the WO past IN_PROGRESS.
