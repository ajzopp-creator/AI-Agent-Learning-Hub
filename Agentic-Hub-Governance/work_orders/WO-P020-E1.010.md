## WHY

Only the OAuth login/token-*acquisition* action centralizes under P_020.
Everything downstream of having a valid token -- P_400's
`fetch_snapshot.py`, `fetch_chain.py`, `schwab_positions.py`,
`schwab_market_data.py`, and P_020's own `schwab_balance_pull.py`/
`P_020_Balance_Snapshot.py` -- stays exactly as built in E4.001/E4.002,
untouched. Each project keeps reading and using its own local token file
directly for every actual data call, same as today.

The only thing that changes: when a project's token needs a fresh grant
(first-time auth, or a dead/invalid refresh token), that login flow runs
through P_020 instead of each project maintaining and running its own
separate login code. P_020 writes the resulting token into that project's
own designated file. After that hand-off, the project goes right back to
operating independently against its own token, unchanged, until it needs
another fresh grant.

This also fixes a smaller, real duplication: P_020 currently still runs its
own original login code (`P_020_Schwab_Auth.py`), separate from the
generalized `shared_resources` module E4.001 built for P_400. Two parallel
implementations of the same login mechanics exist in the Hub right now.
This WO collapses that to one, operated from P_020.

## SCOPE

1. P_020 becomes the operational home for the already-built generalized
   login module (`shared_resources\python_utils\schwab_auth.py`,
   `schwab_client.py`). No new module -- it already takes
   `config_path`/`token_path` as parameters per project.
2. P_020 gets a small CLI command -- e.g. `auth --project P_400` (and
   `--project P_020` for itself) -- that calls `schwab_auth.run_auth()`
   with the target project's own config/token paths and writes a fresh,
   *independent* token for that specific project. Each project's token
   stays its own separate file, its own separate grant -- no copying token
   content between files, no shared file. That distinction matters:
   schwab-py's own docs warn that sharing one token file causes a refresh
   race ("one of them will beat the other to refreshing, locking the
   slower one out") -- this WO doesn't do that. It centralizes who *runs*
   the login flow, not the resulting token itself.
3. P_400's `cli.py schwab-auth` subcommand removed. Getting a fresh P_400
   token becomes a P_020-run action from here on.
4. P_020 migrates its own login flow onto the shared module too
   (`P_020_Schwab_Auth.py` retired in favor of calling
   `schwab_auth.run_auth()` with P_020's own paths) -- so there's exactly
   one login-flow implementation in the Hub, not two.
5. Everything else is untouched: P_400's `fetch_snapshot.py`,
   `fetch_chain.py`, `schwab_positions.py`, `schwab_market_data.py`, and
   P_020's `schwab_balance_pull.py`/`P_020_Balance_Snapshot.py` keep
   reading their own local token file directly, exactly as today. No new
   runtime dependency between the two projects.

## OUT OF SCOPE

- Any live/subprocess data relay between P_400 and P_020 at fetch time --
  that was the earlier, incorrect version of this WO. Quotes, bars, chains,
  positions are fetched locally by whichever project needs them, same as
  today, using that project's own already-issued token.
- Sharing one token file or one token's content across projects -- still
  exactly the race schwab-py's docs warn against. Each project keeps its
  own independently-granted token; only who *runs the login* moves.

## ACCEPTANCE CRITERIA

- A fresh P_400 token can be obtained by running a P_020 command, written
  correctly to P_400's own token path, functionally identical to what
  `cli.py schwab-auth` (P_400) produced before.
- P_400's existing `fetch-snapshot`/`fetch-chain`/`audit-book` commands
  work completely unchanged afterward -- zero lines touched in those files.
- P_020's own token continues to work exactly as before, now via the same
  shared login module instead of its own separate copy.
- P_400's `schwab-auth` subcommand and its direct call into
  `schwab_auth.py` removed from `cli.py`.
- Regression: P_400's `evaluate`/`spec`/`compare`/`screen-all` paths
  unaffected -- unrelated to this WO entirely.
