## Corrected understanding (verified this session, not assumed)

The parent WO's premise was wrong on the central fact: **"P_820: Not yet
built."** It has been built and live since 2026-08-16. Reading
`P_820_SYSTEM_DOCUMENTATION.md`, `p820_override.py`, `p820_capture.py`,
and `vault_schemas.py` directly confirms:

1. P_820 already IS the highest-priority source in P_020's attribution
   chain. `apply_p820_overrides()` runs after `apply_thinklog_overrides()`
   in the ingest pipeline and wins over whatever the base resolver
   (vault/tracker/default) already set -- effective priority is P_820 >
   ThinkLog > Tracker/vault > default, already live, not a future design.
2. P_820 entries are, by construction, exactly what Rule 3 of the parent
   WO defines as `CONFIRMED`: "a P_820 dictated tag." The mechanism the
   parent WO asked to be designed already satisfies the requirement
   functionally -- it's dictated at or near order time, structured, no
   inference from chart/context involved.
3. **This correction needs propagating to two other filed WOs, not just
   noted here:** WO-P000-E22.001's own child-WO table still says "P_820 |
   Not yet built"; WO-P000-E24.001's "Current state" section says "No
   P_820 source exists in the chain -- P_820 has no codebase yet." Both
   are being corrected in the same session this WO is filed.
4. **What's actually still missing** (real, narrow gaps, not a ground-up
   build): `P820Record` (`vault_schemas.py` line ~285) has `why_code: str
   = ""` -- open vocabulary, zero validation, same pattern found in every
   other project's signal_source field this Standard has touched. No
   `confidence_tier` field exists anywhere on the schema.

## Scope

1. Add `confidence_tier` field to `P820Record`, hardcoded `"CONFIRMED"`
   -- every P_820 write is a dictated capture event at or near order
   time by definition; no conditional logic needed, same shape as the
   P_400 fix in WO-P000-E26.001.
2. `why_code` validity check -- with a caveat this WO must not paper
   over: P_820 exists specifically to handle sources the Tracker/other
   scanners don't cover, so a hard-reject validator risks blocking a
   legitimate new source (e.g. a subscription Tony hasn't logged before).
   Recommended: log/flag `why_code` values not found in the Hub-wide
   Signal Source ID list (WO-P000-E23.001's registry) for review, rather
   than rejecting the write outright -- surfaced, not silently accepted,
   per Rule 3's own "surfaced, not buried" language, but also not blocked.
   Final call on reject-vs-flag belongs to whoever implements this.
3. Coordinate schema timing with WO-P820-E1.001's already-flagged,
   not-yet-opened follow-on (`quantity`/`trade_mode`/`override_reason`
   fields) -- both are P820Record edits; doing them in one pass avoids
   two separate schema-version bumps on the same file in short order.
   Not mandatory to combine, just flagged as the efficient option.
4. Propagate this correction: fix WO-P000-E22.001's child-WO table row
   and WO-P000-E24.001's "Current state" section (both done same session
   as this filing, see their own changelogs).

## Out of Scope

The quantity/trade_mode/override_reason fields themselves -- that's
WO-P820-E1.001's follow-on, owned by P_800, referenced not duplicated.
