## WHY

WO-P000-E2.003 left 4 sys.path inserts open specifically because the hub_shared editable install (WO-P000-E2.002) covers `hub_lib`, `shared_resources`, and `obsidian_writers` only -- not `integrations`. Removing any of the 4 `_HUB_ROOT` inserts targeting `integrations.lm_studio` today breaks `import integrations.lm_studio...` outright.

Separately, P_300's 2026-06-10 session (todo.md ENH-P000 note) flagged a second problem in the same file: `daily_evaluate_pipeline.py` calls `integrations.lm_studio.infrastructure.lm_studio_status.check()` directly from `application/` -- a Process Boundary Standard violation. The `python-project-architecture` SKILL's Process Boundary Standard section names this exact file as its worked example: status checks belong in `infrastructure/`, application orchestrates only. Confirmed still live this session (2026-06-22): the call is wired straight into `daily_evaluate_pipeline.py`'s import block, no P_300-owned `infrastructure/lm_studio_status.py` wrapper exists.

Both problems share one root cause: `integrations/lm_studio` was built as a P_300-adjacent module, not a Hub-level shared interface, so every consumer reaches into it directly instead of through a published contract -- the same anti-pattern M-038 already named for Obsidian writes (`vault_interface.py`) before that boundary was fixed.

## QUESTION TO RESOLVE

A) Add `integrations` to the Hub's `pyproject.toml` editable install (same fix as `obsidian_writers` in WO-P000-E2.003) -- removes the sys.path need but leaves consumers importing `integrations.lm_studio.infrastructure.lm_studio_status` directly; the Process Boundary violation in P_300 stays unresolved.

B) Port the LM Studio status-check logic into a genuine `shared_resources/python_utils/lm_studio_status.py` Hub interface (mirrors the `vault_interface.py` and `atr.py` precedent). Consumers import from `shared_resources`, never from `integrations`. Each consuming project (P_300 first) adds its own thin `infrastructure/lm_studio_status.py` wrapper that calls the Hub interface, so `application/` still only ever calls into its own `infrastructure/` -- closes both the sys.path row AND the Process Boundary violation in one move.

**Recommendation: Option B.** It's the only option that resolves the Process Boundary violation P_300 already flagged, and it follows the exact precedent already set for Obsidian writes (M-038) and ATR (M-049) -- both moved into `shared_resources/python_utils/` as pure Hub interfaces rather than leaving consumers reach into another project's internals. Option A only papers over the import-resolution half of the problem.
