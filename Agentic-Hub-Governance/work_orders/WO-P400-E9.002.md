# WO-P400-E9.002 -- p020_order_writer.py: P_020's schemas.py Split Broke the Bridge

**Status:** OWNER_DONE (fix applied + live-verified 2026-09-21)
**Owner:** P_400
**Affects:** shared_resources\python_utils\p020_order_writer.py -- Hub-wide bridge, used by any project writing orders into P_020's database
**Depends On:** none
**Acks:**

---

## WHY

Live 2026-09-21: `record AMZN --order-id 1008004303125` wrote the P_400 vault
record cleanly (SUBMITTED, vault_write=OK) but the P_020 order write failed:
`module 'schemas' has no attribute 'Order'`.

Root cause: P_020 split its monolithic `schemas.py` into `schemas_ops.py` /
`schemas_trade.py` / `schemas_tracker.py` on 2026-09-19 (`Order` moved to
`schemas_ops`, `Exit`/`Trade` to `schemas_trade`). P_020's own
`db_order_writer.py` was updated for the split (`from schemas_ops import
Order`); this external bridge's `_load_p020()` was not -- it still did `import
schemas`. Since P_020's `database\` folder no longer has a `schemas.py` at
all, the import didn't fail -- it silently fell through past P_020's dir
(inserted at sys.path[0]) to P_400's own unrelated `schemas.py` (still on
sys.path, just behind it), which loaded fine but has no `Order` attribute. No
exception on the missing file, so it surfaced as a confusing `AttributeError`
instead of a clean `ModuleNotFoundError`.

**NOT a recurrence of WO-P400-E8.001** -- E8.001 was a sys.modules
cache-collision bug (same bare name owned by two different packages, one
caller-cached). This is a different failure class: an upstream rename in
P_020 that this bridge was never updated for. The `_COLLIDING_PACKAGES`
stash/restore mechanism E8.001 built was working correctly throughout; it
just had the wrong target name for the field that changed.
## WHAT

1. `_load_p020()`: `import schemas` -> `import schemas_ops`; return tuple's
   `schemas` -> `schemas_ops`.
2. `submit_order()`: `schemas.Order(...)` -> `schemas_ops.Order(...)`.
3. `_COLLIDING_PACKAGES`: `"schemas"` removed (dead -- P_020 no longer has
   that file to collide on), `"schemas_ops"` added (the real current
   dependency).
4. Docstring/comment above `_COLLIDING_PACKAGES` and inside `_load_p020()`
   updated with a dated note explaining the split and the fix.

`Order`'s field set is unchanged by P_020's split, only its file location --
confirmed by reading `schemas_ops.py`'s `Order` class directly and diffing
its fields against every keyword `submit_order()` passes; all match.
`submit_order()`'s own public signature is unchanged, so no other caller of
this bridge needs touching.

## FIX APPLIED (2026-09-21)

Patched live via windows-mcp:PowerShell, same safety pattern as E9.001: read
full file -> backup (`p020_order_writer.py.backup_2026-09-21`) -> match-count-guard
(4 distinct edits, each guarded, all matched exactly once) -> replace ->
UTF-8-no-BOM write -> read-back verify (all new markers present, all old
schemas/schemas.Order references confirmed gone). A live py_compile syntax
check was attempted but hung and timed out -- confirmed cause: invoking
python.exe directly via the PowerShell MCP bridge, the exact hang risk
already documented in ways-of-working.md ("Never invoke Python directly via
PowerShell MCP"). Correctly aborted rather than retried; syntax confidence
instead rests on the edit being a pure identifier rename inside
match-count-guarded blocks (no structural/indentation changes) plus the live
verification below, which exercises the real interpreter via the normal CLI
path.
