# WO-P300-E4.003 -- M-079 Walk-Forward Eval Has No Runtime Cap (BUG, not a performance backlog item)

**Status:** CLOSED
**Owner:** P_300
**Affects:** domain/eval_scoring.py, application/ingest_mined_pipeline.py,
  application/catalog_merge_pipeline.py (any caller that runs the

**Depends On:** None. Directly triggered by the 2026-07-15 real
  BulkAddPattern archive + ingest-mined run against the full
  6039-pattern live catalog -- the first time this eval has run at
  this scale. Took 40+ minutes and looked hung to the operator.
**Acks:** N/A
**Follow-up filed:** WO-P300-E4.004 (incremental post-batch scoring --

## WHY

**Reclassified 2026-07-15 (Tony's correction):** this was first filed as a
performance-improvement backlog item. It is not. A process step that
sits inside a promotion/decision gate, has no cap, no timeout, and no
bound on its own runtime -- and whose cost grows with catalog size, so
it will only get slower from here -- is a reliability defect. It
blocked a real operator run for 40+ minutes with no way to know how
much longer it would take. Treat as a bug: fix required before this
gate is trusted for routine use, not an optional later enhancement.

Root-caused during the 2026-07-15 session: `staging_ingest_
mined.db` was last modified 9 seconds after the run started and never
changed again for the remaining 40+ minutes, while the python.exe
process's CPU time climbed in lockstep with wall clock the entire
time. The actual staging insert (`_ingest_all_symbols`) completes in
seconds. Everything after that -- the whole rest of the run -- is
`domain/eval_scoring.py`'s M-079 walk-forward comparison: for every
one of 6039 patterns, build a corpus of every earlier-dated pattern
(avg ~3000) and run a full similarity/DTW pass against each, then
repeat the entire thing a second time for the staging ("post")
catalog.

Two design gaps make this worse than it needs to be:

1. **No caching.** The "pre" batch scores the LIVE catalog, which is
   byte-identical to what it was at the last promote -- it cannot have
   changed since then. `run_ingest_mined()` recomputes it from scratch
   on every single call anyway. Pure waste on every run after the
   first.
2. **No parallelization.** `score_one()` (domain/eval_scoring.py) reads
   only from three pre-loaded, read-only dicts (`all_metadata`,
   `historical_windows`, `all_labels`) and mutates nothing shared
   across pattern_ids -- each pattern's score is fully independent of
   every other. `run_walk_forward()` currently runs this as a plain
   Python list comprehension, single core, single process.

Previous PEH/production runs of this eval never surfaced this because
they all ran against the much smaller pre-promote catalog (~508
patterns or less). At 6039 patterns this is the first real stress test
of the eval's actual cost curve.

## PROPOSED FIX (built 2026-07-16)

Two independent, additive optimizations -- both shipped:

**1. Pre-batch caching.** Memoize the "pre" `WalkForwardBatch` result,
keyed on the live catalog's file path + mtime_ns + override tag.
`run_ingest_mined()` checks the cache before calling `run_walk_forward()`
for the pre pass; a hit skips straight to the cached report, a miss
(catalog changed since last cache write, i.e. a promote happened)
recomputes and refreshes the cache. Zero change to scoring logic or
output.

**2. Parallel scoring.** `run_walk_forward()` gained an optional
`parallel=True` path (`ProcessPoolExecutor`, per-worker globals via
`_init_worker` so the large metadata/window/label dicts are pickled
once per worker, not once per pattern), gated behind
`config.EVAL_PARALLEL_ENABLED` so the existing serial path stays
available as a fallback/debug mode. Applies to both pre and post
batches independently -- compounds with the caching fix rather than
replacing it.

**Did NOT touch** the AND-gate thresholds, BUY/WATCH/PASS
classification logic, `signal_classifier.py`, or CE gate wiring --
purely an execution-strategy change to an already-correct computation.

## OUT OF SCOPE

- Corpus sampling or capping (would change the eval's statistical
  rigor -- a real design decision, not bundled into a performance fix;
  separate discussion if ever needed).
- Any change to Pipeline B's live signal path (`aggregator.py`,
  `similarity.py` as called from `daily_evaluate_pipeline.py`) -- this
  WO is scoped to the offline M-079 backtest loop only.
- Multiprocessing for the mine-patterns / audit-gate steps (not shown
  to be the bottleneck here).
- Incremental/skip-unaffected-patterns post-batch scoring -- real,
  larger lever (see CLOSURE NOTE), filed separately as WO-P300-E4.004
  rather than bundled into this bug fix.

## CLOSURE NOTE (2026-07-16)

Both fixes work as designed and are PEH-confirmed against the real
live catalog, not just synthetic fixtures. Parallel speedup was more
modest than expected (24 logical cores available, ~15% faster than a
serial estimate) -- most likely per-worker pickling overhead of the
full metadata/window/label dicts at pool startup, compounded by
`score_one`'s O(corpus_size) dict-rebuild per pattern, which doesn't
parallelize away. Not re-opened here: WO's actual goal (stop a promote
from looking hung, and eliminate the wasted duplicate "pre" pass) is
met either way.

Bigger lever identified during closure discussion, not built here:
walk-forward's corpus for any pattern is only patterns with a
STRICTLY EARLIER anchor_date. On a daily BulkAddPattern run, the day's
new picks (0-15 patterns) always have today's date -- later than
every existing catalog pattern -- so none of the existing ~8000+
patterns' scores can ever change by adding them. The current "post"
batch re-scores the entire staging catalog anyway. Filed as
WO-P300-E4.004 for a dedicated plan + explicit go-ahead next session --
this is a real change to what M-079 computes (skip-unaffected-patterns
logic), not just how fast, so it's out of scope for this bug-fix WO.
