## Source data: `v_trade_summary` view (P_020's own SQLite DB)

Full current definition, `python\database\update_v_trade_summary.py`:

```sql
CREATE VIEW v_trade_summary AS
SELECT
    t.trade_id, t.account_id, t.system, t.underlying_symbol, t.asset_type,
    t.direction, t.open_date, t.qty, t.entry_price, t.stop_price,
    t.risk_amount, t.total_commissions, t.status, t.tags, t.notes,
    t.reason, t.signal_strength, t.source,
    COALESCE(SUM(e.exit_pnl), 0.0)   AS realized_pnl,
    COALESCE(SUM(e.qty_exited), 0)   AS qty_closed,
    t.qty - COALESCE(SUM(e.qty_exited), 0) AS qty_remaining,
    MAX(e.exit_date)   AS last_exit_date,
    MAX(e.hold_days)   AS max_hold_days,
    -- exit_1_*, exit_2_*, exit_3_* (price/qty/date/hold_days per leg) --
    CASE WHEN t.risk_amount IS NOT NULL AND t.risk_amount != 0
         THEN ROUND(COALESCE(SUM(e.exit_pnl), 0.0) / t.risk_amount, 2)
         ELSE NULL END AS realized_R,
    CASE WHEN t.status = 'open' THEN 'OPEN'
         WHEN COALESCE(SUM(e.exit_pnl), 0.0) > 0 THEN 'WIN'
         WHEN COALESCE(SUM(e.exit_pnl), 0.0) < 0 THEN 'LOSS'
         ELSE 'SCRATCH' END AS outcome
FROM trades t LEFT JOIN exits e ON t.trade_id = e.trade_id
GROUP BY t.trade_id
```

**Only closed trades should be written** -- filter `status != 'open'`
(or `outcome != 'OPEN'`) before calling `write_to_vault`. P_800's own
docs describe P_020's vault role as "one .md per P_020 closed trade";
writing OPEN rows would misrepresent unrealized positions as final
records with no way to update them (P_020 has no note_version-driven
re-evaluation loop like P_115/P_300 do -- vault_writer's overwrite path
would need the exact same filename to update a note, and this integration
doesn't specify one yet -- see filename decision below).

## Field mapping: `v_trade_summary` -> `P020Record`

| view column | P020Record field | Notes |
|---|---|---|
| `underlying_symbol` | `symbol` | rename at call site |
| `account_id` | `account_id` | direct |
| `system` | `system` | direct -- must be one of P_020's `_VALID_SYSTEMS` |
| `reason` | `why_code` | per p020-project-context: `reason` DB column IS the WHY tag |
| `signal_strength` | `sig_code` | per p020-project-context: `signal_strength` DB column IS the SIG tag |
| `open_date` | `open_date` | direct |
| `last_exit_date` | `close_date` | only populated once a trade has at least one exit |
| `entry_price` | `entry_price` | direct |
| `realized_pnl` | `realized_pnl` | direct |
| `realized_R` | `realized_R` | direct (already rounded to 2dp in the view) |
| `qty` | `qty` | direct |
| `risk_amount` | `risk_amount` | direct |
| `max_hold_days` | `days_held` | direct |
| `outcome` | `outcome` | **vocabulary mismatch -- see Open Decision 1 below** |
| `signal_strength` (source, not the DB one) | (n/a) | no `signal_strength` collision -- P020Record has no such field name conflict, just double-check at implementation |

**No source column for:** `exit_price` (P020Record has one `exit_price`
field; the view has up to 3 numbered exit legs -- see Open Decision 2).
`asset_type`, `direction`, `total_commissions`, `stop_price`, `tags`,
`notes`, `trade_id`, `source` have no P020Record field at all -- not
carried into the vault note under this WO's scope.

## Open Decisions (P_020 owner to resolve, not assumed by this WO)

1. **`outcome` vocabulary mismatch.** `v_trade_summary.outcome` emits
   `OPEN | WIN | LOSS | SCRATCH`. `P020Record.outcome`'s existing comment
   says `TP Hit | SL Hit | Manual` (copied from the P_115 model when
   P020Record was first drafted -- never actually wired). Decide: keep
   the view's `WIN/LOSS/SCRATCH` vocabulary (recommended -- it's already
   computed correctly) and update the stale comment in `vault_schemas.py`,
   or translate to the P_115-style vocabulary at the call site. Either
   way, update `P020Record`'s comment to match reality once decided.
2. **Multi-leg exits -> single `exit_price` field.** The view supports up
   to 3 partial exits per trade; `P020Record` only has one `exit_price`.
   Decide: use `exit_1_price` only (simplest, loses partial-exit detail),
   or extend `P020Record` with the same `exit_1/2/3_*` pattern P_400 used
   for spread fields (WO-P400-E3.004) if partial-exit detail matters for
   the vault view. This is a P_800 schema change if you pick the second
   option -- file a follow-up WO against P_800, don't edit
   `vault_schemas.py` from a P_020 session (project boundary).
3. **Filename / overwrite key.** Every other integration's note is keyed
   by ticker + date and re-written via `overwrite=True` on re-run (see
   `write_signal_to_obsidian.py`). Decide the equivalent key for P_020 --
   likely `trade_id` or `(symbol, close_date)` -- so re-running the
   integration after a trade's second/third exit updates the same note
   instead of creating duplicates.

## Example call (illustrative, not prescriptive on the open decisions above)

```python
from shared_resources.python_utils.vault_interface import write_to_vault

write_to_vault(
    schema_name="P020",
    data={
        "signal_date": row["last_exit_date"] or row["open_date"],  # required
        "written_by": "P_020/vault_writer",                        # required
        "symbol": row["underlying_symbol"],
        "account_id": row["account_id"],
        "system": row["system"],
        "why_code": row["reason"],
        "sig_code": row["signal_strength"],
        "open_date": row["open_date"],
        "close_date": row["last_exit_date"],
        "entry_price": row["entry_price"],
        "realized_pnl": row["realized_pnl"],
        "realized_R": row["realized_R"],
        "qty": row["qty"],
        "risk_amount": row["risk_amount"],
        "days_held": row["max_hold_days"],
        "outcome": row["outcome"],   # pending Open Decision 1
    },
    overwrite=True,
)
```
