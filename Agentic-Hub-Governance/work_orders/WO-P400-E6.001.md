# WO-P400-E6.001 -- Obsidian Performance Data: Dead Bases Paths + Order Lifecycle Never Closes the Loop

**Status:** IN_PROGRESS -- dead-path Bases fix applied same session (see FIX APPLIED below). Reconciliation design (Scope item 2) not started -- direction recommended, not yet approved for build.
**Owner:** P_400
**Affects:** P_020 (Bases/P020_Performance.base shares the same dead-path bug; recommended fix extends P_020's SQLite-as-source-of-truth pattern to P_400 orders), P_800 (owns Bases/ and the vault rename that caused this -- WO-P800-E3.003)
**Depends On:** none

## WHY

Tony asked (2026-08-11, P_020 session) for a plan to get real performance data
out of Obsidian for both paper and live Orders, since P_400 is the
authoritative Trade Order Management layer. Investigation surfaced two
separate problems, one small and immediate, one structural.

## FOUND LIVE -- 2026-08-11

**1. Both performance Bases are silently broken.** `Bases/P400_Trades.base`
and `Bases/P020_Performance.base` both filter on
`file.folder contains "TradeManagement/..."`. That folder was renamed to
`TradeOrderManagement/...` hub-wide on 2026-07-25 (WO-P800-E3.003).
`TradeManagement` no longer exists on disk (confirmed via
`obsidian_list_files_in_dir` -- 404). Both Bases have been returning zero
rows since the rename, 17 days, unnoticed -- neither P_400's nor P_020's
skill file logged this as a bug because the rename WO's own completion
never checked Bases/ as a caller of the old path.

`P400_Trades.base` additionally sorted on a `date` field that does not
exist in the P400 note schema (`signal_date`/`run_date`/`entry_date`/
`close_date` do; `date` does not) -- a second, independent defect in the
same file.

**2. P_400's order notes never close the loop.** Sampled records across
`TradeOrderManagement/P400/`, `/paper/`, `/P115/`: `lifecycle_status`
stops at `SUBMITTED` or `DROPPED` permanently. `entry_date`, `close_date`,
`realized_pnl` are null in every sampled record, including ones from
June. Nothing in P_400 ever writes back once an order fills or closes --
there is no reconciliation step. P_020 has the equivalent closed loop
(SQLite -> vault export with real `realized_pnl`/`realized_R`/`outcome`)
but only for the live account's Schwab-sourced trades; it has no
visibility into P_400's council verdicts, why/sig tags, or paper-account
orders.

Net effect: the performance data Tony asked for does not exist yet for
P_400-originated orders, live or paper, regardless of the Bases bug --
fixing the Bases path alone would just render an accurate table of nulls.

  `TradeOrderManagement/P400`; sort field `date` -> `run_date` (the only
  existing schema field that expresses "when P_400 acted on this").
- `Bases/P020_Performance.base`: folder filter `TradeManagement/P020` ->
  `TradeOrderManagement/P020`. Column/sort fields already matched schema
  (`close_date`, `symbol`, `account_id`, `system`, `realized_pnl`,
  `realized_R`, `outcome`, `sig_code`) -- path was the only defect.
- Bug rows added to `p400-project-context` and `p020-project-context`
  skill files (Bugs table + changelog each) -- IN THE APP skill update
  still required (Customize -> Skills), not just the disk file.

Verification: `TradeManagement` confirmed absent via vault listing (404).
`TradeOrderManagement/P400`, `/paper`, `/P020` confirmed present with
files via the same tool. Field names cross-checked against 3 sampled
P400 notes (2 non-paper, 1 paper) and 1 P020 note. Not yet confirmed
inside the Obsidian app itself (Bases render client-side; no way to

## SCOPE -- item 2, NOT STARTED

Recommended direction (not yet approved for build): extend P_020's
already-locked "SQLite is single source of truth" architecture to P_400
orders instead of leaving Obsidian as P_400's only, dead-ended record.

- P_400 orders land in SQLite at submit time (new `orders` table, or a
  `pending` status row in `trades`).
- A reconciliation step -- reusing P_020's existing Schwab pull, not a
  new integration -- matches submitted orders against actual fills/exits
  and writes real `entry_date`/`close_date`/`realized_pnl` back.
- Obsidian notes become a generated view again (same pattern P_020's
  vault export already uses), not a hand-maintained or dead-ended
  primary record.
- Keeps ownership clean: SQLite stays P_020's, P_400 becomes a writer
  into it, Obsidian stays P_800's presentation layer -- no project
  editing across a boundary it doesn't own.

**DESIGN REFINEMENT -- 2026-08-11 (same session, Tony).** Matching entry
to exit doesn't have to lean on `exit_allocator.py`'s FIFO/symbol/date
heuristic as the primary path. Confirmed in the D_020_2026-08-11 TOS
account statement export (`Account Order History filtered by SPY`
section): closing/replacing orders carry an explicit back-reference to
the order they belong to -- `TRG BY #5375753645` (triggered-by) and
`RE #5376488736` (re-issued-from) in the Spread column, pointing at
another order's Order ID. Bracket/OCO order groups are therefore
explicitly linked by Schwab/TOS, not just inferred. This makes
reconciliation a lookup by linked ID for anything placed as a bracket
(entry + attached stop/target), not a guess.

**Two matching tiers, not one:**
1. **Primary -- linked order ID.** If the closing order references the
   entry order_id (directly or via a short reference chain), match on
   that. Deterministic, no heuristic involved.
2. **Fallback -- P_020's existing FIFO/symbol/date matcher.** Covers the
   case a bracket doesn't cover: a naked entry closed later by a
   standalone order with no attached stop/target, so no link exists to
   follow. Not a gap -- `exit_allocator.py` already handles exactly this
   shape of match today. Tier 2 stays as backstop, not replaced.

**Not yet confirmed:** whether Schwab's live orders API exposes this
same parent/child linkage programmatically (bracket/OCO order structures
usually do -- e.g. child order strategies -- but this hasn't been checked
against an actual API response yet, only seen in the TOS CSV export's
Account Order History section, which today's parsers don't read at all --
only the Cash Balance section is parsed). Confirming this against a live
`fetch` call is a prerequisite before Tier 1 can be built for the live
account.

**DESIGN REFINEMENT 2 -- 2026-08-11 (same session, Tony).** Paper and
live cannot share one data-acquisition path, structurally -- not a style
choice. Live has the Schwab API. Paper runs on TOS paperMoney, which has
no API at all; the only way data leaves it is a CSV export, permanently.
So Tier 1 for paper can only ever come from parsing the Account Order
History section of the TOS export (unparsed today -- only Cash Balance
is read); Tier 1 for live may come from a live API call once confirmed,
or fall back to the same CSV-section parse if the API doesn't expose it.

This isn't a new problem to solve -- P_020 already has this exact shape
solved: `paper_import.py` (CSV-based) and `schwab_trade_pull.py`
(API-based) are two separate ingestion adapters already feeding one
shared SQLite schema. Reconciliation should follow the same pattern: two
adapters (one per data source), both normalizing into a common shape
before the Tier 1/Tier 2 matching logic runs once, shared. "One
reconciliation path or two" (below) is answered at the acquisition
layer -- always two -- not at the matching layer, which stays one.

Not scoped yet: which table P_400 writes to, how council/why/sig
metadata (fields SQLite's `trades` table doesn't currently have) gets
carried through, the Tier-1 live-API confirmation, and building the
Account-Order-History-section parser neither ingestion path has today.
Needs a design session with Tony before any code.

**STEP-BY-STEP AUDIT -- 2026-08-11 (same session, Tony's request: "check
what we do with paper vs API for every step").** Read the actual code
(`ingest_pipeline.py`, `schwab_mapper.py`, `exit_allocator.py`,
`paper_import.py`, `paper_csv_reader.py`, `exit_builder.py`) rather than
assuming. Corrects the "matching logic stays shared" claim in Design
Refinement 2 above -- it does not, today:

| Step | Live | Paper |
|---|---|---|
| Data acquisition | Schwab API JSON pull (`ingest_pipeline.py`) | Manual TOS CSV export -> `P_020_TOS_Parser_v2.py` (nominally retired per PROJECT_PLAN_v3, but still the only active path for paper since paperMoney has no API) -> intermediate `_OPTIONS_IMPORT.csv`/`_STOCKS_IMPORT.csv` -> `paper_csv_reader.py`. Reader does NOT consume the raw Account Statement CSV directly. |
| Multi-fill grouping | Real `orderId`, grouped in `schwab_mapper._aggregate_by_order()` | `REF #` text parsed from the CSV `DESCRIPTION` field, inside the old TOS parser -- same concept, string-matched, not a queryable ID |
| Entry/exit classification | `schwab_mapper._parse_transaction()` from txn type | Old TOS parser, from BOT/SOLD in `DESCRIPTION` |
| **Entry-to-exit matching** | `exit_allocator.py` -- FIFO, qty-aware, built by WO-P020-E1.001 specifically to fix exits being greedily consumed by the wrong sibling entry | `exit_builder.py` does NO matching -- it only formats exit slots the old TOS parser already matched using the simpler pre-E1.001 "grab up to 2 exits" logic. **Same bug class E1.001 fixed for live is still live in paper, unfixed, independent of this WO.** Also caps 2 exits (paper) vs 3 (live, `MAX_EXIT_SLOTS`). |
| Order-ID linkage (TRG BY#/RE#) for Tier 1 | Not read today. `orderId` already flows through for same-order grouping; whether the payload also carries cross-order parent/child linkage is unconfirmed | Not read today -- only source is the Account Order History CSV section, which the active paper pipeline never touches (see Data acquisition row) |
| Dedup | `schwab_transaction_id` | `(account_id, symbol, date, entry_price, source)` tuple |

**Consequence for this WO's scope:** building Tier-1 order-linkage for
paper is not a small addition to `paper_csv_reader.py` -- it requires
either extending the old TOS parser (already marked retired once) or a
new reader built against the raw Account Statement CSV's Order History
section from scratch, bypassing the old parser entirely. Separately: the
parent-vs-nominal-retirement status of `P_020_TOS_Parser_v2.py` should
get a straight answer before more is built on top of it either way.
