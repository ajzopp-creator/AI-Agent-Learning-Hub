## WHY

E1.004 shipped `expected_trading_day()` as weekend-only (today minus 1, or last Friday
on a Monday run) -- a scoping decision Tony signed off on 2026-08-29, accepting the
false-positive rate on trading days after a market holiday rather than build/maintain
a holiday calendar. Working out the actual next occurrence during that same session
surfaced that it isn't a rare, evenly-spread event: the very next US market holiday is
Labor Day, Monday September 7, 2026 -- meaning the freshness check's first real-world
test, on Tuesday September 8, would expect grid_date = 09/07 and get the legitimately
correct 09/04, firing a false MORNING_RUN_FAILED flag + toast within days of going
live. Tony reopened the scoping decision on that basis. This WO implements the
holiday-aware version.

Same failure shape as ERROR 004: a fail-loud mechanism that cries wolf on its first
real trigger trains the operator to stop trusting it -- worth avoiding twice.

**Scope expansion (2026-08-30, live discovery):** a manual Sunday run
(2026-08-30) fired MORNING_RUN_FAILED, message: 'grid_date=2026-08-27, 2d
behind expected 2026-08-29.' Initial read of this in chat mischaracterized
it as a false positive -- it is not. 2026-08-27 is a Thursday; the most
recent real trading day before Sunday is Friday 2026-08-28. The grid_date
should have been 08-28 and is 08-27 -- Friday's close was never captured.
Export file LastWriteTime for all three symbols is Friday 2026-08-28
~2:56-2:57 PM, i.e. an intraday VantagePoint refresh before the 4 PM close,
with no later nightly (~6:30 PM) refresh landing that evening. This is a
live, real recurrence of the E1.003/E1.004 root-cause class (VantagePoint/
Windows not overwriting the export) -- separate from this WO and requires
its own follow-up (check whether VantagePoint's Friday evening export ran
at all).

What IS in scope for E1.005: expected_trading_day()'s Sunday-run math is
independently wrong. Old logic computed today-1 = Saturday 2026-08-29 (not
a valid trading day) and reported '2 days behind' when the correct
reference (Friday 2026-08-28) would report '1 day behind.' The generalized
step-back algorithm proposed below (skip weekends AND holidays, walk back
from today until clear) fixes this as a side effect -- Sunday 2026-08-30
walks back through Saturday to Friday 2026-08-28 -- but it must be
explicitly tested; the original VERIFY list below only covered the holiday
scenario, not a weekend-run scenario. Fixing this math bug would not have
prevented the flag from firing on 2026-08-30 -- it should still have fired,
just against the correct reference date and day-count.

## PROBLEM

`expected_trading_day()` in `grid_freshness_check.py` only walks back over Sat/Sun.
It has no concept of a market holiday, so any morning after one of the 10 annual
NYSE/Nasdaq closures produces a guaranteed false positive.

## PROPOSED FIX (not yet built -- needs Tony sign-off)

Add a hardcoded holiday list to `grid_freshness_check.py` and extend
`expected_trading_day()` to walk backward over both weekends AND listed holidays.

**2026 NYSE/Nasdaq full-closure dates (verified via NYSE Group's official 2026
calendar announcement, 10 dates):**

```python
MARKET_HOLIDAYS_2026 = {
    date(2026, 1, 1),   # New Year's Day
    date(2026, 1, 19),  # MLK Day
    date(2026, 2, 16),  # Washington's Birthday
    date(2026, 4, 3),   # Good Friday
    date(2026, 5, 25),  # Memorial Day
    date(2026, 6, 19),  # Juneteenth
    date(2026, 7, 3),   # Independence Day (observed -- July 4 falls on a Saturday)
    date(2026, 9, 7),   # Labor Day
    date(2026, 11, 26), # Thanksgiving
    date(2026, 12, 25), # Christmas Day
}
```

`expected_trading_day(today)`: step back one day at a time from `today`, skipping
any date that is a weekend OR in `MARKET_HOLIDAYS_2026`, return the first date that
clears both. Replaces the current Mon-Fri-only logic; same function signature, so
`P_010_daily_posture_v5.py`'s call site is untouched (no risk to its 300-line ceiling).

**Maintenance requirement (explicit, so it doesn't silently rot):** this list must be
refreshed every December for the coming year. Recommend a `SKILL.md` Must-rule in
p010-project-context: "Before every January, confirm `MARKET_HOLIDAYS_<year>` in
grid_freshness_check.py covers the new year -- source: NYSE Group's official holiday
announcement." Open question for sign-off: is a hardcoded per-year set acceptable
long-term, or do you want a small `holidays`-package dependency instead? Recommend
the hardcoded set -- no new pip dependency, ~10 lines/year to update, matches the
Hub's existing preference for minimal surface area over library dependencies.

Estimated size: ~15-20 lines added to grid_freshness_check.py (currently 65 lines) --
well under its own 300-line ceiling, no split required.
