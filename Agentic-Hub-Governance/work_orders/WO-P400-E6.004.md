## WHY

`batch-2b` is supposed to collapse N manual round-trips into one CLI call
(WO-P400-E5.003's whole point, per its own docstring: "PEH requires Tony to
run every Python command in his own terminal, so round-trip count is the
structural bottleneck"). A single symbol missing from the earnings calendar
cache defeated that entirely -- it aborted the ENTIRE batch before any symbol
was evaluated, including every other symbol that had nothing wrong with it.

## FOUND LIVE -- 2026-08-19

Two real occurrences same session, escalating in cost:

1. `fetch-snapshot DGX` (single-symbol manual path, not batch-2b): cache
   pulled 2026-08-11 had no DGX entry. Worked around individually at the time.
2. `batch-2b` against 12 PASS symbols: ALGN cache miss aborted all 12,
   including SBLK/STZ/HWM/NRG/APTV/CAR/CIFR/POWL/SARK/TSN, none of which had
   any earnings problem at all. A same-session `refresh-earnings-calendar`
   pull (1,483 symbols, up from the stale 3,223-symbol Aug 11 pull actually
   being *smaller* coverage in the names that mattered) still only covered
   1 of the 11 remaining symbols (STZ) -- confirming this isn't a one-off gap,
   it's a real, recurring coverage weakness in the Nasdaq public calendar
   source itself, which makes the all-or-nothing abort design far more costly
   than it would be against a fully reliable source.

**Root cause, traced to actual code, not just symptom:** `batch_2b_scoring.py`
already had a per-symbol skip-and-continue mechanism for exactly this case --
same pattern already used there for "packet not found" and "verdict not
approved". It was wired to the wrong exception: it imported
`EarningsDataMissing`/`require_entry` from `infrastructure.earnings_file`
(the OLD, dead manual-file module, explicitly flagged dead in
`earnings_lookup.py`'s own docstring), not from the live
`application.earnings_lookup` module `build_entries_for_symbols()` actually
raises from. Two separate, same-named `EarningsDataMissing` classes existed
in two different modules. The per-symbol catch could never fire -- the real
exception, from the live module, propagated straight past it and up into
`batch_2b.py`'s `cmd_batch_2b()`, which caught it at the top level and
aborted the whole run.

## FIX -- 2026-08-19 (Revision 1 -- blast radius)

No redesign -- the graceful per-symbol path already existed and was already
correct in shape; it only needed to be reachable.

1. **`application/earnings_lookup.py`** (95 -> 96 lines): `build_entries_for_symbols()`
   no longer raises on a per-symbol cache miss. Logs a warning and omits that
   symbol from the returned dict instead. `EarningsCacheMissing` (whole cache
   never built) is unchanged -- still batch-fatal, correctly, since it means
   the refresh was never run at all, not a coverage gap in one pull. Module
   docstring and `Raises:` section corrected to describe the new behavior
   accurately, not left describing the old raise.
2. **`application/batch_2b_scoring.py`** (270 -> 270 lines, net zero): dropped
   the dead-module import; `_process_symbol()` now does a plain
   `entries.get(symbol.upper())` + None-check feeding the *existing*
   `skipped` list, same mechanism already used for every other per-symbol
   failure in this file.
3. **`application/batch_2b.py`** (211 -> 207 lines): the `except
   EarningsDataMissing` block in `cmd_batch_2b()` is unreachable now that
   `build_entries_for_symbols()` never raises it -- removed. Also fixed a
   stale inline comment that still said "FMP cache" on the
   `build_entries_for_symbols()` call site, left over from before the
   FMP-to-Nasdaq switch (WO-P400-E5.002) and never updated.

**What did NOT change:** the fail-loud safety principle from WO-P400-E5.002 --
a symbol with no confirmed earnings data is never silently treated as clear.
That's fully intact; a missing symbol still gets named with a reason in the
batch report's `skipped` list (`_print_ranked_table()` already renders this
section, unchanged). The only thing that changed is blast radius: one gap
now costs one symbol instead of every candidate in the same run.

**Verification:** all three files compiled clean under p140,

full-file rewrite.

## FOUND LIVE -- REVISION 2, 2026-08-19

Revision 1 fixed blast radius but left the underlying question open: why
does a fresh 1,483-symbol Nasdaq pull still miss HWM, TSN, APTV, CAR --
large, obviously-covered companies? Investigated live rather than assumed:

1. **Ruled out rate-limiting/blocking.** Direct `Invoke-RestMethod` calls
   from Tony's own PowerShell (real network path, same User-Agent spoofing
   the client already uses) hit both the per-symbol
   `/analyst/{symbol}/earnings-date` endpoint and the bulk
   `/calendar/earnings?date=` endpoint directly. Clean HTTP 200s throughout,
   no errors. Not a technical failure.
2. **Ruled out "Nasdaq doesn't carry the symbol."** The per-symbol endpoint
   returned an explicit, honest answer for HWM: "Our vendor, Zacks
   Investment Research, hasn't provided us with the upcoming earnings report
   date." The data exists (confirmed independently via Perplexity's
   connected feed AND the Nasdaq Earnings Calendar website itself showing
   up as one of its own sources) -- Nasdaq's automated data vendor just
   hasn't published it yet, this far out.
3. **Found the real shape of it.** Row counts by date, live-tested:
   2026-08-19 (today) 49 rows, 08-20: 57, 08-25: 43, 09-01: 11, 09-15: 2.
   Confirmed-date coverage is dense near-term and collapses hard past
   roughly two weeks out -- structural, not a bug, not fixable by pacing or
   switching endpoints (both endpoints hit the same underlying data gap).
4. **Found the actual mismatch.** `domain/earnings_window.py`'s
   `earnings_in_window()` -- the real gate MACRO uses -- checks a fixed
   3-days-forward/2-days-back window from TODAY (`config.py`
   `EARNINGS_WINDOW_FORWARD_DAYS`/`BACKWARD_DAYS`, Tony's explicit call
   2026-07-28, replacing an even wider 14-day-forward-only check -- see that
   date's session). It does NOT scale with a signal's `signal_horizon`. The
   original P_400 v0.3 architecture (2026-06-02 session) called for
   checking "the full expected holding period... not a fixed window" --
   that was never what got built; 2026-07-28 deliberately replaced a
   different fixed window with a narrower one, on Tony's explicit
   instruction, fully aware it would "retroactively widen what counts as
   clear." Confirmed directly by Tony 2026-08-19: "That is the real trading
   Window." The 83-day calendar pull was pulling 12x more data than the
   actual gate ever consumes -- it never looks past 3 days forward
   regardless of what's cached.

## FIX -- REVISION 2, 2026-08-19 (matching the pull to the real gate)

1. **`config.py`:** `EARNINGS_CALENDAR_LOOKAHEAD_DAYS` 83 -> 7,
   `EARNINGS_CALENDAR_LOOKBACK_BUFFER_DAYS` 7 -> 5. Small buffer around the
   actual +3/-2 gate, not the gate values exactly. Total daily calls per
   refresh: 91 -> ~13, landing entirely inside the dense part of the
   coverage curve measured above.
2. **`application/earnings_lookup.py`:** `build_entries_for_symbols()` no
   longer omits a missing symbol from the returned dict (Revision 1's
   behavior). With the pull now genuinely matched to the gate, "nothing
   found in this narrow window" IS the correct clear signal, not an unknown
   worth skipping over -- a constructed `EarningsEntry` with
   `next_earnings_date=None` is returned instead, flowing into full
   evaluation exactly the way an honestly-unknown date already does via
   `earnings_in_window(None)` returning False. Module docstring and
   `Raises:` section rewritten to describe this, not left describing
   Revision 1's skip behavior.

**Why this isn't the FMP-era danger the original hard-fail design was built
against:** that design's fear was real -- FMP's narrow ~73-symbol coverage
meant absence was unrelated to earnings timing (large-cap coverage only),
so treating absence as clear would have silently disabled the block for
most real signals. A miss in a 7/5-day Nasdaq pull is different in kind,
not just degree: it means "no report in the only window MACRO's gate
actually checks," which is the true, correct answer, not a coverage gap
standing in for one.
