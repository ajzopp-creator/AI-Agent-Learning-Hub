## WHY

2026-07-21 daily-evaluate run for CXW/JOBY/NCMI: CXW and NCMI's WATCH
signals were REJECTED from the SIGNAL_V2 write to P_400 --
`intelliscan_support_2` validation failure (`Stop/support level must
be positive when present, got -8.921096802` for CXW, `-17.08050728`
for NCMI). JOBY's BUY signal wrote through cleanly.

Investigation found the schema's positive-only check is real but
incomplete. Root cause, confirmed directly by Tony: `intelliscan_
support_1`/`_2` come from a manual two-step process -- a separate
IntelliScan tool export, then a manual copy/paste into the grid file
`daily_evaluate_pipeline.py` actually reads
(`P_300_HistoryGrid_IntelliscanEvalParameters.xlsx`). Tony re-ran the
export and compared old vs. new pasted rows directly:

| | Support 1 | Support 2 |
|---|---|---|
| Old (tonight's rejected run) | 84.88 | -8.92 |
| New (fresh re-export) | 28.70 | 32.30 |

CXW's real close that day was ~$31.85 (confirmed present in both old
and new rows, just at different column offsets between the two). A
support_1 of **84.88** for a $31.85 stock is not a support level --
it's a column-shifted paste. The negative support_2 got caught by the
existing schema check; the positive-but-wrong support_1 (84.88) would
NOT have been caught by anything, and would have flowed straight into
the SIGNAL_V2 packet if this run's support_1 had happened to validate
cleanly. Column misalignment from a copy/paste doesn't reliably
produce negative numbers -- it was luck, not defense, that this got
caught at all.

Tony's own framing: "it's the copy and paste that got us... I will
need to [double check] in the future but we also need to protect
against my manual errors." This WO is that protection -- a defense
that doesn't depend on the operator remembering to check.

## WHAT WAS BUILT

`application/daily_evaluate_pipeline.py` v1.21 -> v1.22. One guard
clause, right after `_is1, _is2 = get_support_levels(...)`, before
either value is used anywhere else (the ATR-stop calc or the SIGNAL_V2
packet assembly):

- Null (not fatal) any support value that is non-positive **or**
  deviates from `_close` by more than 50% in either direction.
- `_close` is deliberately the cross-check anchor -- it comes from the
  per-symbol History Grid export, a COMPLETELY SEPARATE file from the
  manually-pasted IntelliScan grid. Checking a pasted value against
  something from the same paste wouldn't catch a paste that's
  internally self-consistent but wrong; checking against an
  independent trusted source does.
- 50% is deliberately generous. `intelliscan_support_1` is documented
  as "primary stop anchor" -- a real near-term stop/support level for
  this pipeline's purpose has no legitimate reason to sit that far
  from price. A value this far off is far more likely a column-shifted
  paste than a genuinely wide structural support zone.
- Logged at WARNING (ticker, field, bad value, close, reason) so a bad
  paste is now VISIBLE in the eval output going forward, not silent.
- Nulling instead of rejecting fixes two things in one fix: tonight's
  whole-signal rejection (the WATCH classification, entry, and
  atr_adjusted_stop were all correct -- only the one optional field was
  bad) and the undetected-positive-but-wrong-value gap.

**Scope discipline:** `intelliscan_reader.py` untouched -- stays a
pure parser (project's own Process Boundary Standard). No schema
change. No change to P_400. No change to the ATR-stop fallback logic
(`_is1 < _close` check) -- it already existed and is now fed a
correctly-nulled `_is1` instead of a garbage one, which is strictly
an improvement to its own existing behavior, not new logic in it.

================================================================================
CORRECTION -- 2026-08-10, same session, same reviewer
================================================================================
The "3+ weeks of log history" claim in the review above is wrong.
`P_300_RunAllDailyEvals.ps1` opens `$LOG` with `Set-Content` at the top of
every run -- this OVERWRITES the file each time, it does not append across
sessions. The "0 implausible hits" I found was only ever today's single
run's data, not three weeks of history. Caught while investigating the
same question for WO-P300-E4.009 (which uses the same log).

**Does not change the closure decision.** The actual basis for closing
this WO was the code-correctness verification -- the guard formula
re-read directly from the live file and hand-checked against the exact
real CXW/NCMI numbers from the original 2026-07-21 incident (166.5%,
1150%, 9.9%, 1.4%, all landing correctly), which is unaffected by the log
issue. The false-positive claim was supporting color, not the load-
bearing evidence, and is retracted rather than left standing on a wrong
premise.

**Separate, real finding this correction surfaces:** the project has no
retained history of DailyEval runs -- each run's log destroys the prior
one. There is currently no way to audit "has this guard (or the E4.009
Chaikin-failure detector, or anything else that logs to $LOG) ever fired
in production" beyond whatever happens to still be in the file from the
most recent run. Worth a lessons.md entry / possible follow-up WO
(per-run log archiving, e.g. timestamped filename or append-with-rotation)
if this kind of retrospective check matters going forward -- not
building that here, flagging it.
