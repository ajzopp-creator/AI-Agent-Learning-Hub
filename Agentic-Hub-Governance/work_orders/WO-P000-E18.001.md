# WO-P000-E18.001 -- hub_mcp_launcher.ps1 Status File Never Written (Silent Detached-Launch Failure)

**Status:** CLOSED -- Independent Review completed 2026-09-01 (separate session, see block below).
**Owner:** P_000
**Affects:** Hub-wide -- shared_resources\hub_mcp_launcher.ps1 is used by every `_mcp.ps1` wrapper: P_010_daily_posture_mcp.ps1, P_010_intraday_mcp.ps1, P_020_WeeklyUpdate_mcp.ps1, P_300_AddPattern_mcp.ps1, P_300_DailyEval_mcp.ps1, P_805_daily_pipeline_mcp.ps1, and the new P_400_Batch2bCashPull_mcp.ps1.
**Depends On:** None

---

## WHY

### Discovery

2026-08-25, first live run of the new `P_400_Batch2bCashPull_mcp.ps1` wrapper
(built same session). Tony invoked it via Claude/Windows-MCP; it polled the
full 10-minute timeout with no status file ever appearing, even though the
underlying `.bat` actually failed in about one second (dead P_020 Schwab
refresh token). Tony then ran the `.bat` directly in the foreground and
confirmed it fails fast and cleanly on its own -- the `.bat` itself is not
the problem.

### Root Cause (confirmed via isolated repro, not guessed)

`Invoke-HubBat` in `shared_resources\hub_mcp_launcher.ps1` launches the
target `.bat` via:

```
cmd.exe /c "<BatPath>" && echo SUCCESS > "<StatusFile>" || echo FAILED:%ERRORLEVEL% > "<StatusFile>"
```

`cmd /c` only preserves the outer quoting of the command line under a narrow
condition: exactly two quote characters, no special characters between them,
and the quoted text is the name of an executable. This command line has SIX
quote characters (one pair around the bat path, one pair around each of the
two `StatusFile` redirect targets), so that condition fails. cmd.exe falls
back to its documented legacy behavior: strip only the very first and very
last quote character of the ENTIRE line and leave everything else as-is --
which corrupts the inner quoting and breaks the `&&` / `||` chain silently.
Neither branch fires; no status file is ever written, on success OR failure.

**Confirmed by direct test**, same session: built two trivial one-line test
`.bat` files (`exit /b 0` and `exit /b 1`), ran each through the exact
`Invoke-HubBat` `Start-Process` construction. In both cases `Start-Process`
reported success and returned a PID, the process exited within seconds
(consistent with the trivial bat), and in both cases the status file never
appeared. This means the bug is unconditional -- it is not specific to the
P_400 wrapper or to the failure path, and has likely been present in every
`_mcp.ps1` wrapper since `hub_mcp_launcher.ps1` v1.0 (2026-05-29). Prior
wrappers' apparent successes were presumably verified by checking downstream
artifacts (e.g., did P_020's weekly import actually land), not by trusting
the wrapper's own SUCCESS/FAILED/TIMEOUT text -- so this has likely gone
unnoticed rather than not occurred.

### Proposed Fix (not yet built)

Stop relying on shell-level `&&` / `||` chaining for the status write.
Generate a small one-off `.cmd` launcher at call time that does the
success/failure check with normal internal batch logic instead of inline
shell chaining:

```
@echo off
call "%~1"
if errorlevel 1 (
    echo FAILED:%errorlevel% > "%~2"
) else (
    echo SUCCESS > "%~2"
)
```

`Start-Process` then launches this generated `.cmd` directly with the real
bat path and status file path as plain arguments (`-ArgumentList @($BatPath,
$StatusFile)`) -- no inline quoting-heavy one-liner, no `cmd /c` multi-quote
edge case. This is the standard, reliable way `.bat` files check a called
program's exit code.

### Immediate Workaround (in effect now)

All `_mcp.ps1` wrappers should be treated as unverified for status reporting
until this is fixed -- run the underlying `.bat` in the foreground when the
actual pass/fail result matters, or check downstream artifacts directly
rather than trusting a TIMEOUT result as a true failure.

## RESOLUTION (2026-08-28)

`shared_resources\hub_mcp_launcher.ps1` bumped v1.0 -> v1.1. `Invoke-HubBat`
now generates a one-off `.cmd` launcher per call (`_launcher_<statusfile>.cmd`,
next to the status file, overwritten each run) that checks `%errorlevel%`
with normal batch `if` logic instead of the old inline `cmd /c "<bat>" &&
echo SUCCESS > "<status>" || echo FAILED:%ERRORLEVEL% > "<status>"` chain.
`Start-Process` launches the generated `.cmd` directly with `BatPath` and
`StatusFile` as separate `-ArgumentList` array elements, so PowerShell
quotes each one correctly -- no manual multi-quote one-liner, no `cmd /c`
edge case.

**Verification:** same repro as the original diagnosis -- two trivial test
bats (`exit /b 0`, `exit /b 1`) run through the fixed `Invoke-HubBat`.
Success case returned `SUCCESS`, failure case returned `FAILED:1`. Both
branches fire correctly; prior to the fix, neither wrote a status file at
all. Test artifacts removed from `Agentic-Hub-Governance\verify\` after.

**Caller propagation check:** all 7 affected wrappers (P_010_daily_posture_mcp.ps1,
P_010_intraday_mcp.ps1, P_020_WeeklyUpdate_mcp.ps1, P_300_AddPattern_mcp.ps1,
P_300_DailyEval_mcp.ps1, P_805_daily_pipeline_mcp.ps1,
P_400_Batch2bCashPull_mcp.ps1) dot-source the shared function and call
`Invoke-HubBat` -- none carry a local copy of the old inline chain. Fix
propagates to all 7 automatically, no per-wrapper edit needed. Note: the two
P_300 wrapper files (P_300_AddPattern_mcp.ps1, P_300_DailyEval_mcp.ps1) live
under `docs\archive\` only, with no active copy elsewhere in P_300 --
per standing Hub convention, files in an archive folder are deprecated
intentionally, not strays. They are not currently live entry points; the
fix still reaches them since they dot-source the shared function, but the
WO's Affects list of `7 wrappers` should be read as 5 active + 2
deprecated. No correction needed -- expected state, not an anomaly.

**Downstream notification:** documented here and reported to Tony directly
in session (2026-08-28) -- single-operator Hub, no separate downstream
session to notify beyond this WO record and this chat.

**Backup of pre-fix file:** `hub_mcp_launcher.ps1.backup_2026-08-28_1131`
