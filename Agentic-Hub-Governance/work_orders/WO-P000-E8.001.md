## WHY

`tasks/lessons.md` + `tasks/todo.md` is an append-only pattern (numbered
M-series lessons never deleted; todo.md prepends a dated entry every
session going back to project start) that several projects have grown
into organically -- it was never a documented Hub standard. Checked
directly: `P_000_SYSTEM_DOCUMENTATION.md` Section 3.1 ("Folder Structure --
All Projects") does not list a `tasks/` folder at all; it only appears in
Section 3.2, P_000's own project-specific structure. Reality across the
Hub is inconsistent, audited 2026-07-22:

| Project | CLAUDE.md | tasks/ (lessons+todo) |
|---|---|---|
| P_300 | no | yes -- todo.md 1,001 lines/~225KB, lessons.md 108 entries/~180KB |
| P_115 | no | yes |
| P_805 | no | yes |
| P_400 | yes (~8.6KB) | no |
| P_020 | yes (~4KB) | yes, but tiny (todo.md ~1.5KB, no lessons.md at all) |
| P_010 | no | no |
| P_800 | no | no |

**Update 2026-08-10:** P_115 row above is stale -- P_115 acquired a CLAUDE.md between 2026-07-22 and 2026-08-10 (created 2026-06-29, independently of this WO). See P_115 ROLLOUT AUDIT section at bottom of file for full findings.

P_300's own files have grown large enough to cause real session cost: a
`todo.md` read hit a tool-side "too large" truncation this session, and a
routine one-line WO-status correction required reconstructing and
rewriting the entire 225KB file (no in-place-edit tool reaches these
Windows paths for a targeted diff on a file this size). At the same time,
the append-only depth is NOT dead weight -- it is what let this same
session trace whether a real catalog purge had actually gone live, and
catch a real WO misattribution before it got logged wrong (M-107/M-108,
2026-07-22). A CLAUDE.md-only model (P_400's) has zero session history and
would have made that same recovery-of-truth exercise impossible. This WO
is explicitly NOT "replace tasks/ with CLAUDE.md" -- it is "keep the
append-only depth, stop paying its full cost on every read."

## WHAT P_000 OWNS GOING FORWARD

### 1. Per-project audit before any action

Project starting states above are too different for one mechanical rule.
P_000 audits each project's actual current-state needs before applying
anything -- some (P_010, P_800) may not need this pattern at all; P_020's
existing small CLAUDE.md + lean todo.md may already satisfy the intent
with no changes needed.

### 2. Current-state file -- RESOLVED 2026-07-22: name is `CLAUDE.md`

For projects carrying real accumulated depth (P_300 first): a small,
edited-in-place file at project root holding what INIT actually needs on
every session -- architecture snapshot, key paths, locked decisions,
active stage/next task -- distinct from the append-only session/lesson
logs. **Naming decided (Tony, 2026-07-22): `CLAUDE.md` at project root**,
matching the organic P_400/P_020 convention already in the Hub rather
than inventing a new name. Content overlap with each project's own
INIT/SIP "Session Summary" step and SKILL.md must still be resolved per
project, not assumed -- P_300 already generates account/posture/decision-
flags live at INIT; `CLAUDE.md` should not duplicate what SIP Step
5/5b/5c already freshly reads, only the genuinely static architecture/
decisions layer (the kind of content already in P_400's CLAUDE.md:
running commands, layer map, key paths, "Locked Decisions").

### 3. Live/archive split for tasks/lessons.md + todo.md -- RESOLVED 2026-07-22: size-based cap

Same retention shape as WO-P000-E4.002's changelog pattern, applied to
this doc family. **Cutoff decided (Claude's call, Tony deferred): a size
cap, not a fixed date or session count** -- a session-count/date rule
goes stale on its own (some sessions are 5 lines, some are 150+), while a
size cap is self-correcting and ties directly to the actual cost being
solved (read-truncation risk, full-file-rewrite cost on every edit).

- **`todo.md` live cap: ~500 lines / ~100KB.** Reasoning from today's
  real evidence: a 400-line read of the file's densest (most recent)
  content failed ("too large for context"); 100-140 line chunks of the
  same density read cleanly. 500 lines gives real margin under the
  observed failure point and reads in 1-2 calls even at worst-case
  density. At current pace (~600 dense lines covers roughly 2026-07-08
  through 2026-07-22, two weeks), 500 lines lands at roughly "the most
  recent 2-3 weeks" -- close enough to reason about in calendar terms
  without the rule itself being calendar-based.
- **`lessons.md` live cap: ~40 entries / ~70KB.** Lesson entries are
  short and structured (unlike todo.md's narrative paragraphs), so an
  entry count works better than a line count here. 108 current entries
  span ~180KB (~1.7KB/entry average); 40 entries is a safe single-read
  size with real margin.
- **Trigger:** whenever a live file crosses its cap, the oldest entries
  move to the sibling `_archive` file (nothing deleted) until the live
  file is back under cap. Same self-documenting pattern as E4.002: a
  one-line retention-rule note + archive pointer stays in the live file
  so the convention doesn't depend on anyone remembering it.
- Still open: WHO/WHEN notices a live file has crossed its cap and
  triggers the split. Cheapest option is a non-blocking INIT reminder
  (same shape as SIP Step 1A's preflight-freshness nudge) that checks
  live-file size/entry-count at session start and reminds, never HALTs.
  To be resolved as part of the P_300 pilot build, not decided here.
