## WHY

Tony currently hand-calculates and hand-writes three numbers into
`P_000_Account_Parameters_Current.md` monthly, per that file's own "Monthly
Review Checklist": pull current balance from broker, calculate Risk Capital
(balance x 0.015), calculate Max Position (balance x 0.05), then manually
update the file. E1.009 proved the write path works (Buying Power / Cash
Available now auto-populate on every balance pull). This WO extends the
same mechanism to Account Balance, Risk per Trade, and Max Position --
eliminating the manual monthly task.

**Historical note on "Account Balance":** Parameter History rows are
annotated "Net Liq per broker" -- this already matches `pull_balance()`'s
`total_value` field (`curr.get("liquidationValue") or curr.get("totalValue")`),
so no new Schwab data is needed, same as E1.009.

## SCOPE

Unlike E1.009 (2 independent reference rows), this touches 5 places in the
same file that must stay synchronized from one balance number:

1. **Active Parameters table** -- Account Balance, Risk per Trade, Max
   Position (5%) rows.
2. **Risk Mode Adjustments table** -- 5 rows (OFF/CORRECTION, HALF,
   STANDARD, FULL, HOT), each a percentage of the same base Risk/Max.
3. **Three-Gate Position Sizing code block** -- Gate 1 and Gate 3 dollar
   figures embedded in a fenced code block, not a markdown table.
4. **Growth Projections table** -- the "(current)" row only; the fixed
   $35K/$40K/$50K/$75K/$100K projection rows are static and untouched.
5. **Parameter History table** -- append one new row per update
   (Date | Balance | Risk | Max | Notes), never edit/delete prior rows.

A single domain function needs to derive all of the above from one balance
figure and rewrite all 5 locations atomically -- partial sync (e.g. Active
Parameters updated but Risk Mode Adjustments left stale) would be worse
than the current fully-manual process, since a stale table reads as
authoritative.

## OPEN DESIGN QUESTIONS (resolve with Tony when this WO is picked up)

1. **Silent auto-write every pull, or confirm gate?** Current recommendation
   on record (2026-05-30) was flag-and-confirm, not silent write, because
   these numbers directly set real-money risk per trade. Options:
   - **A -- Silent, every balance pull:** simplest, matches E1.009's
     pattern exactly, but a single volatile intraday pull could swing
     position sizing without Tony seeing it happen.
   - **B -- Threshold-gated:** only auto-write when balance crosses ±X%
     from the last *written* baseline (not last pull) -- day-to-day noise
     doesn't touch the file, meaningful moves do, no confirmation step,
     no dialogue needed.
   - **C -- Flag-and-confirm (matches existing SIP step):** compute and
     display the new numbers, write only after Tony explicitly confirms in
     that session -- closest to today's process, least automated.
2. **Which pull triggers this?** Every weekly balance pull (same hook as
   E1.009), or only a designated "monthly" run? File's own checklist says
   monthly; the underlying balance data updates weekly.
3. **Next Review date field** ("August 2026 (monthly) or when balance hits
   $35,000") -- auto-bump this too, or leave as a manual note?

## OUT OF SCOPE

- Any change to `RiskConfig.json` / P_010's risk_mode authority rule --
  that JSON field stays authoritative over the avg_posture ranges shown in
  the Risk Mode Adjustments table; this WO only keeps the table's *dollar
  values* in sync with balance, not the mode-selection logic itself.
- Changing the 1.5% / 5% base percentages themselves -- pulled from
  existing `P_020_Account_Params.json`, not hardcoded fresh here.
- P_400 or any other consumer's read-side logic -- `params_reader.py`
  changes are explicitly out of scope (same boundary E1.009 drew).

## ACCEPTANCE CRITERIA

- One balance pull produces a fully self-consistent file -- all 5 locations
  reflect the same balance, no stale cross-references.
- Parameter History gets exactly one new row per triggering update, never
  edits or removes prior rows.
- Whichever option is chosen for the open design questions above is
  explicit in the implementation, not left ambiguous.
- No regression to E1.009's Buying Power / Cash Available rows.
