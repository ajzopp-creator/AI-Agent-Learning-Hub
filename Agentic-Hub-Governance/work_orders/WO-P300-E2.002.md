## WHY

WO-P300-E2.001's own SCOPE explicitly deferred this: "Sector-level result
analysis (Phase 5, after scale-out)" was called out as OUT OF SCOPE, and
"Any merge or analog-pool use is a separate future WO gated on Phase 5
validation." Scale-out has produced 126 files across 7 sectors, well past
the ~384-instance threshold for a +/-5% margin at 95% CI in aggregate --
but the catalog has never actually been analyzed. Every symbol inserted so
far has `sector=None` (sector_map.csv was never populated -- WO-P300-E2.001

purpose). Without Phase 5, the research catalog is just a pile of verified
row counts with no analytical output -- the point was always to find out
whether STRICT/RELAXED detection rates and forward returns differ
meaningfully by sector, and whether the catalog is good enough to eventually
feed Pipeline B (a still-later, still-separate WO).

## DECISIONS (resolved 2026-07-10)

1. **Retroactive sector backfill: APPROVED.** One-time `UPDATE symbols SET
   sector = ? WHERE ticker = ?` backfill against all 126 existing symbols,
   keyed off sector_map.csv, run once the map is built.
2. **Sector classification standard: GICS** (Global Industry Classification
   Standard, S&P/MSCI) -- the market standard, used by virtually all US
   equity research and sector ETFs (XLE/XLF/XLK/etc.). CRITICAL CORRECTION:
   the informal export-batch labels used during WO-P300-E2.001 (Basic
   Materials, Capital Goods, Consumer Cyclical/Non-Cyclical, Services) are
   NOT real GICS sectors -- they were licensing/export convenience buckets
   only. sector_map.csv must be built from an actual per-symbol GICS Level-1
   lookup, not a reuse of the batch label. Known mismatch already
   identified: MCO/SPGI/VRSK/FDS were bucketed under "Services" during
   export but are true GICS Financials -> Capital Markets, not a services
   grouping. **Zero-tolerance requirement (Tony, 2026-07-10): no symbol may
   ever be left without a sector assignment -- an unclassified symbol is a
   data integrity error, not an acceptable gap.** All 126 current symbols
   (including the 7 IntelliScan mixed-batch symbols) get a real, verified
   GICS sector -- no "Unclassified" bucket permitted as a resting state.
3. **Output form: RECONSIDERED, table approved.** Original assumption
   (report-file-only) reflected mid-scale-out caution about adding
   complexity -- no longer applicable now that scale-out is substantially
   complete. Add a small additive `sector_stats` table to
   research_catalog.db (new table, does not touch the existing 7), written
   via the same Lock+Temp-DB+Atomic Move pattern already built in
   research_catalog_io.py. Gives a queryable, re-runnable historical record
   as more sectors get added incrementally, instead of a disposable
   from-scratch report each time. Human-readable report still generated,
   but FROM the table, not instead of it.
4. **Per-sector minimum N: flag, don't exclude -- CONFIRMED, with a scope
   note.** Sector coverage will remain incrementally partial: Tony is not
   licensed for all GICS sectors and each additional license is a real cost
   that needs to be justified by trading profitability first -- this WO
   does NOT require or assume eventual full 11-sector coverage. Analysis
   runs against whatever sectors are actually licensed and cataloged at
   any given time; under-sample sectors/tiers are flagged in the report,
   not excluded, and missing GICS sectors entirely (no symbols licensed
   yet) are simply absent from the report, not an error.
5. **ETF/index vehicles: NEW DECISION (2026-07-10), added mid-build after
   discovering SPY has no single GICS sector.** Checked all 126 catalog
   symbols -- SPY is currently the only non-single-company security
   (GNL and HESM looked unusual at a glance -- a REIT and an MLP
   respectively -- but both are real single-entity securities with
   legitimate GICS classifications, not funds). However, Tony has a
   separate VantagePoint license category for ETFs not yet exported --
   any future ETF batch would hit this same problem systematically, not
   as a one-off. Checked for an existing ETF-detection mechanism in the
   codebase (config.py, daily_evaluate_pipeline.py) -- none exists; the
   "ETFs skipped cleanly" behavior noted elsewhere (Chaikin Power Gauge
   integration) is just a URL-scheme detail (`/pgr/etf/` vs `/pgr/stock/`)
   local to that one integration, not a reusable registry.
   **Design adopted:** `sector_map.csv` gets a 4th column, `asset_class`
   (`STOCK` | `ETF`). ETF rows carry `sector=N/A` (never a fabricated
   sector value -- this does NOT violate Decision 2's zero-tolerance rule,
   since Decision 2 is about every STOCK having a real sector, not about
   forcing a sector onto something that structurally doesn't have one).
   Phase 5 analysis groups STOCK rows by sector as designed; ETF rows get
   their own separate "Index/Diversified" summary line, never silently
   dropped and never force-fit into a sector bucket. This means licensing
   and bulk-extracting the VP ETF category later requires zero rework of
   this WO's design.

## SCOPE

- `data/reference/sector_map.csv` built from verified per-symbol GICS
  Level-1 lookups (not reused export-batch labels), 4 columns
  (`symbol,sector,asset_class,source_note`) -- covers all 126 current
  symbols with zero gaps (Decision 2), 125 STOCK + 1 ETF (SPY, Decision 5).
  Built and verified 2026-07-10.
- One-time sector backfill script (`infrastructure/`, I/O only) applying
  sector_map.csv to existing `symbols` rows in research_catalog.db.
  Lock+Temp-DB+Atomic Move per Must-rule #2, same pattern as the extractor.
  Must fail loudly (not silently skip) if any symbol in the catalog has no
  entry in sector_map.csv -- enforces Decision 2's zero-tolerance rule at
  the code level, not just by convention. For ETF rows, `sector` backfills
  to NULL/N/A explicitly (not left unset by omission).
- New additive table `sector_stats` in research_catalog.db (Decision 3) --
  schema TBD in file plan, written via the same Lock+Temp-DB+Atomic Move
  pattern as the rest of research_catalog_io.py. Does not alter the
  existing 7 tables.
- Read-only analysis module (`application/`, orchestration only + a
  `domain/` layer for the actual stats logic -- no I/O in domain) computing,
  per sector x detection_tier x horizon (5/7/10/15/20), for STOCK rows only:
  - n (instance count)
  - win rate (`significant_move_15`-style logic, or return_pct > 0 --
    confirm definition against existing forward_labels schema)
  - mean / std forward return_pct
  - flag if n falls under the agreed minimum-N threshold (Decision 4)
  ETF rows (asset_class=ETF) get a separate "Index/Diversified" summary
  line computed the same way but never merged into a sector bucket
  (Decision 5). Writes results to `sector_stats`, then generates a
  human-readable report FROM that table (not computed fresh into the
  report directly).
- Explicitly does NOT: touch live `*catalog.db`, touch Pipeline B, change
  BUY/WATCH/PASS signal logic, or write anything back into
  `pattern_instances`/`pattern_bars`/`forward_labels`.

---

6. **Minimum-N threshold: RESOLVED (2026-07-10, Claude's recommendation,
   Tony confirmed) -- flat N=30 per sector x detection_tier x horizon
   cell.** Not the ~384-instance whole-catalog margin-of-error figure from
   WO-P300-E2.001's scope decision -- that number supports a +/-5% CI claim
   on one aggregate proportion; re-applied per cell (5 horizons x 2 tiers
   split within each sector) it would flag nearly every cell as the catalog
   is currently sized, making the flag meaningless. N=30 is the standard
   rule-of-thumb floor for a normal approximation to hold on a win-rate or
   mean-return statistic -- below it, flag as low-confidence per Decision 4
   (flag, don't exclude), not a hard cutoff. `SECTOR_MIN_N_THRESHOLD = 30`
   lands in config.py (file #1 of the approved build).
