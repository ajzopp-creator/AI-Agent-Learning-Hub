## WHY

2026-07-10 session close-out flagged this as the next candidate after the
CIEN head-to-head made the case explicit: STRICT detector precision
equals Tony's manual picks, and the detector catches real large moves
(Aug-2025 CIEN +52.5%) that manual review never looked at. Merging the
research catalog into the live analog pool was tried and rejected
instead (WO-P300-E2.003, PARKED -- BUY win rate dropped 68.8% -> 63.6%
post-merge). The alternative direction: keep the two catalogs separate,
use the detector as a **breadth scanner** that produces a candidate

eyeball remains the gate into the live catalog, same as every AddPattern
run today -- this WO automates candidate discovery, not candidate
acceptance.

## DATA SOURCE -- RESOLVED 2026-07-12

VantagePoint's IntelliScan natively screens the full symbol universe
against 70+ built-in criteria (including its own "recent predictive
crossovers" call) in one action -- that's the real fix for the
per-symbol export burden originally flagged as this WO's blocker.
Tony's confirmed nightly workflow:

1. Tony runs IntelliScan's crossover screen (native VP feature, whole
   universe, seconds) -- this is VP's OWN crossover call, narrower and
   cruder than P_300's 9-condition STRICT/RELAXED definition (VP's
   "crossover" is closer to condition 1 alone, not the full AND-chain).
2. Bulk-exports the resulting candidate symbols in the SAME format
   already used for the research catalog build: `<years>[I]_Pattern_
   <SYMBOL>.xlsx` (e.g. `10_Pattern_AAPL.xlsx`) -- `BulkBarRaw` shape,
   already parsed by `infrastructure/bulk_grid_reader.py`
   (`parse_bulk_file()`), already detected by
   `domain/bulk_pattern_detector.py` (`detect_bulk_pattern()`). Zero
   new parsing or detection logic needed -- both were built and
   PEH-verified under WO-P300-E2.001.
3. Drops the files. This WO's orchestrator reads them, re-applies the
   FULL 9-condition STRICT test to each (narrowing VP's cruder
   crossover list down to the same bar P_300's research catalog uses),
   and reports STRICT-only hits -- Tony confirmed "Cross Over only"
   (2026-07-12), consistent with the CIEN precision finding (STRICT ==
   manual precision; RELAXED was never the comparison point).

**Folder decision (Claude's call, not re-asked):** new subfolder
`data/bulk/nightly_scan/`, NOT the top-level `data/bulk/` where the
126-file permanent research corpus already lives. Verified
`bulk_extract_pipeline.py`'s file discovery
(`input_dir.glob(BULK_INPUT_GLOB)`) is non-recursive -- a subfolder is
invisible to it by construction, so nightly scan files can never get
swept into a future research-catalog bulk-extract run, and the
permanent corpus can never get rescanned as if it were tonight's
candidate list. Tony said "the bulk folder" generically; this satisfies
that while keeping the two file populations structurally separate.

**Point-in-time, not historical sweep:** unlike
`bulk_extract_pipeline.py` (walks every eligible bar of a multi-year
file for the historical corpus), this WO's orchestrator calls
`detect_bulk_pattern(bars, len(bars) - 1)` once per file -- only the
most recent bar matters for a nightly candidate check.
`bulk_windowing.py`'s spacing-rule logic is not used here (that's a
within-file multi-hit dedup for historical sweeps; irrelevant to a
single point-in-time check per file).

## ARCHIVING -- RESOLVED 2026-07-12 (corrects the original "no archiving" draft)

Tony rejected no-archiving. Every file processed by the scanner --
STRICT hit or not -- gets moved out of `data/bulk/nightly_scan/` after
processing, into a monthly zip at:

    E:\AI-Agent-Learning-Hub_BackupFiles\10_Pattern_BulkCreate<MMMYY>.zip

e.g. `10_Pattern_BulkCreateJul26.zip`. Confirmed the target directory
already exists and already holds a related file
(`10_Pattern_BulkCreate.zip`, 21.8 MB, no month suffix -- an existing
one-time backup of the original research-corpus bulk exports, not
touched by this WO). New monthly-suffixed zips are additive, this WO's
own archive stream, never overwriting or appending to the existing
unsuffixed file.

Reuses the exact safety pattern already proven in
`utilities/archive_pattern_file.py` (Pipeline A's archiver): append to
zip with a date-prefixed entry name to avoid collisions -> verify the
entry landed by re-opening the zip -> only then delete the source file.
Zip write failure leaves the source file in place, same as today's
AddPattern archiver. New file `utilities/archive_scanner_file.py`
mirrors it, adapted for the bulk filename convention
(`<years>[I]_Pattern_<SYMBOL>.xlsx` regex, not
`Pattern_YYYYMMDD_YYYYMMDD_SYMBOL.xlsx`) and the E:\ target path instead
of `DATA_PROCESSED`. Called automatically per file inside
`scanner_loop.py`'s loop -- not a separate manual step, since every
scanned file archives regardless of hit/no-hit.

## SCOPE

- New `application/scanner_loop.py` -- for each `*.xlsx` file in
  `data/bulk/nightly_scan/`: parse via `parse_bulk_file()`, run
  `detect_bulk_pattern()` at the last bar only, keep STRICT hits, skip
  RELAXED/no-hit silently (logged at INFO, not surfaced in the report).
  Archives every file via `archive_scanner_file.run_archive()` after
  detection, regardless of outcome. Pure orchestration -- no DB write.
- New `infrastructure/scanner_report_writer.py` -- formats STRICT hits
  into a markdown watchlist: ticker, anchor date, resistance level,
  9-condition pass detail (audit trail, same rationale as every other
  detection report in this project). Written to
  `outputs/reports/scanner/scanner_<YYYYMMDD_HHMMSS>.md`. **Read-only
  artifact. No DB write of any kind** -- the key design boundary that
  keeps this WO out of WO-P300-E2.003's rejected-merge territory. The
  detector's opinion never enters the analog pool automatically.
- New `utilities/archive_scanner_file.py` -- per-file archive to the
  monthly E:\ zip, verify-then-delete, mirrors
  `archive_pattern_file.py`'s proven safety pattern.
- `cli.py` -- add `scanner-loop` subcommand, orchestration call only.
- New `P_300_ScannerLoop.bat` -- operator launcher, mirrors
  `P_300_Preflight.bat`'s simple pattern, goto-label (M-032) -- no
  PowerShell python subprocess from inside a chat session (M-030).
- Tony reviews the watchlist by eye, manually selects winners,
  re-exports single-symbol Pattern files for those tickers exactly as
  today, runs `P_300_AddPattern.bat` exactly as today. **No change to
  Pipeline A, AddPattern, or the live catalog schema.**
