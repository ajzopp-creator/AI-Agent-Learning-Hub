# WO-P400-E9.001 -- hub_mcp_launcher.ps1 Silent Detached-Job Failure (No Output Capture)

## WHY

Live 2026-09-21: a P_400 `batch-2b` run reported `"fetch-snapshot failed -- see
console output above"` inside its own JSON output -- but there was no "above"
to see from the MCP side. `Invoke-HubBat` launches every job via `Start-Process
-WindowStyle Hidden` with zero stdout/stderr redirection anywhere -- the
detached bat's console output goes to a hidden window and is lost. The bat's
own exit code was even 0 that run (a soft internal skip, not a script
failure), so the existing `FAILED:N`/`TIMEOUT` branches wouldn't have caught
it either -- there was no path from "something went wrong inside the job" to
anything visible outside it.

## WHAT

1. `Invoke-HubBat` now derives a console-log path automatically from
   `$StatusFile` (e.g. `mcp_status_batch2b_cashpull.txt` ->
   `mcp_status_batch2b_cashpull_console.log`, same folder) -- no new required
   parameter, fully backward compatible.
2. The one-off `.cmd` launcher redirects the `call` line's stdout+stderr into
   that log (`call "%~1" > "%~3" 2>&1`); `$LogFile` passed as the 3rd
   `Start-Process -ArgumentList` element.
3. A `"LOG: <path>"` line is always appended via `Write-Output` after the
   result (`SUCCESS`/`FAILED:N`/`TIMEOUT`), flowing into the caller's
   `$result` the same way the existing `RUNNING`/`SUCCESS` text already does.
4. Header bumped v1.2 -> v1.3 with a dated changelog paragraph.

## FIX APPLIED (2026-09-21)

Patched live via windows-mcp:PowerShell, standard safety pattern: read full
file -> backup (`hub_mcp_launcher.ps1.backup_2026-09-21`) -> match-count-guard
(6 distinct edits, each guarded, all matched exactly once) -> replace ->
UTF-8-no-BOM write -> read-back verify (all 6 new markers present, all 3 old
markers confirmed gone) -> ParseFile clean parse, no syntax errors -> dot-sourced
in an isolated child process, confirmed Invoke-HubBat's public parameter set
unchanged (BatPath, StatusFile, PollSeconds, TimeoutMinutes + common params only).
## LIVE VERIFICATION (2026-09-21)

Re-ran the P_400 batch-2b wrapper twice after the fix (both real runs, not a
synthetic test):
- Run 1: genuinely failed -- `RESULT: FAILED:1 LOG: ...mcp_status_batch2b_cashpull_console.log`.
  Log file read back, showed the real Python error in full for the first time
  from the MCP side: P_020's Schwab refresh token was expired/revoked
  (`invalid_grant`, HTTP 400 on `get_account_hash`). Previously this would
  have been invisible; the only signal would have been `FAILED:1` with no way
  to know why.
- Run 2 (after P_020 token re-granted): `RESULT: SUCCESS LOG: ...console.log`
  -- LOG line present on the success path too, as designed (the original bug
  was a *soft* failure at exit code 0, so capturing only on failure wouldn't
  have caught it).

Confirms the fix works end to end on real, unplanned failures -- not just a
syntax check.
