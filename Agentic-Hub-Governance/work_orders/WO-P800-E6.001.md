## DECISIONS (2026-09-06, made in a P_805 session)

1. **Candidate list, not an auto-trigger.** P_805 output sits at the same
   tier as P_117's subscription-service inputs (Big Trends/SNT). P_115's
   mandatory chart-pattern check and "analysis first, Tony decides after"
   rule for outside signals stays intact — the dashboard surfaces
   candidates for Tony to glance at and manually run through P_115's
   diagnostic. Nothing here should silently create a BUY signal.
2. **Tracker placement: fold into P_117, no new tier.** SignalSource stays
   `P_117` ("Outside Recommendations") for anything that graduates from
   this dashboard into the 27-column tracker — Tony doesn't need
   newsletter-consensus visually separated from Big Trends/SNT right now.
   Reversible later if he wants to isolate email-sourced signals (e.g. to
   pause just those).
3. **Noted, not in scope:** Tony's longer-term aspiration is full
   automation — P_115's diagnostic eventually auto-gating on its own
   criteria against these candidates, still with no skipped checks, just
   machine-executed instead of manual. Not building toward this now, but
   the dashboard's data shape shouldn't foreclose it later.
4. **No manual input, anywhere.** Corrects an earlier misreading in this
   same conversation: Tony's action stays exactly what it already is —
   pulling a candidate symbol up on a TOS chart to eyeball the pattern.
   That is not data entry for this dashboard. The "BUY/ASYM passed"
   columns are a JOIN against records that already exist, not anything
   Tony types into this tool.
5. **Verdict source: the Tracker, not the raw signal JSON.** P_115 emits
   a signal JSON (input to P_400) carrying the native `BUY | ASYM | PASS`
   vocabulary directly — no P_400 council-language mapping needed, so
   the vocabulary-mismatch concern raised earlier in this conversation
   doesn't apply. But that JSON is temporal and gets archived once P_400
   consumes it (`trading_journal\TradeOrderManagement\signals\`) — not a
   practical thing to query historically. The Tracker Dashboard spreadsheet
   is where the same verdict is available "anytime" per Tony, so it's the
   actual join target for MTD/YTD counting, not the archived JSON.
6. **PASS excluded; BUY and ASYM both count; paper and live both count**
   — no distinction needed between paper/live for this dashboard's purpose.

**2026-09-21 (same session, continued)** -- Tony asked how the join window
should be measured, given a volatile 2026. Ran a lag analysis
(`Agentic-Hub-Governance\verify\run_this_P800_20260921_join_window_lag_analysis.py`,
read-only) against the full ranked.csv history (27 files, 2026-06-14 to
today) and the live Tracker: of 302 distinct (source, ticker) pairs ever
surfaced, only 12 ever hit BUY/ASYM at all, and the old 15-day window caught
just 2 of those 12 (17%). Median lag from first_seen to actual hit was 36
trading days; 25th percentile alone was 19, already past the old cutoff.
Tony approved raising `JOIN_WINDOW_TRADING_DAYS` 15 -> 45 (captures ~75% of
real hits per the same analysis). Applied in `config.py`, compiled clean,
re-ran the dashboard live: YTD BUY/ASYM hits across the 21 sources went
from 4 to 9, consistent with the analysis. Sample is thin (12 hits) --
worth re-running the same lag-analysis script periodically as more Tracker
history accumulates, to confirm 45 still holds.
