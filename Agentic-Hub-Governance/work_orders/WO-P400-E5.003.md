## WHY

The Tier-2B path is fully built and works, but runs as N separate console
round-trips per session. The 2026-08-05 session ran 7 symbols: ~13s of fetch
compute and ~11s of evaluate compute, spread across roughly ten copy-paste cycles.

Compute is not the bottleneck. Round-trips are, and they are structural -- PEH
requires Tony to run every Python command in his own terminal (PowerShell MCP
hang risk, confirmed repeatedly, twice more during this session). No amount of
parallelism reduces how many times a human has to paste.

Collapse N round-trips into one command that loops internally and prints one
ranked table.

## DESIGN DECISION -- loop, not agent graph

Evaluated against "Graph Engineering explained" (KnowledgeBase, 2026-07-29,
reviewed same session) using its own fake-edge test.

Per symbol the chain is real (evaluate needs the snapshot; snapshot needs the
earnings date). Across symbols there are no edges. So a fan-out genuinely exists
and the shape resembles the article's diamond. It is still the wrong tool:

1. **Six of seven steps are deterministic Python**, not agent reasoning.
   `screen-all`, `fetch-snapshot`, `fetch-chain`, `evaluate`, `spec`, `record`
   are pure function calls with no judgment in them. Wrapping an HTTP call in a
   reasoning loop is the article's Section 8 "coordination is pure overhead"
   case. The one genuinely agentic node is earnings/sector lookup -- E5.002.

2. **Parallel fetch is a false-independence trap** (article Section 7.2).
   Concurrent fetches would all refresh the same P_400 token file -- precisely
   the refresh race schwab-py's docs warn about and WO-P020-E1.010 exists to
   avoid. Inputs are independent; the API and the token file are not. Hidden
   edge. Parallelism here breaks auth rather than merely wasting effort.

Conclusion: sequential loop in a single CLI command. Per the article's own
closing rule -- "It is a loop, and a loop is fine."
## SCOPE

1. New CLI subcommand `batch-2b`. Runs Tier-1 screen, loops each PASS symbol
   through the vehicle pipeline below, collects verdicts, prints one ranked
   table. One command, one paste-back.

2. **Options-first vehicle selection** (Tony's decision, 2026-08-05, restating a
   long-standing preference). Replaces today's three-way conditional fork
   (stock sizes to 0 OR R:R < 2:1 OR Tony asks). New order: try options, fall
   back to stock.

   **Important mechanical constraint:** `OPTION_RR_PARITY_MIN` (config.py:122)
   defines qualification as `option_rr >= stock_rr * 1.0` -- a *comparison
   against the stock path*, not an absolute bar. `options_council.py:67-68`
   takes `stock_rr` as a parameter. So options-first cannot mean skipping the
   stock computation; both R:Rs must exist for parity to evaluate. Options-first
   means the option wins where it qualifies, not that the stock path is bypassed.

   **RESOLVED at build, 2026-08-05 -- this scope item collapses to a call.**
   `domain\vehicle_selector.py::compare_vehicles()` already implements the whole
   of this item, orchestrated by `application\compare_vehicles.py` (146 lines)
   behind the live `compare` subcommand, covered by `test_vehicle_selector.py`
   and `test_compare_vehicles.py`. It computes both paths, runs the options
   council viability gates, applies parity, and returns
   `STOCK | OPTION | SPREAD | OPTION_OVERRIDE_ONLY | NEITHER`. Its tie-break is
   already options-first: `option_rr >= stock_rr` recommends OPTION, commented
   "option wins ties (leverage benefit)".

   It is also stricter than a fresh build would have been. WO-P400-E3.004 fixed
   two failure modes in it: a 0-contract override-required option counting as
   viable and winning on raw R:R, and the council gates existing but never being
   invoked on the live path. `OPTION_OVERRIDE_ONLY` is a distinct return value
   specifically so it cannot be silently relabeled "OPTION".

   `batch_2b.py` therefore CALLS this per symbol. It does not implement vehicle
   selection. Building one would have duplicated live, already-hardened logic.
   File estimate drops ~145 -> ~110 lines.

3. **Ranking is a deterministic composite score, explicitly NOT a probability.**
   P_400 has no probability model and this WO does not add one. Score composes
   R:R, ATR-multiple headroom, spread, liquidity, and drift. Column header and
   report field read "score" -- never "probability" or "confidence".

   Ranking sorts only APPROVED candidates. Everything reaching it has already
   cleared R:R >= 2.0 and stop >= 1x ATR, so the invariant worth testing is
   *discrimination among survivors*: a candidate with stop at 1.05x ATR must not
   outrank an otherwise-comparable candidate at 2.4x ATR. Raw R:R alone must not
   drive the sort.

   **Correction, spec v1 -> v2:** v1 asserted a sub-1x-ATR-stop candidate "must
   not rank top", citing INDI (2026-08-05, R:R 22.78, stop 0.05 vs ATR 0.31).
   That criterion was wrong and is struck. INDI was BLOCKED by QUANT's
   STOP_TOO_TIGHT gate and never reaches ranking at all -- the test asserted an
   input that cannot occur, which would have given false confidence that ranking
   guards something it never sees. Tony caught this. The existing stop >= 1x ATR
   rule (SIP Step 3A, `quant_vote()`) already handles it and fired correctly six
   times that session.

4. **Heat is warned, not accumulated** (Tony's decision, 2026-08-05). Each
   evaluate continues sizing independently against the book as it stands. The
   ranked table prints a warning line stating cumulative committed risk if every
   APPROVED row were taken, against the heat cap. The runner does not net
   positions across the batch and does not auto-decline on cumulative heat.
   Rationale: sequential single-trade sessions never surfaced this because only
   one trade was taken; a batch returning five APPROVED rows makes it visible,
   and the right response is to show Tony the number, not have the tool silently
   arbitrate. Consistent with RISK never blocking (SIP v2.4).

5. Earnings bridge: runner reads `earnings_YYYY-MM-DD.json` (session-scoped),
   written once per session from the manual web-search pass. A symbol missing
   from the file is a hard, named error -- never a silent skip, never an assumed
   "no earnings". Retired when E5.002 ships.

6. **`fetch-chain` gains a viability warning line.** Found live 2026-08-05:
   `fetch-chain DLO --type call` auto-selected a strike and printed
   `OI=68 spread=15.4%` with no flag, despite both failing gates already in
   config -- `OPTION_OI_MINIMUM=150` and `OPTION_SPREAD_MAX_PCT=10.0`. Rejection
   only surfaces later inside `options_council.py`. For a batch pulling one chain
   per PASS symbol, that is N silent selections where some are already dead. Add
   a WARN line at fetch time comparing the selected contract against both gates.
   Reporting only -- gates, thresholds, and where they BLOCK are unchanged.

7. **SIP updated in this same WO.** `docs\prompts\P_400_SESSION_INITIALIZATION_PROMPT_v2_0.md`
   Step 2 currently documents stock-first with an options fork. Shipping
   options-first while the SIP says stock-first recreates exactly the doc-drift
   WO-P020-E1.010 hit (skill file pointed at a command deleted nine days
   earlier, cost a live session an improvised workaround). Both change together
   or neither does. `p400-project-context` SKILL.md checked in the same pass.

## OUT OF SCOPE

- Parallel/concurrent fetching -- see Design Decision item 2.
- Any agent-graph or sub-agent orchestration.
- Automating earnings/sector acquisition -- that is E5.002.
- Auto-submitting orders. Tony reads the table, picks, runs `spec`, submits in
  Schwab himself. Unchanged.
- Changing any option gate threshold. `OPTION_OI_MINIMUM`,
  `OPTION_SPREAD_MAX_PCT`, `OPTION_RR_PARITY_MIN`, `OPTION_IV_RANK_SPREAD_PREF`,
  `OPTION_ATR_FLOOR_MULTIPLE` keep their current values.
- Tier-2A / dossier path.
- Any new options-viability pre-check heuristic. Explicitly rejected: the chain
  pull is ~1 HTTP call and returns OI and spread directly -- the exact two
  numbers the gates need. A proxy built from underlying price/volume would be
  strictly worse than the measurement it approximates.
- Pushing options-viability upstream to P_115/P_300. Rejected: those are pattern
  and dip scanners on the underlying with no options data; adding chain calls
  there duplicates P_400's job and gives them a second reason to change. Vehicle
  selection is P_400's.

## ACCEPTANCE CRITERIA

- `batch-2b --cash DOLLARS` runs screen-all, loops all PASS symbols, prints one
  ranked table, in a single invocation.
- Per-symbol verdicts are byte-identical to running the equivalent commands
  individually with the same inputs -- the runner adds no evaluation logic.
- Options-first: for a symbol whose option qualifies under parity + viability,
  the runner reports the option vehicle. Where it fails either, the runner
  reports the stock vehicle. Both outcomes exercised before OWNER_DONE.
- Ranked output labels its ordering column "score"; the string "probability"
  appears nowhere in output or schema.
- Among two APPROVED candidates equal on other factors, the one with greater ATR
  headroom ranks higher. Regression test in `tests\test_ranking.py`.
- Cumulative-heat warning prints whenever two or more rows are APPROVED, showing
  summed risk vs cap.
- A symbol absent from the earnings file produces a named error identifying the
  symbol; that symbol does not proceed and is not assumed clear.
- `fetch-chain` prints a viability WARN when the auto-selected contract fails
  either gate. Verified against the DLO 2026-08-05 case (OI=68, spread=15.4%) --
  both gates must flag.
- Existing commands run unchanged; `test_council.py` still passes in full.
- SIP Step 2 and `p400-project-context` SKILL.md reflect options-first before
  this WO moves past IN_PROGRESS.
- Runner writes its ranked report through a Pydantic schema (persistent I/O).

### Bug found and fixed same session: disposition gap
`batch_2b_scoring.py` originally called `evaluate_signal()` directly with no
disposition wrapper -- `evaluate_signal()` itself has no I/O side effects
(confirmed by reading it), and `cmd_evaluate()`'s disposition logic
(`write_eval_cache` / `build_spec`+`cache_spec_text` / `write_p400_record`
on BLOCKED / `archive_packet` unconditionally, all in `commands.py`) was
never wired into batch_2b's per-symbol loop. Net effect: a batch-2b-
evaluated symbol never left the inbox regardless of verdict -- BLOCKED got
silently re-evaluated (and re-billed against live Schwab) on every
subsequent run, and APPROVED had nothing cached for `record` to find. This
is a direct hit against this WO's own acceptance criterion ("byte-identical
to running individually"), found live when Tony asked why FSLR kept
reappearing.

Fixed via new file `application\batch_2b_disposition.py` (64 lines) --
`dispose_evaluation()`, called right after every `evaluate_signal()` in
`_process_symbol()`, reusing the exact same functions `cmd_evaluate()`'s
plain-stock branch already calls. Not counted in the file-plan table above
since it didn't exist as a planned file; recorded here instead.
