## WHY

WO-P300-E4.005's own candidate-lever ranking (Finding 2) identified the
top-K state cache as the only lever with a real path to the <15-min
target at 1700-symbol scale -- JIT (lever #1) and parallel (lever #2,
now parked, Phase 2c) are constant-factor: they make each pair cheaper
but a full rescore stays O(N^2). This lever removes the quadratic term
for the common case (per-batch cost O(N^2) -> O(B*N)).

Real economics, computed against the actual post-JIT measured rate
(0.0654ms/pair, Phase 2b/2c) and today's real catalog size (N=10,761,
B=1792 from the batch just promoted):
  - Full rescore (what M-079 just ran): ~63 min
  - Top-K cache path at today's scale: ~1.9e7 pairs x 0.0654ms =
    ~21 min -- real, but does NOT hit 15 min alone at today's size.
  - At 1700-symbol scale (~44k patterns), a full rescore is N^2/2 ~=
    9.7e8 pairs ~= 17-18 HOURS serial -- at that scale this lever is
    the difference between "a batch takes ~minutes" and "a batch isn't
    a per-batch operation at all anymore." That's the real
    justification, not a today's-speed number.

## DESIGN DECISIONS -- CONFIRMED 2026-07-19 (Tony)

1. **Replaces `run_incremental_post_batch`'s current incremental path
   outright** -- not built alongside it as a third option. Rationale
   (Claude's, Tony confirmed): the existing incremental path
   (`assemble_incremental_post_batch` / `IncrementalGuardrailError`
   fallback) has never actually fired successfully on a real batch --
   both real batches to date hit ~0% reuse fraction and skipped
   straight to a full parallel/serial rescore via the v1.2 "worth it"
   threshold. The top-K cache becomes the ONE incremental path, not a
   second option sitting next to a path that's never actually run.
2. **Storage: a new table inside `catalog.db` itself** -- single
   source of truth, not a separate cache DB or side file. No second
   store to go stale or fall out of sync with the real catalog, no new
   fingerprint/invalidation logic needed (unlike the eval_cache JSON
   files, which are keyed to a content fingerprint precisely because
   they're NOT the source of truth). Table shape (draft, not final):
   `pattern_instance_id, rank, matched_pid, composite_distance`.
3. **Cache-update step reuses `_partition_unaffected()`'s corpus-
   eligibility filter, applied at two levels (confirmed 2026-07-19,
   Tony).** New pids (the batch itself) get fresh top-K scored against
   their full corpus -- no shortcut, same cost as today's full
   scoring, and this is what dominates the ~21-min estimate. Existing
   pids are first split via `_partition_unaffected()` on
   `min_new_date` (M-082, reused not re-derived): pids with
   `anchor_date <= min_new_date` are provably unaffected and skipped
   entirely -- their cache row is never opened. For the remaining
   "must-check" existing pids, only new pids with `anchor_date`
   strictly earlier than that existing pid's own `anchor_date` are
   real candidates for its top-K (a tighter per-pattern filter than
   the batch-level split) -- each qualifying candidate is compared
   against that pid's current worst cached slot; closer displaces, K
   stays fixed. No full corpus rescan of existing pids is needed:
   their old corpus is a strict subset of the new one (nothing is ever
   removed or redated), so the cached top-K merged with newly-
   qualifying candidates is exact, not an approximation -- same
   standard as Phase 2a's JIT byte-identity work, applied to admission
   logic instead of a kernel.
4. **K stays exact at `TOP_K_MATCHES=20` (config.py) -- no headroom
   (confirmed 2026-07-19, Tony).** The "displacement cascade" concern
   in the original STILL OPEN bullet doesn't actually occur under
   decision #3's admission logic: a new candidate is compared against
   the cache's current worst (20th-place) entry, closer evicts, O(K)
   per comparison -- not a cascade into wider recomputation. The real
   risk headroom would hedge against is `TOP_K_MATCHES` itself being
   raised later (e.g. to 25); a cache holding exactly 20 has nothing
   for ranks 21+ in that case regardless of whether it held headroom
   to 40 or not, since headroom only covers up to whatever number was
   guessed. That's already treated as a calibration-affecting event
   requiring re-validation (same class as `RISK_AVERSION_LAMBDA`
   changes) -- a full cache rebuild in that scenario is consistent
   with existing practice, not a new burden. Doubling storage
   indefinitely against a hypothetical future bump violates SIMPLICITY
   FIRST for a risk headroom doesn't actually retire.
5. **No `feature_set_id` column -- schema stands as originally
   drafted (confirmed 2026-07-19, Tony).** `composite_distance` is
   derived entirely from the DTW comparison over the 10 normalized
   features, already governed by `feature_set_id` on
   `pattern_instances`. A feature-version bump invalidates every
   cached distance at once, not selectively -- mixed old/new-version
   rows aren't comparable to each other, so per-row version tracking
   would let you detect staleness but never use a stale row anyway.
   Same rule as `baseline_5bar_v1` (architecture doc Section 9.1: "any
   later feature additions must be recorded as a new feature version
   ... preserves auditability"): the correct response to a version
   bump is the same one-time O(N^2) rebuild as the initial seed, not
   row-level bookkeeping for a state that's binary (whole cache valid
   or whole cache invalid). Final schema:
   `pattern_instance_id, rank, matched_pid, composite_distance`,
   PRIMARY KEY (pattern_instance_id, rank), both FK-reference
   `pattern_instances(pattern_instance_id)`.
6. **Migration mechanics: one atomic-move cycle covers both schema
   creation and the initial population, not two (confirmed 2026-07-19,
   Tony).** Copy live catalog to a temp path (same mechanism the
   pipeline already uses for `temp_working.db`); run
   `CREATE TABLE IF NOT EXISTS topk_cache (...)` against the copy
   (idempotent, safe to re-run if interrupted); run the SEQUENCING
   Step 1 tie-census + seed computation reading from that same copy
   (read-only queries against a static snapshot, nothing else writes
   to it mid-calculation), accumulate in memory, one bulk `executemany`
   INSERT at the end (same batch-insert shape as
   `insert_pattern_bars_batch`); verify table exists (sqlite_master
   introspection, same style as `stage_3c`'s `verify_catalog()`), all 7
   existing tables' row counts unchanged (zero-delta check, same
   row-count-snapshot mechanism `catalog_checkin` already uses),
   `topk_cache` row count = 20 x pattern count; `atomic_move()` the
   verified copy into place -- reused verbatim from
   `verify_ingestion.py`, not reimplemented. This differs from
   `stage_3*`'s pattern (those bootstrap a brand-new empty file with no
   existing data to protect, so they write directly) -- ours ALTERs a
   live 59MB catalog with 10,761 real patterns, so it goes through the
   same Lock + Temp-DB + Atomic Move discipline every other
   master-touching write already uses. One cycle instead of two means
   there is never a window where `pattern_instances` rows exist on the
   live catalog without their `topk_cache` rows -- the entire
   create-and-populate happens privately on the copy first.
7. **`catalog_writer.CATALOG_TABLES` grows to 8 -- `topk_cache` joins
   the canonical list (confirmed 2026-07-19, Tony).** Decision #6
   means the "always populated" guarantee holds continuously, not just
   at initial seed: decision #3's new-pattern top-K scoring runs inside
   BulkAddPattern's existing Lock + Temp-DB + Atomic-Move cycle (not as
   a separate follow-up job), so every future batch promote already has
   full `topk_cache` rows for its new patterns before going live.
   `topk_cache` is therefore a real 8th member of the canonical set,
   not an eventual-consistency table needing separate staleness
   semantics. Two concrete follow-ons: (a)
   `_check_no_hollow_instances()` in `verify_ingestion.py` needs a
   matching clause -- `pattern_instances` missing `topk_cache` rows is
   the same EC-027/EC-057 class of bug the existing check already
   guards `pattern_bars`/`forward_labels` against; `verify_ingestion.py`
   (MODIFY) added to this WO's Affects list, not treated as a silent
   gap. (b) WO-P300-E5.002's `expected_delta` computation for the
   promote path needs an explicit `topk_cache: 20 * B` entry (20 rows
   per new pattern) -- that's domain knowledge specific to this WO, not
   something E5.002 can derive on its own. Building E4.006 first, or
   the two together, makes more sense than E5.002 first.
8. **Live IntelliScan candidate matching is untouched by this WO
   (confirmed 2026-07-19, Tony).** Structurally, the cache cannot apply
   to live candidates: the table is keyed on `pattern_instance_id`, and
   a live candidate has none -- it isn't in the catalog, it's the thing
   being compared against the catalog. There is no row to look up. The
   live path stays exactly what it is today: a fresh full-corpus scan
   against history. `eval_scoring.py` appearing in Affects is about it
   being one physical file both the batch and live code paths live in
   (M-079 gate discipline applies to any change to that file regardless
   of which path it touches), not about shared cache state between the
   two paths -- there is none.
9. **Reuse-fraction gate and `IncrementalGuardrailError` fallback are
   removed, not kept alongside the new path (confirmed 2026-07-19,
   Tony -- found reading the real `application/incremental_post_
   batch.py` during plan-gate, not anticipated by decisions #1-#8).**
   `compute_reuse_fraction()` / `INCREMENTAL_MIN_REUSE_FRACTION` only
   made sense when there was a genuine "attempt the incremental path,
   or skip straight to full rescore" decision -- decision #1 already
   removed that decision (the cached path is unconditional, always
   scores new patterns fully). The old `IncrementalGuardrailError`
   fallback-to-full-rescore guarded `assemble_incremental_post_batch`'s
   own date-partition internal invariant, which no longer exists once
   that function is replaced. Both are vestigial and get deleted, not
   left dormant. In their place: a narrow, new guardrail for the
   cached path's real failure mode -- an exact tie found at the
   displacement boundary on a LATER batch (distinct from Step 1's
   one-time seed census, which only covers the initial state). That
   raises and propagates -- Finding 3's own rule is STOP and report,
   not a silent fallback, so this must not swallow into an automatic
   full-rescore either. `run_incremental_post_batch()` keeps its exact
   name and signature (M-082-adjacent minimal-impact reasoning:
   `ingest_mined_pipeline.py`'s call site at line 288 needs ZERO
   changes) -- only the function body changes, calling
   `eval_scoring.run_cached_post_batch` instead of the old
   assemble/fallback dance.
10. **The real integration point for decision #6's new-batch topk
    population and decision #7(b)'s expected_delta fix is
    `catalog_merge_pipeline.py`'s `promote_staging_to_live()` -- not
    `ingest_mined_pipeline.py` (confirmed 2026-07-19, Tony -- also
    found during plan-gate code-reading, correcting an earlier
    assumption).** `ingest_mined_pipeline.py` only calls
    `run_incremental_post_batch()` for the walk-forward eval REPORT --
    it never touches the live catalog and needs no changes at all for
    this WO (resolves the earlier headroom concern: that file is
    confirmed at exactly 300/300 lines, but it doesn't need editing).
    The actual `atomic_move()`-to-live promote is a separate, explicit,
    manually-triggered function, `promote_staging_to_live()` in
    `catalog_merge_pipeline.py` (197/300 lines, real headroom) -- and
    it currently calls `catalog_checkin(conn, pre_counts)` with NO
    `expected_delta` argument at all, meaning zero per-table
    validation happens on any live promote today. That gap is exactly
    what WO-P300-E5.002 exists to close. Since E5.002's fix and this
    WO's new-batch topk population are both edits to that same
    function, they are not just sequenced work, they are the SAME
    edit site -- building them separately risks a merge conflict
    there. Building them together, in one coordinated change to
    `promote_staging_to_live()`, is the plan. `catalog_merge_pipeline.py`
    (MODIFY) added to Affects; `ingest_mined_pipeline.py` explicitly
    NOT added -- confirmed no-touch, not an oversight.

## SEQUENCING (Step 1 does double duty, deliberately)

1. **Tie census + initial cache population, ONE combined ~63-min run.**
   Finding 3's precondition (zero exact ties at the top-K boundary
   across the FULL live catalog -- not the 150-pattern sample Phase 2b
   sampled) requires computing every pattern's real ranked distances.
   That's the exact same O(N^2) pass needed to seed the cache's initial
   state for all 10,761 existing patterns. One run gets both -- no
   reason to pay for it twice. If real ties are found: STOP, report
   back, no silent tiebreak fix (Finding 3's own rule).
2. Build storage + migration; PEH-verify schema creation against a
   COPY of live catalog.db first.
3. Build domain/topk_cache.py (admission logic) + eval_scoring.py's
   new orchestration, replacing the incremental path per the confirmed
   decision above.
4. Regression: run BOTH the old full-rescore path and the new
   incremental path on the same real batch, assert byte-identical
   results -- same byte-identity discipline as Phase 2a's JIT work.
5. Real-scale validation (comparable rigor to the M-079 gate) before
   this touches the live BulkAddPattern flow for real.
