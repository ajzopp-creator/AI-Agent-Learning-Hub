## WHY

While addressing CLAUDE.md staleness (Tony's request, 2026-09-19 P_020 session),
found the p020-project-context skill's canonical path table lists the Tracker
Dashboard under `F:\OneDrive\...`, flagged since 2026-08-09 as an unresolved
drift against `config.py`'s own hardcoded `D:\OneDrive\...`. Checked live:

- `HKCU:\Environment\OneDrive` (registry) = `D:\OneDrive`
- The Tracker Dashboard file exists at `D:\OneDrive\...`, not `F:\...`
- `config.py`'s hardcoded `D:\OneDrive\...` was correct all along; the
  skill's `F:\` entry was the wrong one.

Tony does not want a hardcoded drive letter as the permanent fix (a drive
letter is not durable -- OneDrive reconfiguration, a different machine,
etc.). The skill's own stated best practice was
`Path(os.environ["OneDrive"])` -- tested live: a script launched via
`Start-Process` through the windows-mcp relay (the Hub's own standard
execution pattern, Protocol C) sees `os.environ.get("OneDrive")` as
`None`, even though the registry value is set. Root cause is standard
Windows process-creation behavior, not a bug specific to this project: a
child process only inherits the environment its parent had at creation
time; changes made to `HKCU\Environment` after that point (including by
the OneDrive client, which sets this key post-logon) are not visible to
that process or anything it spawns until it restarts. Any process in a
lineage that started before OneDrive's client set the value -- an MCP
relay process, a scheduled task, a service -- will not see it. This is a
well-documented class of Windows behavior (Microsoft's own "Old New
Thing" engineering blog covers the general mechanism), not unique to
OneDrive, but OneDrive's env var is one of the most commonly-hit
real-world examples of it.

The registry itself is always current regardless of process lineage, so
reading it directly at call time is the correct fix -- not the env var,
and not a hardcoded literal.

## FIX

`config.py` gets a new `get_onedrive_root() -> Path` function: reads
`HKCU\Environment\OneDrive` via `winreg` at call time, falls back to the
last-known `D:\OneDrive` with a logged warning only if the registry read
itself fails (key missing, permissions, etc.) -- never silently wrong.
`TRACKER_DASHBOARD` is built from `get_onedrive_root()` instead of a
hardcoded string.
