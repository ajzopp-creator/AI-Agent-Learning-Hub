## FOUND LIVE -- 2026-08-12

Every `.base` file in `trading_journal\Bases\` (checked via
`obsidian_get_file_contents`, reading the raw YAML rather than trusting the
rendered UI) uses a top-level block shaped like this:

```yaml
filter:
  conditions:
    - field: file.folder
      operator: contains
      value: TradeOrderManagement/P400
  conjunction: and
sort:
  - field: run_date
    direction: desc
columns:
  - id: run_date
    field: run_date
```

**None of `filter:` (singular), `conditions:`, `field:`, `operator:`,
`value:`, `conjunction:`, or top-level `columns:`/`sort:` are real Obsidian
Bases schema keys.** Confirmed against the official spec
(`help.obsidian.md/bases/syntax`, `help.obsidian.md/bases/functions`). Real
Bases syntax uses `filters:` (plural) containing `and`/`or`/`not` lists of
function-call expression strings (e.g. `file.inFolder("path")`), and
per-view `order`/`sort` blocks under `views:`.

**Effect:** the Bases plugin silently ignores the entire fabricated `filter`
block -- no error, no warning, just treats the base as unfiltered. Every
base has been rendering the **entire vault** (P400_Trades showed 3,002
results before the fix; correct scoped result is 405) since creation. This
predates and is independent of WO-P800-E3.003's 2026-07-25 vault rename --
that rename's "dead path" framing (in WO-P400-E6.001 and the P_400/P_020
skill files) was itself wrong: the path was never being evaluated at all,
correct or not.

The only part of these files that ever worked is the `views[].sort` block
using `property`/`direction` keys -- that syntax happens to be valid, which
is why P400_Trades rendered sorted by file name (a leftover/default) instead
of showing no sort behavior at all. This partial validity masked the larger
defect -- the base clearly did *something*, just not the right thing.

## FIX PATTERN (proven, applied to all 6)

```yaml
filters:
  and:
    - file.inFolder("ACTUAL/FOLDER/PATH")
properties:
  field_name:
    displayName: Display Name
  # ... one entry per column, cosmetic only
views:
  - type: table
    name: Table
    order:
      - field_name
      # ... same fields, display order
    sort:
      - property: field_name
        direction: DESC
```

`file.inFolder()` is recursive by design (matches the named folder and all
sub-folders) -- confirmed against the official function reference, no
separate handling needed for nested archive folders.

`P300_Signals.base` kept its existing view-level `filters` block as-is (it
was already valid, real syntax) -- the top-level `filters: {and:
[file.inFolder("TradeOrderManagement/P300")]}` block was added above it;
global and view filters concatenate with AND per the spec, adding folder
scoping without touching the working WATCH-signal logic.

`Open_Positions.base` doesn't filter on a folder path -- it filters on
`lifecycle_status`/`traded`/`outcome` properties with an OR/AND nest. Not
covered by the proven `file.inFolder()` pattern; treat as the least-verified
of the six until Tony confirms row count live.

## VERIFICATION METHOD (for all 6, and any future Bases work)

Do not trust the rendered UI result count alone as evidence of a working
filter -- an unfiltered base and a correctly-filtered one can both render
without error. Read the raw YAML via `obsidian_get_file_contents` (or disk)
and check it against `help.obsidian.md/bases/syntax` before and after any
edit. After writing, re-open/reload the base in the Obsidian app and get a
human (Tony) to confirm the row count matches the underlying folder's known
file count.
