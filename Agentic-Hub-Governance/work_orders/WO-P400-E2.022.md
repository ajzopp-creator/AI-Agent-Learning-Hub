# WO-P400-E2.022 -- RISK Gate Can Read a Record This Same evaluate Run Is About to Overwrite

**Status:** CLOSED
**Owner:** P_400
**Affects:** none -- internal P_400 only
**Depends On:** None
**Acks:** N/A

## WHY

Live on WMT, 2026-07-14 (options-path IV-scaling fix verification
session): a single `evaluate WMT --options` run wrote its own vault
record twice in sequence -- version 2 (`BUY`/`PENDING`, from the
corrected-IV options council pass) immediately followed by version 3
(`PASS`/`DROPPED`, from a stock-level RISK POSITION_COUNT block).

Between those two writes, `portfolio.py`'s open-position count read
WMT's own version-2 record (still `PENDING`, from earlier in the same
`evaluate` call) off disk, counted it as the 8th open slot, and blocked
WMT against a stale copy of itself. The block was real in the sense
that RISK's gate fired correctly on the data it read -- but that data
was this run's own not-yet-final intermediate write, not a genuinely
separate open position.

Confirmed on disk same day: current true state is 7/8 open positions
(HAL, ICE, MSTR, VTR, BAM, CRPT, BP -- all in portfolio.py's
OPEN_STATUSES). WMT's version-3 overwrite self-corrected the count back
to 7/8 immediately after, so no manual cleanup was needed -- but the
transient self-block happened, and the mechanism that produced it is a
real ordering question, not just a one-off data artifact.

## Root Question

Should `evaluate`'s options/spread path write an interim vault record
(options-council-only verdict) *before* the full stock+portfolio Council
gates have run and produced the final combined verdict? Two candidate
directions, not yet investigated:

(a) The interim write is unintentional -- `evaluate_options()` /
    `write_options_eval_record()` should only fire once, after the
    stock-level RISK/QUANT/MACRO/TAPE gates are known, not as a
    mid-pipeline side effect that a later gate can then read back.
(b) The interim write is intentional (options council result is
    genuinely independent and worth recording even if the stock-level
    portfolio gates haven't run yet), in which case portfolio.py's
    position-count read should exclude the record currently being
    written by the in-flight evaluate call for the same symbol --
    i.e. a symbol should never be able to count against its own
    still-running evaluation.

## Scope

- Trace `cmd_evaluate`'s call order in `commands.py`: confirm exactly
  when `write_options_eval_record()` fires relative to the plain-stock
  `evaluate_signal()` call and its RISK gate read of `load_book()`.
- Determine which of (a)/(b) above is the right fix, or a third option
  if the trace reveals something neither anticipated.
- Fix without changing council.py's block logic itself (RISK's
  POSITION_COUNT threshold and OPEN_STATUSES set are correct as
  written -- this is a sequencing bug, not a threshold bug).

## Out of Scope

- Any change to OPEN_STATUSES, MAX_CONCURRENT_POSITIONS, or the
  heat/count math itself.
- WO-P400-E2.019 (paper/real book routing) -- unrelated, still open.
- WO-P400-E2.021 (drop_reason) -- unrelated, closed.

## Execution (2026-07-14, same session)

Root cause traced fully -- two independent bugs stacked, both P_400-owned:

1. `evaluate_options()`/`evaluate_spread()` never checked whether the
   stock-level `result.verdict` (already computed earlier in the same
   `cmd_evaluate` call, including RISK/QUANT/MACRO/TAPE) was BLOCKED --
   `_build_options_fields()`/`_build_spread_fields()` in record_writer.py
   only looked at the options/spread council's own verdict. A clean
   options/spread pass could write APPROVED to the vault even when the
   stock-level Council had already blocked.
2. `cmd_evaluate`'s trailing blanket
   `if result.verdict == "BLOCKED": write_p400_record(...)` fired
   unconditionally, AFTER the options/spread branch's own write --
   silently clobbering every option_*/spread_* field any time that
   combination occurred. Not a one-off -- default behavior any time an
   options/spread run's stock-level Council blocked.

## Fix

| File | Change | Lines |
|---|---|---|
| infrastructure\record_writer.py | `_build_options_fields()` / `_build_spread_fields()`: final verdict forced to BLOCKED (drop_reason=COUNCIL_BLOCK) when `stock_result.verdict == "BLOCKED"`, regardless of the options/spread council's own result | 234 (was ~211) |
| application\commands.py | Trailing blanket BLOCKED write gated `and not spread and not options` -- only fires on the plain stock-only path now | 281 (was 272) |
| test_record_writer.py | Split -- crossed 300 lines after adding 2 new tests (325). Trimmed to base write_p400_record tests only | 150 (was ~211) |
| test_record_writer_derived.py (new) | Options/spread field-builder tests moved here (9 existing + 2 new): `test_options_stock_blocked_overrides_clean_options_pass`, `test_spread_stock_blocked_overrides_clean_spread_pass` | 247 |
| test_commands.py | +1 test: `test_options_blocked_run_writes_record_exactly_once` -- counts real `write_p400_record` calls end-to-end through `cmd_evaluate` with `--options` set, asserts exactly 1 (not 2), asserts that write reflects BLOCKED/COUNCIL_BLOCK not the clean options PASS | 163 (was 102) |

Also: `make_stock_result()` fixture (both test files) gained a
`verdict="APPROVED"` default param, preserving all ~13 pre-existing
call sites with no args.
