DESIGN REQUIREMENT -- MUST PARAMETERIZE, NOT HARDCODE
--------------------------------------------------------------------------------
As offered, the script hardcodes the P_300 folder as the launch target. This
defeats the premise of a "general utility" -- a Hub-wide launcher that only
ever opens one project isn't general, it's a P_300 launcher with a generic
name. Fix: target project is a parameter (command-line arg, or a small config
value read at launch), defaulting to Hub root (P_000's own context) if no
argument given -- see OPEN DECISIONS item 3 for the reasoning. Landing
directly in P_010, P_115, P_400, etc. must be a one-line parameter change,
not a rewrite.

FUNCTIONAL SPEC (as offered by P_300 session, pending Tony confirmation)
--------------------------------------------------------------------------------
1. Runs at Windows sign-in via a shell:startup shortcut (RESOLVED -- see
   OPEN DECISIONS item 2).
2. Launches Chrome.
3. Drops into claude --chrome scoped to the target project folder
   (parameterized per above; default is Hub root, NOT P_300 -- see OPEN
   DECISIONS item 3).
4. /login and /chrome are also automated by this launcher -- NOTHING manual
   at morning startup (Tony decision, 2026-08-10). Script must programmatically
   send /login then /chrome into the claude --chrome session after launch, not
   just open the window and wait for keystrokes. Needs investigation: whether
   claude --chrome accepts piped/scripted stdin input for slash commands, or
   whether this requires SendKeys-style keystroke injection via PowerShell/
   AutoHotkey after a launch-detection delay. Flag as the primary technical
   risk of this WO -- if slash commands cannot be reliably scripted, escalate
   back to Tony with findings before falling back to a partial-manual design.

FINDING: no verification step exists, anywhere, confirming a per-action-
triggered skill (a skill meant to fire before every occurrence of some action,
not once at session start) is actually current in a Claude session's live
practice versus what's on disk.

Concrete case: peh-handoff v1.7 (WO-P000-E15.001, 2026-08-09) moved the
default file-write remedy from PowerShell-command-string embedding to a
direct-write tool, specifically because command-string embedding was the
confirmed root cause of three corrupted files in one session (2026-08-05).
A P_400 session on 2026-08-10 (WO-P400-E5.005) used the old, superseded
method for an entire session of file writes -- including reintroducing the
exact escape-sequence-corruption failure class the v1.7 fix exists to
prevent (a skill-file docstring corrupted via backtick+letter misread as a
PowerShell escape). Caught only because Tony independently ran the test
suite and got a SyntaxError; not caught by anything in the session itself.

WHY: p400-project-context (session-start-triggered: "load at the start of
ANY session involving P_400 work") gets read every session because INIT is
one concrete moment every session hits. peh-handoff (per-action-triggered:
"before any Windows-MCP call expected to produce a file") has no equivalent
enforcement point -- it depends entirely on the session correctly
self-invoking it before the first of potentially dozens of file-writing
calls, with no gate, checklist, or INIT step confirming that happened, and
no check for whether the invoking session's own memory/recall of the skill's
content is current versus stale.

NOT PROPOSING A SPECIFIC FIX -- P_000's call, not this session's. Two shapes
worth considering, not a recommendation:
1. INIT-time fresh-read of any skill whose own trigger text is per-action
   rather than session-level (peh-handoff is the known instance; worth an
   audit for others written the same way) -- answers "is this current"
   once, visibly, before work starts, rather than never.
2. Some structural gate on Windows-MCP file-writing tool calls themselves,
   analogous to how the computer_use skill-check reflex is wired for
   Linux-sandbox file creation (docx/pptx/etc.) but is not currently wired
   for Windows-MCP calls at all -- this may be the deeper gap: session-start
   skill loading and the "check skill before writing a file" reflex are two
   separate mechanisms, and only the first one reliably fires here.

Cost: Tony's own words -- "this cost me tokens and my time which I find
valuable." A real syntax break, caught externally, on a Hub-governance file,
by a rule that had already been written down once specifically to prevent
this class of failure.
