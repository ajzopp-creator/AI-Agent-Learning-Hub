## WHY

Live BLOCKED records written 2026-07-14 (CCI, TS -- both MACRO earnings-
in-window vetoes, evaluate command) have `why_code: null`, `sig_code:
null`, and `drop_reason: null` in vault frontmatter. Architecture v2.0
Section 4.9 (Council Narrative Templates) and Section 6.5 (Entry
Resolution Rule) both assume a populated reason code travels with a
BLOCKED/DROPPED record for audit purposes -- P_020 correlates outcomes
against these. Confirmed on disk:

  trading_journal\TradeManagement\P400\2026-07-10_CCI.md
  trading_journal\TradeManagement\P400\2026-07-10_TS.md

Both show `council_verdict: BLOCKED`, `lifecycle_status: DROPPED`,
`why_code: null`, `sig_code: null`, `drop_reason: null`.

Not yet confirmed whether this is:
(a) council.py never populates these fields on a MACRO block specifically
    (vs. QUANT/RISK/TAPE blocks, which may set them correctly), or
(b) record_writer.py drops them on write regardless of what council.py
    returns, or
(c) the fields were never wired end-to-end since WO-P400-E2.001 and this
    is the first live MACRO-blocked record to expose it.

## Investigation (2026-07-14, same session)

Root cause found, and the WHY narrower than the three-way (a)/(b)/(c)
guess in the original filing:

**why_code / sig_code -- not a P_400 bug.** Confirmed in
`obsidian_writers\domain\vault_schemas.py`: both fields are commented
`# P_020 WHY vocabulary` / `# P_020 SIG vocabulary` -- a cross-project
taxonomy P_020 owns for correlating outcomes across P_115/P_300/P_400
uniformly. P_400 was never wired to map its own `RC_*` council codes
into that vocabulary. Real gap, but not fixable from the P_400 side
without P_020's vocabulary definition first. Descoped from this WO --
left null by design until a separate cross-project WO defines the
mapping (not opened yet; ask Tony if wanted).

**drop_reason -- confirmed P_400 bug, narrow.** `record_writer.py`'s
options and spread paths (`_build_options_fields`, `_build_spread_fields`)
both already set `drop_reason="COUNCIL_BLOCK"` correctly on a block. The
plain-stock BLOCKED write call in `commands.py`'s `cmd_evaluate` simply
never passed `drop_reason` at all -- defaulted to `None` on every stock
BLOCKED verdict since the call site was first written. Not a
council.py issue -- `council.py` already populates `block_codes`
correctly for every role including MACRO; the gap was purely in the
write call site.

## Fix (2026-07-14)

One line: added `drop_reason="COUNCIL_BLOCK"` to the stock-path
`write_p400_record()` call in `application\commands.py`, matching the
already-correct options/spread convention.
