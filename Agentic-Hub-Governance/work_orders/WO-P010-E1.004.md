## WHY

2026-08-28 session: `P_010_RiskConfig.json` showed `spy_grid_date`/`qqq_grid_date`/
`vxx_grid_date` of 08/25/2026 while the morning script was running on Friday 08/28.
VantagePoint had not overwritten the History Grid exports for two trading nights
(Wed 8/26, Thu 8/27 -- confirmed via `LastWriteTime` on the xlsx files, which matched
the internal grid_date exactly: 8/25/2026 6:23-6:25 PM). `P_010_daily_posture_v5.py`
ran successfully both mornings, wrote a clean `RiskConfig.json` with today's timestamp,
and `risk_mode`/`avg_posture` were silently computed off 3-day-old grid data for two
full trading days. Caught only by Tony manually eyeballing grid_date against the
calendar -- no automated check exists for this failure class.

`staleness_check.py` deliberately keys off RiskConfig's `timestamp` (did the script
run today), never `grid_date`, specifically because grid_date is expected to lag over
weekends. That same design choice is the blind spot: it proves the script ran, not
that the data it ran on was fresh.

## PROBLEM

- VantagePoint exports the night before for next-day use -- grid_date is EXPECTED
  to be "yesterday" (or last Friday on a Monday run), never today.
- Nothing compares grid_date to that expected value. The morning script reads
  whatever's on disk and proceeds regardless of age.
- No holiday calendar exists anywhere in the Hub (confirmed by staleness_check.py's
  own weekend-only carve-out). A naive Mon-Fri "expected = yesterday" rule will
  false-positive on the trading day after a market holiday, when grid_date
  legitimately lags 2 calendar days.

## PROPOSED FIX (not yet built -- needs Tony sign-off on approach)

**Recommendation:** extend `P_010_daily_posture_v5.py` with a grid-freshness check,
reusing the existing `MORNING_RUN_FAILED.flag` + `toast_notify.py` fail-loud
infrastructure from E1.003 rather than building new machinery -- no changes needed
to the `.bat`, Guardian, or any downstream consumer, since they already check for
that flag's existence.

1. New module `grid_freshness_check.py` (~50 lines, same split-file pattern as
   `intraday_risk_logic.py` / `note_*.py`):
   - `expected_trading_day(today)` -- today minus 1 day, or last Friday if today
     is Monday. Weekend-only logic, no holiday calendar (see scoping decision below).
   - `check_grid_freshness(spy_grid_date, qqq_grid_date, vxx_grid_date, today)` --
     returns stale flag + which symbol(s) are behind.
2. Call it in `P_010_daily_posture_v5.py` right after grid dates are parsed. On
   stale=True: write `MORNING_RUN_FAILED.flag` (message distinguishes "STALE GRID
   DATA" from an exception) and fire `toast_notify.py` -- same halt-before-STEP-2
   behavior E1.003 already built.
3. `RiskConfig.json` still gets written (consistent with existing
   `MORNING_RUN_FAILED` behavior) so the stale data is visible for diagnosis, but
   the note writer does not run against it.

**Scoping decision -- SIGNED OFF 2026-08-29 by Tony:** accept the holiday false-positive rate
(~9 US market holidays/year -- each produces one unnecessary toast + halt the next
trading morning, cleared by Tony in seconds) rather than build/maintain a holiday
calendar now. Matches existing staleness_check.py precedent and keeps the fix small.
Flag if a holiday calendar should be built instead.
