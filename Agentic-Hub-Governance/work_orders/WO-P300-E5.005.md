## WHY

Current state, confirmed real via this session's own review of the
2026-07-25 BulkAddPattern run: `P_300_RunBulkAddPattern.ps1` mines, audits,
stages, and archives automatically, then stops -- printing both walk-forward
report paths and the exact `ingest-mined --promote <path>` command, waiting
for Tony to run it by hand. M-108 already documents that Tony's real practice
is "audit gate clean -> promote directly, I do not eval manually" -- the
manual walk-forward review step the WO's own Acceptance Criteria describes
has never actually been Tony's workflow. This WO proposes closing that gap
the other direction: instead of correcting the WO text to match a practice
that skips the eval entirely, make the SCRIPT itself run the same eval-based
check the walk-forward report already computes, and only stop for Tony when
that check itself flags something -- otherwise promote automatically in the
same run.

**Real precedent this must not regress:** WO-P300-E2.003 (2026-07-10). Merging
495 STRICT bulk patterns into the then-live pool dropped walk-forward BUY win
rate 68.8% -> 63.6% (a real, meaningful precision hit) while nearly doubling
BUY volume. The staging-eval-before-promote gate is what caught it -- promotion
was correctly withheld. Any auto-promote design must preserve this gate's
ability to block a promote that real data says would hurt, not just skip
the step that happened to catch it that one time.

---

## PROPOSED DESIGN (for Tony's approval -- not built)

After `ingest-mined` (staging) produces its own walk-forward report, the
script would additionally parse BOTH walk-forward reports (pre vs. staging,
already generated by the existing M-079 machinery) and auto-promote only if
ALL of the following hold; otherwise it stops exactly like today (print both
report paths + the manual promote command, no change to that fallback path):

- **Audit gate:** already 100% enforced before this point (ingest-mined's own
  build step) -- no change, just confirming it's a precondition, not new.
- **BUY precision:** staging's BUY accuracy does not drop more than
  **3 percentage points** vs. the pre-batch baseline. (E2.003's real regression
  was a 5.2pp drop -- 3pp gives real margin below the only confirmed real
  incident this gate exists to catch, without being so tight it blocks
  ordinary noise on small batches.)
- **PASS accuracy:** does not drop more than 3pp (same threshold, same
  rationale -- PASS accuracy degrading means the corpus is getting worse at
  correctly rejecting non-setups, not just less precise on BUY).
- **BUY volume shift:** flagged (not auto-blocked, just surfaced in the stop
  message) if BUY count changes by more than 50% -- informational, matching
  E2.003's own "nearly doubled BUY volume" as part of what made that regression
  worth stopping for, without making volume itself a hard gate (volume swings
  are expected and not inherently bad).

**This is a recommendation, not a final number** -- the 3pp threshold is
proposed specifically because it sits below the one real regression this
project has actually measured (5.2pp) with margin, but it has not been
back-tested against every prior batch. Tony's call before this gets built:
confirm 3pp, or set a different number.

**Explicitly NOT changing:** the audit gate itself, the M-079 staging-eval
mechanism, the Lock+Temp-DB+Atomic-Move promote protocol, or the manual-promote
fallback path (stays available/required whenever the auto-check doesn't
clear).

## MEASURED BASELINE -- 2026-07-28, real numbers, PEH-verified

Parsed today's walk-forward report pair (read-only PEH run, exit 0):
  PRE = `walkforward_072526catalog_default_20260728_062718.txt`
  STG = `walkforward_staging_ingest_mined_default_20260728_075803.txt`

| Class | Pre | Staging | Delta | n |
| :---- | :---- | :---- | :---- | :---- |
| BUY | 69.11% | 69.05% | **-0.06pp** | 6983 -> 9260 |
| PASS | 61.29% | 62.63% | **+1.34pp** | 6593 -> 7741 |
| WATCH | ungraded | ungraded | n/a | 3225 -> 4246 |

**Today's batch PASSES the gate being built here.** BUY -0.06pp against a
3pp bar; PASS improved. BUY volume +32.6%, under the 50% informational flag.

**Report format -- verified, NOT as originally assumed.** The reports are
TSV `.txt`, not markdown, and contain **no summary block**. One row per
(pattern x horizon), ~106k rows, ~10MB. `correctness` is populated ONLY on
the `is_chosen_horizon=True` row. The gate must aggregate these itself.

**Full `correctness` enum -- observed, not guessed (5 values):**
`correct_buy`, `false_positive`, `correct_pass`, `missed`, `neutral`.

**Class mapping, arithmetic verified exact in both files:**

| Class | Correct | Incorrect | Check |
| :---- | :---- | :---- | :---- |
| BUY | `correct_buy` | `false_positive` | 6394 + 2866 = 9260 |
| PASS | `correct_pass` | `missed` | 4848 + 2893 = 7741 |
| WATCH | -- | -- | `neutral` = 4246, ungraded |

Class totals sum to 21,247 chosen-horizon rows exactly.

**Design defect caught BEFORE it was written:** the first parser sketch
scored correctness via `startswith("correct_")`. That yields WATCH n=3225,
correct=0, rate 0.00% -- a permanently-zero metric that reads as a finding
about WATCH rather than a bug. WATCH rows carry `neutral`, which is not
graded right or wrong at all. **The parser MUST use explicit per-class
mapping and MUST exclude WATCH from accuracy entirely rather than scoring
it.** The gate thresholds BUY and PASS only.

**Caveat on interpreting these deltas:** they are whole-corpus comparisons
and CANNOT be decomposed into "how did the new patterns do." Adding to the
corpus re-runs top-K for pre-existing patterns too, so some existing signals
flip. That is precisely the mechanism that made E2.003 a real regression,
and it is why the gate compares corpora rather than cohorts. Do not "improve"
this later by scoring only the new cohort.
