# WO-P300-E5.002 -- Fold Bulk-Merge Promote Through verify_and_promote()

**Status:** PENDING (not planned, not built)
**Owner:** P_300
**Affects:** application/catalog_merge_pipeline.py (promote_staging_to_live),
  application/ingest_mined_pipeline.py (uses the same promote pattern for
  the BulkAddPattern path) -- likely 2 files at minimum. No domain/
  infrastructure changes expected; infrastructure/verify_ingestion.py's
  verify_and_promote() already exists and should be reused, not rewritten.
**Depends On:** None.
**Acks:** N/A

---

## WHY

Filed 2026-07-19, prompted by Tony directly questioning why the
single-pattern AddPattern promote path and the bulk-merge promote path
don't share the same verification logic. Checked, not assumed -- they
genuinely don't:

- `infrastructure/verify_ingestion.py`'s `verify_and_promote()` (used
  by every single-pattern write) runs `verify_temp_db()` first: a
  per-table expected-delta check AND a hollow-record scan (patterns
  missing pattern_bars or forward_labels -- the EC-027/EC-057
  tripwire). Only promotes on a clean pass; leaves temp in place and
  master untouched on any failure.
- `application/catalog_merge_pipeline.py`'s `promote_staging_to_live()`
  (the bulk-merge path, used by both the STRICT-tier merge and
  BulkAddPattern's ingest-mined flow) does NEITHER check. It calls
  `catalog_checkout()` / `catalog_checkin()` for informational
  before/after row-count logging only -- no `expected_delta` is ever
  passed to `catalog_checkin()`, so nothing is actually enforced. It
  reuses `atomic_move()` from verify_ingestion.py (the safe part --
  backup + atomic rename), but skips the verification wrapper around
  it entirely.

Nothing in the code or changelog history (catalog_merge_pipeline.py
v1.0 2026-07-10, v1.1 2026-07-14) suggests this split was a deliberate
design choice -- it reads as catalog_merge_pipeline.py being built
later, reusing only the low-level atomic_move() primitive, and
reimplementing a lighter pre/post snapshot instead of computing a real
`expected_delta` from the merge summary and calling the existing
`verify_and_promote()` wholesale. Same shape as M-082 (duplicate logic
diverging across rewrites), one layer up -- at the write-protocol
level instead of the DTW-math level.

**Closed for one specific promote already (2026-07-19, staging_
ingest_mined.db -> live, 1792 new patterns):** a one-off script
computed a real `expected_delta` from actual config constants (new
pattern count x BULK_WINDOW_LENGTH x len(FORWARD_HORIZONS)) and called
the real `verify_temp_db()` before calling `promote_staging_to_live()`
-- verified clean, promote succeeded. That was a manual, one-time
workaround for this WO's gap, not a fix to the gap itself. The next
bulk promote (or a future session that doesn't remember to do this
manual step) gets the unverified path again unless this WO is done.

## SCOPE NOTE -- explicitly NOT decided yet

- Whether `promote_staging_to_live()` should call `verify_and_promote()`
  directly (cleanest, but verify_and_promote()'s signature currently
  assumes a single temp_path/master_path pair with an expected_delta
  the CALLER must already know -- bulk merge's caller (ingest_mined_
  pipeline.py / catalog_merge_pipeline.py's own build_staging_merge())
  would need to compute that delta from its own MergeResult/
  IngestMinedResult summary (inserted_count, and per-pattern bar/label
  counts which are currently NOT tallied anywhere in those summaries --
  may need a small summary-field addition) -- or whether a shared
  lower-level verify helper gets extracted that both single-pattern and
  bulk paths call, with each caller supplying its own expected_delta.
  Not decided -- first step below is to actually look at both callers'
  data before picking an approach.
- Whether the hollow-record scan alone (assumption-free, no
  expected_delta needed) should be split out and made cheap+automatic
  in promote_staging_to_live() even before the fuller expected-delta
  fold is designed -- a smaller, faster partial fix. Worth considering
  as a first increment rather than waiting for the full fold.
