## WHY

Surfaced as a side effect of WO-P400-E6.001 (P_400/Obsidian performance-data
research). Tony asked to audit every step of paper vs. live ingestion; that
audit required reading the actual paper-side matching code rather than
assuming it matched the live-side `exit_allocator.py` logic. It didn't.

## FOUND LIVE -- 2026-08-11

`P_020_AccountParser.bat` -- the batch file Tony actually runs -- called
`python\parsers\P_020_TOS_Parser_v2.3.py`. WO-P020-E1.002 (2026-07-26,
still open) had already investigated this exact folder and stated
explicitly: *"Confirmed affected file: `P_020_TOS_Parser_v2.4.py` -- this
is the live/active parser... Do not confuse with the several
older/archived copies... `P_020_TOS_Parser_v2.3.py` -- none of these are
live."* That finding was correct about which file *should* be live, but
nobody had gone back and checked whether the batch runner actually
pointed at it. It didn't -- confirmed directly with Tony this session
before touching anything (asked which one he actually runs, rather than
guess between two conflicting pieces of evidence).

**The bug this exposed Tony to, every paper import, for however long the
bat has pointed at v2.3:** `match_entries_exits()` in v2.3 recomputes
`potential_exits` fresh from the *entire* exits DataFrame (filtered only
by `date >= entry's own date`) independently inside each entry's loop.
There is no shared state tracking which SOLD rows a sibling entry already
consumed. Two entries on the same symbol opened close together can both
attach the *same* exit transaction to themselves -- double-counted
realized P&L, not merely a starved sibling left open (that was my first,
also-wrong guess before reading the actual code -- corrected mid-session).

v2.4 (dated 2026-07-05, newer than v2.3) replaced this entirely with a
single chronological pass over one shared `long_book`/`short_book`
ledger per symbol+type. An exit transaction is popped from the book
exactly once as it's processed -- double-counting is structurally
impossible, not just less likely.

## FIX APPLIED

- `P_020_AccountParser.bat`: `P_020_TOS_Parser_v2.3.py` ->
  `P_020_TOS_Parser_v2.4.py`.
- `test_p020_known_bugs.py`: two new tests --
  - `test_v24_no_sibling_double_exit` (BEHAVIOR) -- 2 sibling stock
    entries, qty 2 each, one SOLD of qty 2. Asserts total exit qty
    recorded across all positions equals 2 (the real fill), not 4
    (what v2.3's logic would have produced), and that exactly one
    position remains open.
  - `test_accountparser_bat_points_at_v24` (SOURCE) -- greps the bat
    file for `v2.4.py` present / `v2.3.py` absent, so this can't
    silently regress again the way it did the first time.
- Bug row + fix added to `p020-project-context` SKILL.md's Bugs Already
  Fixed table.

Full suite run after the change: 14/14 passing (12 pre-existing + 2 new),
zero regressions.

## HISTORICAL AUDIT -- 2026-08-11 (same session, Tony asked "go look")

**How far back:** `git --no-pager log --follow` on `P_020_AccountParser.bat`
shows exactly one commit, ever -- `18d9487` 2026-06-06 "Initial commit -
full Hub backup before P800 cleanup" -- already pointing at v2.3 at that
point. `P_020_TOS_Parser_v2.4.py` itself wasn't created until 2026-07-05,
a month later, so the runner could not have been updated to match it
since that file existed. Exposure window: at least 2026-06-06 through
this session, possibly earlier (predates git tracking on this repo).

**Whether any real trade was actually corrupted:** checked. All 58
`trades` rows with `source='tos_paper_csv'` (the only source this bug
can reach), spanning 2026-05-15 to 2026-07-24 -- the full window, since
every one of them was necessarily produced by v2.3 per the git finding
above.

- Query for the bug's exact fingerprint (same underlying_symbol +
  asset_type + exit_date + exit_price + qty_exited attached to more than
  one distinct trade_id): **0 matches.**
- 5 symbol+asset_type groups had 2+ entries (the only shape where this
  bug is even possible): ABM, ADM, DECK, NBIX, RL. Pulled full trade+exit
  detail for all 5 and checked by hand, not just the query. ABM and DECK
  each show a same-day, same-price close-then-reopen (one position's exit
  price exactly equals the next position's entry price, same date) --
  looks suspicious at a glance but isn't the bug: that's the ordinary
  signature of closing a position and re-entering at the market price a
  moment later, and neither reopened position has any exit attached. ADM,
  NBIX, RL have cleanly separated dates/prices between siblings, no
  overlap.

**Conclusion:** the bug was live in the code for the entire window, but
none of Tony's actual paper trades happened to hit the specific
precondition (an exit transaction landing inside two siblings' eligible
date windows at once) -- in every real case the exits were sequential
enough that this didn't occur. No paper P&L correction needed. This
closes the "separate call if you want it looked at" item from the
original write-up below.
