## WHY

P_400's `evaluate`/`spec`/`compare` require a manual `--cash` flag on every run.
Tony's explicit call (2026-07-25, P_400 session): keep it manual -- cash is a
deliberate per-trade decision, not something P_400 should auto-read from the
broker (architecture doc Section 3.3, "cash is per-trade, not tracked").

Right now the only way to know the real numbers before typing `--cash` is to
check the Schwab app/TOS by hand. P_020's `database\infrastructure\schwab_balance_pull.py`
already pulls both `cashAvailableForTrading` and `buyingPower` from
`securitiesAccount.currentBalances` on every balance-pull run (`pull_balance()`
already returns both, `store_balance()` already writes both into the
`account_balances` SQLite table) -- but neither value is surfaced anywhere
Tony can glance at quickly. This WO doesn't add a new Schwab API call; it
surfaces data already being pulled.

## SCOPE

1. Extend the existing balance-pull invocation (`database\application\account_commands.py`,
   or wherever the weekly job calls it) so that, after `store_balance()` writes
   the SQLite snapshot, it also writes two new rows into
   `projects\P_000_PythonClaudeLocalLLM\config\P_000_Account_Parameters_Current.md`'s
   "Active Parameters" table: "Buying Power" and "Cash Available for Trading" --
   same `pull_balance()` return dict already in hand, no new API surface area.
2. `P_000_Account_Parameters_Current.md`: two new rows in Active Parameters,
   plus a one-line note under "Critical Rules > Cash Balance (Separate Concept)"
   clarifying these are broker-reported reference numbers only -- P_400's
   `--cash` stays a manual figure Tony types himself, never auto-read from
   these fields.
3. No P_400 code changes. `params_reader.py` does not need to parse these two
   new fields unless/until Tony later wants automatic `--cash` (explicitly
   out of scope this WO).
