# WO-P300-E1.002 -- Target Generation Violates Architecture 3.5 (VP Resistance Available But Not Used)

**Status:** OWNER_DONE
**Owner:** P_300
**Affects:** P_400 (Tier-1 R:R gate non-functional as a filter; full dossier required on every signal)
**Depends On:** None
**Acks:** N/A

---

## WHY

Architecture v2.0 Section 3.5 (Target Selection Standard) states standard setups
use resistance-based targets. The Confluence-Based Target Framework (ATR extension,
round-number alignment, measured move, prior structure) is reserved for
price-discovery setups -- defined as having no visible overhead resistance.

Current P_300 implementation does not branch on this. Across multiple sessions
(2026-06-14 full batch of 58 signals, 2026-06-17 batch of 10 signals),
guideline_target is computed unconditionally as entry + 2x risk (= entry + 2x ATR),
regardless of whether a VP-derived resistance level is present in the same packet.

This is not a missing-data edge case. We already decided the standard: use the
VP-derived resistance level first; fall back to the 2x ATR extension only when
no VP resistance level is available. P_300's current code skips the VP-first
branch entirely.

**Evidence -- AG, 2026-06-17:**
  Packet carries intelliscan_support_2 = 21.27, sourced from the VantagePoint
  grid export, with a VP touch count of 9 (well-tested, statistically validated
  resistance -- compare intelliscan_support_1 at 15.62 with only 2 touches).
  guideline_target was nonetheless set to 21.84 = entry(19.42) + 2x ATR(1.21),
  ignoring the 21.27 VP resistance sitting in the same packet.
  AG is not a price-discovery setup -- visible resistance exists in the
  packet's own data. This is a violation of 3.5, not an edge case it wasn't
  designed for.

**Consequence:** Every signal's R:R reads exactly 2.00 at Tier-1 screen by
construction, since target is always set to make that true. The R:R gate
cannot fail any signal at screen-all regardless of real setup quality. Full
P_400 dossier (2A) is currently load-bearing on every signal, not a
deeper-dive option for selected candidates.

---

## RECOMMENDED FIX

- P_300 target generation checks intelliscan_support_2 (or nearest VP-derived
  resistance level above entry) first.
- If a VP resistance level exists above entry: guideline_target = that level.
- If no VP resistance level exists above entry (true price-discovery case):
  fall back to the existing 2x ATR extension, per the Confluence-Based Target
  Framework.
- VP touch count (already present in the grid export) is a candidate for
  future confidence weighting -- not a blocker for this fix.

---

## ACCEPTANCE CRITERIA

- P_300 signal packets set guideline_target = VP resistance level when one
  exists above entry.
- 2x ATR extension fallback used only when no VP resistance level exists
  above entry.
- Re-run of the 2026-06-17 batch shows R:R values that vary by symbol --
  not uniformly 2.00.
- Audit trail preserved in packet: which target source was used
  (vp_resistance vs atr_extension).
