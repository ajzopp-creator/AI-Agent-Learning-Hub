## WHY

WO-P300-E5.001's own SCOPE NOTE (filed 2026-07-17) said this
explicitly: "P_300 only. Not Hub-wide -- other projects ... may not
share this same formal layer split; bolting contracts onto them is a
separate, bigger conversation, not part of this WO." This WO is that
conversation, filed now (2026-09-10) so it surfaces at future INIT
rather than being lost to chat history, per the Hub's own M-015/M-017
discipline -- the same reasoning that WO used to justify filing itself
two months before any work started on it.

P_300's result, for context: two real, pre-existing architecture
violations found and fixed (domain/ modules importing infrastructure/
directly; utilities/ holding two bidirectionally-coupled layers in one
folder), then a first-ever real `lint-imports` audit against the
cleaned tree -- PASS, 91 files, 159 dependencies, 0 breaks. The
contract only works because P_300 already had a named, documented
layer diagram (domain/infrastructure/application/...) before any of
this started -- the linter enforced an existing design, it didn't
invent one.

## SCOPE NOTE -- explicitly NOT decided yet

- **Not every Hub project has P_300's layer split.** The original WO
  called this out as the reason P_300 was the natural first case, not
  a template to copy blindly. Each candidate project needs its own
  "does a real layer diagram already exist here" check before writing
  any contract -- a project without one would be retrofitting an
  architecture under the banner of adding a linter, a much bigger
  piece of work wearing this WO's name.
- **Candidate projects, unassessed:** P_010, P_020, P_110, P_115,
  P_120, P_200, P_400, P_800, P_805/810/820. No project-by-project
  read done yet on which of these have an honor-system layer split
  worth enforcing versus a flatter structure with nothing analogous
  to check.
- **No CI in this environment**, same as the original WO -- PEH-run,
  operator-triggered, not automatic.
- Second real risk, same shape as the original WO's: a project's first
  audit might not come back clean, same as P_300's genuinely could
  have. Budget for real violations turning up, not an add-and-pass
  assumption, on whichever project goes first.

## NEXT STEPS (not started)

1. Per candidate project: confirm a real, documented layer split
   already exists (architecture doc, project-context skill, or
   equivalent) before considering a contract for it at all. Projects
   without one get dropped from this WO's scope, not force-fitted.
2. For each project that passes step 1: define that project's own
   layer-contract prose and get Tony's sign-off, same as WO-P300-
   E5.001's own step 1 -- not inherited from P_300's contract, each
   project's real dependency graph decides its own layers.
3. Add each project's `.importlinter` config, run its first real audit
   via PEH, one project at a time -- not a single Hub-wide sweep.
4. Triage findings per project before moving to the next one.
