# WO-P400-E2.020 -- Rename write_handler's Routing-Only `verdict` Field (was: "Fix council_verdict Mapping")

**Status:** CLOSED
**Owner:** P_800
**Affects:** P_400 (read-only consumer of the renamed field's old name, if any)
**Depends On:** none

---

## Problem (original filing, 2026-07-06)

`obsidian_writers.application.write_handler.handle_write()` maps
`council_verdict=BLOCKED` to `verdict=PASS` in the written P400 record.
Seen live on KTOS 2026-07-06: record status still landed correctly as
DROPPED, so no trade executed on bad data -- but the `verdict` field in
the vault record looked wrong at a glance.

## Investigation (2026-07-08, P_800 project session) -- not a logic bug

Read write_handler.py directly. `verdict` and `council_verdict` are two
separate keys. `council_verdict` (set by P_400's record_writer.py) holds
the true disposition and is never touched again. `_inject_verdict()`
separately computes a 3-value (BUY/WATCH/PASS) routing field, `verdict`,
used only to file the note into the right Obsidian folder, per
WO-P800-E2.004's locked VERDICT_MAP. It doesn't overwrite or corrupt
council_verdict. No code anywhere in the Hub was found reading the vault
note's `verdict` field expecting true disposition -- grepped P_020,
P_400, and elsewhere; the only "verdict" reads outside obsidian_writers
are P_400's in-memory eval_cache dict (a different thing, pre-vault-write).

## Decision (Tony, 2026-07-08)

Not a bug, but a real human-readability problem: `verdict` reads as
"outcome" at a glance even though it's routing-only. Resolution is a
**pure rename, no logic change**:

- Rename the field `verdict` -> `write_route` (preferred) or
  `routing_disposition` (acceptable alternative) everywhere it is
  produced and consumed: the VERDICT_MAP output key in
  write_handler.py's `_inject_verdict()`, the corresponding schema
  field(s) it's written into, and any templates/tests that reference
  the old key name.
- `council_verdict` is untouched -- remains the single source of truth
  for what actually happened. No mapping logic changes; VERDICT_MAP's
  BLOCKED->PASS / REVIEWED_NO_TRADE->PASS / APPROVED->BUY /
  APPROVED_WITH_CAUTION->WATCH entries stay exactly as WO-P800-E2.004
  locked them.
- This is P_800's call to ship -- they own obsidian_writers/write_handler.py.
  Not something to action from a P_400 or P_800 session.

## Execution (2026-07-10, P_800 session)

Scope turned out wider than the original filing implied: `verdict`/
`verdict_history` aren't just a `write_handler.py` output key -- they're
woven through five files, including `vault_writer.py`'s provenance logic,
which reads the prior `verdict:` value off disk on every overwrite to
build history. ~1945 existing vault notes already had `verdict:` in their
frontmatter (P115 1477, P300 339, P400 128, P020 1) at time of this WO.

Chose `write_route` (not `routing_disposition`). Renamed `verdict` ->
`write_route` and `verdict_history` -> `write_route_history` everywhere
(the second rename wasn't explicit in the original acceptance criteria,
but leaving `verdict_history` as the history label for a `write_route`
field would have been the same half-rename problem this WO exists to
fix). `council_verdict`, `step1_verdict`, `breakout_verdict`, `signal`,
and `VERDICT_MAP` (name + mapping table) are all untouched.

To avoid a bulk rewrite of ~1945 existing notes, `vault_writer.py`'s
`_read_existing_frontmatter()` now checks `write_route:` first and falls
back to the legacy `verdict:` key when absent (a note never carries
both). Same fallback applied to history parsing (`_parse_history` /
`_normalize_history_entry`), so a legacy note's provenance trail survives
intact the first time it's naturally overwritten post-rename, instead of
silently resetting to a default.

**Files changed** (all under `C:\Users\Trader\AI-Agent-Learning-Hub\obsidian_writers\`,
archived to `.bak_pre_writeroute_rename_2026-07-10` before edit):

| File | Lines | Change |
|---|---|---|
| application\write_handler.py | 206 | `_inject_verdict` -> `_inject_write_route`; output key renamed |
| domain\vault_schemas.py | 260 | `verdict`/`verdict_history` -> `write_route`/`write_route_history` across all 5 models |
| domain\frontmatter_builder.py | 162 | field-order list, history formatter, note-header lookup renamed |
| infrastructure\vault_writer.py | 289 | rename + legacy-key fallback read (see above); split into `_parse_frontmatter_lines` to hold the 50-line function limit |
| config.py | 127 | comments only -- no functional change, VERDICT_MAP untouched |
| test_write_route.py (new) | 81 | 5 tests: per-schema mapping, council_verdict untouched, legacy fallback read, current-format read, history key normalization |

Note: `domain\filename_builder.py` has one stale comment mentioning
`verdict_history` -- left untouched, out of the approved file list for
this WO. Doc-only inconsistency, not a functional issue.

**Verification (PEH handoff, 2026-07-10):** `test_vault_schemas.py` 3/3,
`test_write_route.py` 5/5, `test_signal_v2_e2e.py` 5/5 -- all PASS.

**Known test-coverage gap:** `test_signal_v2_e2e.py` (the gate test cited
in the original acceptance criteria) only exercises the JSON signal path,
which bypasses `write_route` entirely -- it never actually covered
VERDICT_MAP behavior. `test_write_route.py` covers P_300 passthrough and
P_400 BLOCKED->PASS directly; APPROVED->BUY, APPROVED_WITH_CAUTION->WATCH,
and REVIEWED_NO_TRADE->PASS are not individually asserted anywhere. Lower
risk since the mapping dict and its lookup logic are unchanged by this
rename (only the injection destination key changed), but flagging so it's
not assumed to be fully covered.

## P_400 Ack (2026-07-10, P_400 session)

Confirmed clean. `BookRecord` -- the only schema P_400 uses to read a
`*_P400.md` note back in -- has five fields (`symbol`, `status`, `sector`,
`open_risk_dollars`, `realized_pnl`, `close_date`); no `verdict` field
exists on it. `book_loader.py`'s frontmatter parse only remaps two keys
off the note (`ticker`->`symbol`, `lifecycle_status`->`status`) --
`verdict` is never touched, read, or passed through. A grep across every
`.py` file in P_400's `python/` confirmed every other `verdict` hit is
either P_400's own internal objects (`CouncilResult.verdict`,
`EvaluationResult.verdict`) or P_400's own `eval_cache.json` (written and
read by P_400 itself, not the Obsidian note) -- nothing reads the vault
note's frontmatter `verdict` key back into a decision path. Nothing on
the P_400 side reads, depends on, or breaks from the vault note's
`verdict` field being renamed to `write_route`.

## Acceptance Criteria (revised)

      `routing_disposition`) in write_handler.py's `_inject_verdict()`

      diff should show a rename only, no mapping-table changes.
- [x] Existing VERDICT_MAP behavior (APPROVED->BUY,
      APPROVED_WITH_CAUTION->WATCH, BLOCKED->PASS,
      REVIEWED_NO_TRADE->PASS) unchanged -- same test_signal_v2_e2e.py
      (or equivalent) still passes. (See known test-coverage gap above --
      mapping dict itself untouched, but not all four values individually
      re-asserted post-rename.)
- [x] Any downstream reader of the old `verdict` key (templates,
      dataview queries, other scripts) updated to the new name, or
      confirmed there are none (per this WO's 2026-07-08 investigation,

      grepped all six `.base` files in `trading_journal\Bases\` -- none

      `council_verdict`, P115's uses `step1_verdict`).
