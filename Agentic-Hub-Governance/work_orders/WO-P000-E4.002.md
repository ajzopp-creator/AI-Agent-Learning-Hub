# WO-P000-E4.002 -- INIT/SIP Changelog Retention Standard (Two-Version + Archive)

---

## WHY

Every INIT/SIP doc carries a "Recent Changelog" section that grows with every
version bump and gets reloaded into context on every single INIT run, even
though only the current and immediately prior version are ever operationally
relevant. P_300's SIP had already absorbed two prior one-off compression
passes (v3.0, v3.1) but kept re-accumulating between them. This WO makes the
retention itself a standing rule instead of a recurring manual cleanup that
has to be re-requested each time the file gets long again.

---

## WHAT P_000 OWNS GOING FORWARD

### 1. Two-Version Retention Rule

- Each project's live INIT/SIP doc keeps only the current and immediately
  prior version's changelog entries inline.
- Anything older moves to a sibling file:
  `<ProjectDocsDir>\<SIP_filename_stem>_CHANGELOG_ARCHIVE.md`
  P_300 example: `docs\P_300_SIP_CHANGELOG_ARCHIVE.md`
- The live SIP's changelog section carries a one-line retention-rule note
  plus a "Pre-<oldest-kept-version> history" pointer to the archive file, so
  the convention documents itself and doesn't depend on anyone remembering
  to re-apply it next time the file grows.

### 2. Rollout

- P_000 audits each project's current INIT/SIP changelog length; any doc
  already past two versions gets the same archive split applied, in that
  project's own session.
- Canonical pattern recorded in P_000_SYSTEM_DOCUMENTATION.md so new
  projects inherit it by default rather than reinventing it.

---

## OUT OF SCOPE

- Compressing step prose, tables, or other doc content -- ordinary editing,
  not this WO's concern.
- Architecture-doc changelogs (e.g. `P_300_System_Architecture_v2.7.md`) --
  different doc family; separate decision if Tony wants the same treatment
  there later.
