# WO-P400-E2.018 -- No Automated Disposal of Tier-1 FAIL Packets; Inbox Accumulates Indefinitely
**Status:** CLOSED
**Owner:** P_400
**Affects:** (none -- internal P_400 only)
**Depends On:** None
**Acks:** N/A

---

## WHY

`domain\screen.py` / `cmd_screen_all()` runs the Tier-1 deterministic screen
and prints a PASS/FAIL table. It never writes a record, never archives, and
never moves a FAILed packet. Nothing else in the pipeline does either --
`cli.py evaluate`/`spec` only act on a symbol Tony explicitly names. A
packet that fails Tier-1 (RR_BELOW_MIN, duplicate, posture-zero, stale,
etc.) just sits in the inbox indefinitely with no disposition.

Found live 2026-06-30: three separate screen-all runs this session
produced FAIL packets that were never automatically disposed --
15 from 06-22/06-23, 18 from 06-28 (17 RR_BELOW_MIN + 1 manually
dropped after dossier review), 11 from 06-30 still sitting untouched
at end of session. Each batch required an ad hoc manual decision and,
twice, a one-off script (`batch_drop_rr_invalid.py`) Tony had to
explicitly approve mid-session. There is no standing rule -- every
session re-litigates the same question.

Tony's stated position (2026-06-30): if a packet fails Tier-1 on a
static guideline-based R:R check, it will never pass on a later
screen-all run against the *same* packet -- `screen.py`'s R:R check
uses the packet's fixed guideline_entry/stop/target, not live price, so
nothing about the packet itself changes between runs. There is no
scenario where leaving it in the inbox produces a different verdict
later; it only ages toward the staleness threshold. A FAIL today is a
permanent FAIL for that packet. Confirmed correct by the codebase: no
re-screen mechanism re-derives guideline fields from a fresher source.

## SCOPE

1. `domain\screen.py` or a thin new `application\dispose_failed.py` --
   after `screen_all()` produces results, automatically call
   `drop_signal()` (existing E2.011-era function, already used manually
   today) on every FAIL result with `drop_reason` set from the FAIL's
   own reason code (e.g. `RR_BELOW_MIN`, `DUPLICATE`, `POSTURE_ZERO`,
   `SIGNAL_STALE`) -- no separate manual batch step, no separate
   session-end decision.
2. `cli.py screen-all` -- after printing the PASS/FAIL table, print a
   disposal summary line per FAILed symbol: drop reason, vault-write
   status, archive status. PASS packets are left untouched in the
   inbox for Tony to select into Tier 2.
3. Real vault audit trail preserved -- every FAIL gets a real
   `REVIEWED_NO_TRADE` P400Record (same schema/writer path used for
   today's manual batch drop), not a silent file move.
4. `test_screen.py` (or new `test_dispose_failed.py`) -- FAIL packet
   triggers drop_signal with correct reason code; PASS packet is
   never touched; mixed batch only disposes the FAILs.

## OUT OF SCOPE

- Any change to the Tier-1 PASS/FAIL logic itself -- screen.py's
  verdicts are correct, this WO only automates what happens after.
- WARN-tier signals (e.g. SIGNAL_STALE warnings that aren't outright
  FAIL) -- scope this WO to hard FAILs only; staleness-WARN disposal
  policy is a separate decision if Tony wants one.
- Manual `--drop-reason` path on `cli.py evaluate` -- unaffected,
  still available for one-off discretionary drops (e.g. today's ADBE
  MANUAL_PASS dossier-based drop, which was not a Tier-1 FAIL).

## ACCEPTANCE CRITERIA

- Running `screen-all` leaves only PASS-tier packets in the inbox
  afterward -- every FAIL gets a real vault record and is archived,
  same session, no separate manual step.
- Regression: PASS packets are untouched and remain available for
  Tier-2 selection exactly as today.
- The three batches from this session (06-22/23, 06-28, 06-30) serve
  as the manual precedent this WO automates -- no behavior change in
  verdict logic, only in what happens to a FAIL after the verdict is
  known.
