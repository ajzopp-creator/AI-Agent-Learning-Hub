   non-zero (sys.exit(1)) when `test_connection()` fails, instead of
   silently returning. Existing `test_connection()` logic unchanged --

   to fail loud when run as a script.

   Step 0 runs the token manager as a pre-flight probe BEFORE Step 1
   (balance) and Step 2 (trade pull). On failure: distinct exit code 2

   burning either pull attempt.

3. `tests\test_p020_token_preflight.py` -- regression test locking in the
   exit-code contract (fail -> sys.exit(1), success -> no exit) via

### DESIGN DECISIONS (Tony signed off 2026-07-25)

1. **Shadow mode.** `VAULT_SHADOW_MODE = True`. The vault result is
   computed and tallied but never written to `trades.system`. Tracker
   stays authoritative. Flipping to False requires a new work order.
2. **p115_linked / p300_linked are never used for attribution.** 189 of
   191 records carry `p300_linked: true` -- a schema default, not real
   attribution. Using them would produce confident wrong matches.
   Only `why_code` and `signal_source` are read.
3. **DROPPED records excluded.** Verified case: MS has a vault record
   dated 2026-07-02, BLOCKED/DROPPED, while the real MS fill was
   2026-07-23. Symbol-only matching would attribute a taken trade to a
   passed-on signal.
4. **Forward-only date window, 0..+7 days.** A signal cannot post-date
   its own fill, so the Tracker's symmetric +/-3 day walk is wrong here.
   Window is configurable; shadow data will calibrate it.
5. **Path via P_800's VAULT_FOLDER_MAP.** `from obsidian_writers.config
   import VAULT_ROOT, VAULT_FOLDER_MAP` -- verified importable in p140
   with no sys.path work. Survives the pending WO-P800-E3.003 rename.

### BLOCKED ON (upstream, not P_020) -- FIX APPLIED 2026-08-16

Root cause found and fixed same session: P_400's `record_writer.py` was
already receiving `signal_source` on every call (never optional --
`packet.signal_source`, populated by P_115's `signal_builder.py` and
every other emitter) but only ever used it to derive `p115_linked`/
`p300_linked`, then discarded it -- `why_code` stayed null on all 419
real vault records as a result. One-line fix: `"why_code": signal_source`
added to the `data` dict in `write_p400_record()`. No P_800 schema change
needed (`why_code` already defined in `P400Record`,
`obsidian_writers\domain\vault_schemas.py`); no P_020 change needed
(`vault_system_reader.py` already checks `why_code` first). Regression:
P_400's full suite (354 passed, 4 pre-existing skips) plus two new tests
locking in the guarantee (`test_why_code_persisted_from_signal_source`,
`test_why_code_not_limited_to_p115_p300`), both in
`P_400_TradeOrderManagement\python\tests\test_record_writer.py`.

Caveat (not fixed by this, structurally cannot be): a live packet sample
(163 packets, Aug 2026) shows `signal_source` is only ever `"P_115"` or
`"P_300"` today -- P_116/117/118/SNT/DAY never generate inbox packets,
so this fix doesn't attribute those. And `signal_source` reflects which
scanner flagged the candidate, not which system Tony executed the trade
as (confirmed live: DINO's packet said `P_115`, Tony traded it `P_116`).
`why_code` will now populate correctly for genuine P_115/P_300 flow; it
was never going to be a complete fix for the TOS_Import gap on its own.

Not yet verified: a live P_400 evaluate run writing a real vault note
with `why_code` populated, and a subsequent P_020 weekly ingest reading
it back non-null. Unit-tested only (write_to_vault mocked) as of this
session -- confirm on next live evaluate + next Saturday's weekly run.

Note the design change from the original plan: Tony correctly rejected
"populate why_code from the locked WHY vocabulary." The system half of
that vocabulary (BTD/OIL/EXT/EZB/VPT/SNT/DAY) is structural provenance
P_400 already knows and should emit automatically; only the situational
half (ASYM/IFFY/LEARN/CROWDED/FOMO/REVENGE) is genuinely manual. The
reader checks `why_code` first then `signal_source`, so it works either
way once one of them is populated.

### TOS ThinkLog export -- operational limits found live, real backfill runs

1. Watchlist-scoped export. A symbol's ThinkLog entries only come
   through an export if that symbol is on the active TOS watchlist at
   export time -- confirmed twice: SHEL/MRK/WMT/ABT were absent from
   two consecutive exports despite having valid tags, until added to
   a watchlist. Date range of the entry does not matter -- watchlist
   membership at export time is the only gate. A custom watchlist
   works for this; Tony could not add symbols to the built-in
   "current positions" watchlist.
2. No bulk cross-symbol export from a custom watchlist. Even with
   all needed symbols on one custom watchlist, ThinkLog's search only
   returns one symbol at a time -- there is no confirmed one-shot
   "export this whole watchlist's history" path. (The 10-record
   export that worked cleanly for IWM/DINO/SWPPX/etc. appears to have
   worked because those were on the account's live-position-driven
   default watchlist, not a bulk multi-symbol export capability.)
3. Practical workaround, no code needed: per-symbol search in TOS,
   copy/paste the note text directly into chat -- proven fast for
   SHEL/MRK/WMT/ABT already. Claude builds the CSV-format entries
   from pasted text rather than requiring Tony to manage N separate
   export files. Revisit only if this does not scale -- a real
   multi-file-merge helper would be a fair ask if the symbol list
   grows much past what fits in a session.
4. The thinkLog panel's own search box indexes note body text and
   symbol tags only, not the auto-generated timestamp header --
   searching a bare year like "2026" returns nothing unless that
   string literally appears in a note body. Not relevant to the
   export path (per point 2), but a trap if browsing the panel
   directly to find something by date.

### Real formatting issues found in Tony's actual notes (not code bugs)

Confirmed live, 2026-08-16 export: curly braces used for tag brackets
({P_116]), a stray space inside brackets ([ P_117]), and tags with
no brackets at all. All are typos in the source note, not something
the parser should paper over -- Tony's call (same session): fix the
notes at the source, keep the parser strict. Multiple tags crammed
onto one physical line (no MMDD: line break between them) has the
same resolution -- Tony fixes at the source; the parser only starts a
new entry at the beginning of a line.
