--------------------------------------------------------------------------------
WHY
--------------------------------------------------------------------------------
IBM's Granite 4.1 (released 2026-04-29) ships an 8B dense instruct model,
LM-Studio-distributed, positioned by IBM around reliable tool-calling and
instruction-following without chain-of-thought reasoning -- a different job
than `deepseek-r1-distill-qwen-14b` (current daily driver, a reasoning
model) is doing. Discussed live 2026-08-17 (P_000 session) against P_115's
STEP 2: emit the SIGNAL_V2 packet, full stop (architecture v1.3,
2026-07-24) -- a deterministic structured-JSON-out task, not a reasoning
task. The current LM Studio stack (daily driver, batch, long-context) has
no tier aimed at that job specifically. Candidate to fill the gap, not to
replace anything currently running -- contingent on actually proving out
against real P_115 data, not IBM's own benchmarks.

Environment: granite-4.1-8b (Q4_K_M) loaded and reachable at
http://localhost:1234/v1/chat/completions, confirmed via /v1/models.

Ran 3 real, already-scored P_115 setups from today's session (STZ dip_buy,
SBLK breakout, AXTI dip_buy) through Granite for STEP 2 SIGNAL_V2 emission.
Each call: system prompt with full SignalV2 field list, user message with
the same scored inputs (entry/stop/target/close/volume/ATR/rationale/etc)
Claude used for today's real emissions. Output validated against the ACTUAL
SignalV2 pydantic class from signal_schemas.py, not a re-implementation.

RESULT: 3/3 parsed as valid JSON and passed Pydantic schema validation on
first pass -- zero retries needed. Latency: 8.57s / 8.12s / 8.18s (STZ /
SBLK / AXTI). BUT schema-valid is not the same as field-correct, and two
real problems showed up that Pydantic's typing didn't catch:

1. signal_timestamp wrong on 3/3 -- Granite emitted "2023-10-01T12:00:00Z"
   for every single packet, regardless of the actual 2026-08-17 session
   date given in the input. Passes validation because the field is a plain
   `str` with no date-format constraint, but it's flatly wrong on every run.
2. atm_at_signal dropped on 3/3 -- every input explicitly gave an ATR value
   ("ATR: 3.38" / "0.92" / "10.32"). Granite emitted `null` for
   atm_at_signal every time despite the system prompt naming that exact
   field. Passes validation because the field is Optional, but the data
   was available and not used.
3. trailing_volume_30d corrupted on 1/3 -- STZ's input gave "Volume(20d
   avg): 1432261"; Granite emitted 14226.1 -- off by ~100x. SBLK and AXTI
   got their volume figures exactly right. Not systematic, which arguably
   makes it worse: no predictable pattern to guard against.

Core fields that WERE reliable across all 3: entry/stop/target prices,
strategy, confidence_level, symbol, signal_rationale text, session_date,
chart_timeframe, signal_source_link, signal_id format
(P115-YYYY-MM-DD-SYMBOL-001), price-logic ordering (stop < entry < target).

Note on scope: position_size was supplied in the test input rather than
computed by Granite, since STEP 2 (architecture v1.3, 2026-07-24) doesn't
own sizing -- P_400 does. This test only evaluated Granite's field
extraction/formatting, not any sizing judgment. Also worth flagging
structurally: Claude's own emissions today weren't an LLM-inference step at
all -- exact pre-computed fields get passed as CLI flags straight into
cli.py, so there's no natural-language re-extraction step to introduce
transcription error. Granite has to read a text description and re-map it
into fields, which is the same category of task that produced the ATR and
volume misses above -- "deterministic JSON emission" isn't actually
deterministic for a model that has to re-derive field values from prose
instead of receiving them as structured input.

FOLLOW-UP ROUND -- 2026-08-17, same session (Tony flagged LM Studio's
Structured Output capability -- unused in round 1)
--------------------------------------------------------------------------------
Two changes made together (not isolated -- can't cleanly attribute the fix
to one alone from this test):
1. Used LM Studio's `response_format: json_schema` on the API call, built
   directly from SignalV2.model_json_schema() -- grammar-constrained
   decoding, not just prose instruction.
2. Tightened the prompt: injected the real timestamp directly into the
   input instead of asking the model to infer today's date, and added an
   explicit instruction to copy ATR/volume values verbatim rather than
   estimate.

RESULT: 3/3 clean on every field tracked, not just schema-valid --
timestamp correct on all 3, ATR correctly captured into atm_at_signal on
all 3 (3.38 / 0.92 / 10.32, exact matches), volume correct on all 3
(1432261 / 440777 / 6490476, exact matches). Latency 7.26-7.77s, slightly
faster than round 1's 8.12-8.57s.

Reading this fairly: round 1's failures look like prompt/decoding-mode
gaps, not a hard capability ceiling -- once given schema-constrained
generation and unambiguous verbatim-copy instructions, the same 8B model
produced fully correct output on the same real setups. Whether that holds
up outside these 3 hand-picked tickers, and whether schema-constrained
decoding is something the actual STEP2 emission path can use in
production, is worth Tony's own read before any MODEL_MAP decision.
