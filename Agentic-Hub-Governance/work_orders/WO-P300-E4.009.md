## WHY

2026-07-21: `P_300_RunAllDailyEvals.ps1` ran the Chaikin batch for
CXW/JOBY/NCMI. Claude Code hit a Chaikin login wall, correctly refused
to log in on Tony's behalf, and printed a clear explanation -- but the
script itself had no way to know this happened. `claude -p --chrome`
exits 0 either way (a normal, coherent response either way, whether
the task succeeded or the model is explaining why it couldn't) -- the
distinction lives entirely in the prose, not in an exit code the
script could check.

This is the second confirmed instance of the Chaikin step silently
producing nothing: 2026-07-19's session summary notes "A Chaikin Power
Gauge enrichment batch (M-097) failed mid-run because the Claude
Chrome extension was not connected" -- a different specific cause,
same shape of failure (batch appears to run, produces nothing, no
loud signal).

**Root architecture finding, not just this bug:** past-session search
confirmed a real, engineered fix for session persistence
(`chaikin_reader.py`, 2026-07-03) was abandoned within days because
Cloudflare's bot detection blocked Playwright-driven automation,
independent of credentials or session validity. This means there is
no available code-level fix that eliminates the possibility of a
Chaikin login wall recurring -- a real, human-authenticated browser
session will always be able to expire. What's achievable is making
sure it's never silently missed.

## WHAT WAS BUILT

`P_300_RunAllDailyEvals.ps1`, the Chaikin batch step. Previously a
bare `claude -p $prompt --chrome` call with no output inspection.

- Output now captured via `Tee-Object` (preserves live console
  streaming -- Tony still sees Claude's response in real time -- while
  also capturing it to a variable for inspection).
- Best-effort text match against a set of known failure phrasings
  ("login page", "not logging in", "sign in to Chaikin", "extension
  ... not connected", "could not connect", etc.) -- covers both
  confirmed real failure modes (2026-07-21's login wall, 2026-07-19's
  disconnected extension).
- On a match: a loud, unmissable red banner distinct from Claude's own
  response, naming the likely cause and the affected symbol list, plus
  a log line written to $LOG for a persistent record.
- Explicitly documented as best-effort, not exhaustive, in both the
  code comment and the banner text itself -- Claude's failure
  explanations are natural-language prose, not a fixed error code, so
  a MISS here is "not flagged," not proof the batch actually worked.
  This is honest about its own limits rather than overclaiming
  reliability it doesn't have.

**Scope discipline:** Does not touch the per-symbol daily-evaluate
loop or its own messaging (that's the deferred, separate #2 item).
Does not attempt to detect-and-auto-retry or auto-complete any login
flow -- login remains entirely Tony's action, by design (this
boundary doesn't move regardless of framing).

## FOLLOW-UP (2026-07-26) -- CDPYF Per-Symbol Silent Miss, 2026-07-24 Batch

**Found during independent review of this WO** (fresh session, real
2026-07-25 18:10-18:29 DailyEval batch, 21 symbols). Real evidence -- not
the log file, which never captures Chaikin's outcome either way by this
WO's own design -- from checking the actual vault notes: the Chaikin
step succeeded for 18 of 19 actionable (BUY/WATCH) symbols (real
`## Chaikin Power Gauge` sections, mtimes clustered 18:30:21-18:36:00,
sequential ~20-30s apart, all after the eval loop's own "Run complete:
18:29:26"). One symbol -- **CDPYF** -- was silently missed: correctly
classified WATCH, correctly present in the log's own `SIGNAL REPORT
CDPYF WATCH` line (so correctly included in `$actionable`/`$symbolList`),
but its vault note's mtime (18:17:24) matches only its own original
daily-evaluate write and was never touched again. No error, no log line,
no console record survives anywhere identifying why.

**Why this WO's own detection didn't catch it:** the whole-batch text
match against `claude -p --chrome`'s full response (login wall,
disconnected extension) is built for a failure that takes down the ENTIRE
batch. A run that succeeds for 18/19 and quietly drops one ticker very
likely still returns an overall response that reads as broadly
successful -- no registered failure phrase fires, because if the miss was
even mentioned in prose, it was scoped to one ticker inside an otherwise-
normal summary. Different failure shape; not a regression in what this
WO built.

**Proposed follow-up (design only, NOT built -- Tony's call before any
code):**
1. **Detection:** after the Chaikin batch runs, check the vault notes for
   every symbol in `$actionable` for a `## Chaikin Power Gauge` section.
   Any actionable symbol missing it gets a loud line (console AND `$LOG`,
   unlike this WO's console-only success path) naming the specific
   ticker(s) missed. Cheap, checks the real outcome instead of parsing
   prose -- more reliable than phrase-matching for this specific shape.
2. **Recovery:** `P_300_RunChaikinBatch.ps1` already exists as a
   standalone re-run path (p300-project-context SKILL, Critical Paths) --
   check whether it already covers "re-run just the missed ticker(s)"
   before building anything new for this.

**Root cause of CDPYF's specific miss: CONFIRMED 2026-07-29** (fresh session, real Chaikin Analytics screenshots from Tony). Searched both `CDPYF` and `CNSWF` (see next occurrence, same day) directly in Chaikin's own UI -- both return "No results found." Both are OTC pink-sheet mirror tickers for Canadian primary listings: CDPYF = Canadian Apartment Properties REIT (primary TSX:CAR.UN), CNSWF = Constellation Software (primary TSX:CSU). Chaikin's coverage does not include these OTC pink-sheet tickers at all -- this is not a login wall, not an extension issue, not a transient failure. No re-run will ever produce a result for these specific tickers.

**Second confirmed instance, 2026-07-29 batch (25 symbols, 21 actionable):** CNSWF silently missed in exactly the same shape -- correctly WATCH, correctly in `$actionable`, vault note mtime never touched past its original daily-evaluate write. Verified against real vault-note mtimes (`## Chaikin Power Gauge` section present/absent per symbol), not the log or console text. 20/21 succeeded; CNSWF was the one gap.

**This changes the FOLLOW-UP design below.** A detection-only fix (loud alert on a missing section) is still correct and still not built. But the paired "Recovery" idea (re-run the missed ticker) does NOT apply to this failure class -- re-running an OTC-pink-sheet ticker that Chaikin doesn't carry will miss again, forever, by design of Chaikin's own coverage, not a bug in this project's pipeline. The detection should distinguish "known-uncovered ticker" (OTC pink-sheet mirrors of foreign primaries, most likely -- pattern not yet exhaustively confirmed beyond these two) from a genuine transient miss worth re-running. A small denylist/allowlist (or a first-pass heuristic on ticker suffix patterns like `F`-suffix OTC mirrors) would keep the loud-alert path from crying wolf on tickers that will never resolve.

**FOLLOW-UP CLOSED 2026-07-29 (Tony's call).** No detection code gets built for this specific failure shape -- CDPYF/CNSWF are permanent, known-uncovered OTC pink-sheet tickers, not a transient pipeline failure, so there's nothing a loud-alert-plus-retry mechanism would fix. The two-item proposal above (Detection + Recovery) is superseded by this closure, not carried forward as a backlog item. If a *different* per-symbol miss shows up later on a ticker that isn't a known OTC pink-sheet mirror, that's a new, distinct finding -- re-open or file fresh rather than reviving this design.

**Two distinct, separate bugs, both real:**

1. **Extension connection.** Claude Code's `--chrome` flag bridges to the
   same "Claude in Chrome" extension shown connected in Claude Desktop's
   Connectors panel -- but that panel reflects Desktop's own connector
   status, not the CLI's native-messaging bridge to the same extension;
   these can disagree. This is a known, filed issue (anthropics/claude-
   code#35043: extension shows installed/active, CLI still reports "not
   connected"). Documented fixes: the extension's service worker can go
   idle during inactivity -- `/chrome` -> "Reconnect extension" inside a
   Claude Code session clears that; a named-pipe conflict (another Claude
   Code session already holding Chrome) is fixed by restarting Claude
   Code. Not diagnosed which of these applies here -- next step is
   Tony's call.

2. **Detection regex bug, independent of #1.** None of the 9 hardcoded
   failure phrases in `P_300_RunAllDailyEvals.ps1` match "isn't
   connected" -- they all require the literal substring "not connected"
   or "not" within 20 chars of "extension"/"chrome extension". "isn't"
   does not contain "not" as a substring (i-s-n-'-t has no 'o'). Real
   fixable bug in the WO-P300-E4.009 code -- even after the extension
   reconnects, this exact phrasing would slip past the detector if it
   recurred. Needs a code fix (broader match, e.g. "isn.?t connected" or
   matching on "n't connected"/"can't automate the browser"), not
   addressed this session.

**Batch-vs-manual discrepancy still open.** The 16-symbol batch run
produced ZERO console output for the same call (confirmed against Tony's
full scrollback); the manual single-symbol repro without the `|
Tee-Object -Variable` wrapper produced the failure text immediately. Not
yet determined whether Tee-Object/2>&1 in the full script swallows output
under some condition, or whether the extension state genuinely differed
between the two runs (~70 min apart). Worth a second batch-context repro
once the extension connection itself is confirmed working.

Holding at OWNER_DONE -- two concrete, scoped fixes now identified for a
future work session (detector regex; investigate Tee-Object output
handling in the batch context).
