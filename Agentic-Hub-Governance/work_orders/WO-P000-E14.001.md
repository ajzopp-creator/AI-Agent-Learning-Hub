## WHY

Found 2026-08-06 during an LM Studio 0.4.15 -> 0.4.20 update session.
`integrations\lm_studio\config.py` declares:

```python
CONTEXT_LENGTH = {"primary": 16384, "batch": 8192, "long_context": 65536}
```

Nothing in the wrapper reads this constant -- verified by grep across every
file in `integrations\lm_studio\`. Effective context length is whatever LM
Studio last happened to load a model with, set through the GUI or a prior
session, not what the wrapper declares. This is the exact gap that had
deepseek-r1-distill-qwen-14b silently running at 8192 while
`P_000_SYSTEM_DOCUMENTATION.md` documented 16384 as the standing value --
the drift was invisible until someone checked the loaded instance directly.

## MECHANISM -- VERIFIED LIVE 2026-08-06 against LM Studio 0.4.20

```
POST http://localhost:1234/api/v1/models/load
Body: {"model": "<key>", "context_length": <int>}
```

- `context_length` goes at the TOP LEVEL of the body. Nesting it under a
  `"config"` key returns `400 unrecognized_keys` -- confirmed by direct
  test, do not nest it.
- Confirmed applied, not just accepted: re-read `GET /api/v1/models`,
  checked `loaded_instances[].config.context_length` as a property access
  (PSCustomObject, not a string to parse). Test model
  (`llama-3.2-1b-instruct`) went from its default 4096 to the requested
  8192 and the re-read confirmed it.

## FOUND LIVE 2026-08-07 -- the wiring gap is the smaller of two problems

Phase 1 (below) surfaced a second, unrelated defect while confirming the
wiring fix's call site. Recorded here per the correct-in-place convention
(ref WO-P000-E10.001 cross-reference in WO-P000-E13.001) rather than filed
separately, since Phase 2 below is the fix for both at once.

**A second, parallel implementation of the wrapper exists**, and it is not
a prototype that predates the shared one -- it is the wreckage of a half-
finished move. `integrations\lm_studio\domain\__pycache__\
task_router.cpython-312.pyc` and `integrations\lm_studio\application\
__pycache__\lm_studio_client.cpython-312.pyc` both exist in the canonical
location with no `.py` source next to them. `P_000_SYSTEM_DOCUMENTATION.md`
Section 3.2 already documents `domain\task_router.py` and
`application\lm_studio_client.py` as living at that canonical path. They
used to be there. The only surviving source is in
`projects\P_000_PythonClaudeLocalLLM\python\{domain,application}\`, along
with a duplicate `config.py` at the P_000 project root and a duplicate,
*less capable* `infrastructure\lm_studio_api.py` (missing the JIT Pass-2
fallback and `_wait_for_model_ready()` readiness poll that the canonical
`infrastructure\lm_studio_api.py` already has) and
`infrastructure\lm_studio_launcher.py` (a simpler executable-finder/starter,
no model-switch or task_type logic).

**Confirmed blast radius -- exactly two callers, both inside P_000 itself:**
`cli.py` (P_000's operator CLI) and `python\tests\test_health_check.py`

`Audio-Transcription\scripts\transcribe_lmstudio.py` (matches on

`examples\local_llm_status_check.py` (already imports the canonical
`integrations.lm_studio.infrastructure.lm_studio_api`, despite living in
the wrong folder -- see Item 5 below).

**A third file, legitimate and NOT part of this problem:**
`integrations\lm_studio\infrastructure\lm_studio_status.py` -- a real,
