## WHY

`cli.py`'s stated job (per its own module docstring, unchanged since
Stage 4) is to be a thin-shim aggregation point: one operator-facing
entry point wrapping every pipeline's real work, which lives elsewhere
(`domain/`, `infrastructure/`, `application/`). That design intent has
held -- every one of the 15 `_cmd_*` handlers is a genuine thin shim,
none violates the 50-line function limit, and no logic has ever leaked
into `cli.py` itself. The problem is purely structural: the FILE keeps
growing linearly with every new WO that adds a subcommand (add-pattern
-> ... -> ingest-mined, 821 lines and counting), because there is
currently no seam inside `cli.py` for a new command to land on other
than "append another `_cmd_*` function and another `add_parser()` block
to the same file." The 300-line limit was never going to hold for an
aggregation file built this way, and it hasn't -- correctly flagged at
637 lines (WO-P300-E3.001), still flagged and still growing at 821
(WO-P300-E3.002).

Tony's framing (2026-07-14 session): "building cli continually is not
the answer" -- the fix isn't a bigger exception, it's a different shape
that stops the growth from landing in one file at all.

## DESIGN -- proposed, not yet built

**Command-registry pattern.** Split `cli.py`'s two current jobs --
defining every command's handler logic, and wiring every command's
argparse registration -- into one file per CATEGORY, each owning both
its own handlers and its own subparser registration. A thin `main.py`
loops the category modules and does nothing else.

**Categories, mapped from the current 15 subcommands (2026-07-14
inventory, see todo.md session discussion for the full breakdown):**

| Category | Commands | Rationale |
|---|---|---|
| `pipeline_a.py` | add-pattern, archive-pattern | Live catalog ingest (Pipeline A) |
| `pipeline_b.py` | daily-evaluate, archive-eval | Live catalog evaluation (Pipeline B) |
| `bulk.py` | bulk-extract, phase5-analysis, scanner-loop, mine-patterns, ingest-mined, merge-research-catalog | Research-catalog / bulk-pattern-logic pipelines -- separate DB, separate write path from A/B |
| `utility.py` | catalog-summary, integrity-check, inspect-pattern, ledger-fill, ledger-calibration | Read-only diagnostics + ledger tools, no pipeline role |

**Folder shape:**
```
python/cli/
├── __init__.py
├── main.py           -- ~30 lines: builds the top-level parser, loops
                          category modules calling their register(),
                          parses argv, dispatches args.func(args)
├── pipeline_a.py      -- _cmd_add_pattern, _cmd_archive_pattern +
                          register(subparsers)
├── pipeline_b.py      -- _cmd_daily_evaluate, _cmd_archive_eval +
                          register(subparsers)
├── bulk.py            -- the 6 bulk-pattern-logic handlers + register()
└── utility.py         -- the 5 diagnostic/ledger handlers + register()
```

Each category module exports one function, `register(subparsers) ->
None`, that does exactly what its slice of today's `build_parser()`
does -- `subparsers.add_parser(...)`, `.add_argument(...)` calls,
`.set_defaults(func=...)`. `main.py`'s `build_parser()` becomes:

```python
CATEGORY_MODULES = [pipeline_a, pipeline_b, bulk, utility]

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="cli.py", description="...")
    subparsers = parser.add_subparsers(dest="command", required=True)
    for mod in CATEGORY_MODULES:
        mod.register(subparsers)
    return parser
```

**Zero terminal-facing change.** Every command a `.bat` file or Tony
types today (`python cli.py mine-patterns`, `python cli.py daily-
evaluate --xlsx ...`) types identically after this refactor -- no new
prefix, no `python cli.py bulk mine-patterns` nesting, nothing to
relearn. The split is invisible from outside the `python/` folder.

**What does NOT move.** No handler's internal logic changes -- this is
a pure cut-and-paste of existing `_cmd_*` functions + their matching
`add_parser()` blocks into the right category file, plus the shared
`main()` entry point. No behavior change anywhere; this WO is a file
reorganization, not a feature.

## REAL BUG FOUND VIA DYNAMIC SANDBOX EXECUTION (2026-07-20, same
session, after "continue")

Built a mock of the real module graph (stub `config.py`, `application/*`,
`utilities/*` matching real function signatures) in a sandbox and
actually EXECUTED the real `cli.py` + `cli_commands/` files against it --
stronger than the AST diff above, which proves the code is unchanged but
can't prove it actually runs.

**Found: `python cli.py --help` (bare, no subcommand) crashed --
`TypeError: must be real number, not dict` inside argparse's own
`_expand_help`.** Root cause: `mine-patterns`' `add_parser(help=...)`
string contains a literal `%` ("...for >=15% forward moves...") --
argparse treats `help=` as a %-format string when expanding the
top-level command summary, and a bare `%` not part of a valid
`%(name)s` specifier breaks it.

**Confirmed PRE-EXISTING, not a regression:** ran the same crash test
against the original 852-line `cli.py` (from `cli_original.py`, a
faithful sandbox copy) in the identical mock environment -- same
crash, same location, same error. This also independently re-confirms
the AST-diff's "byte-identical" claim -- the new code reproduces the
old code's behavior exactly, including this latent bug.

**Real-world impact was likely near-zero** (none of the 9 `.bat` files
ever call bare `python cli.py --help`; individual `python cli.py
<command> --help` calls -- which the 9 `.bat` files' error paths
never even reach either -- were separately confirmed unaffected) --
but it's exactly what a novice operator would try first to see the
command list, and Tony is explicit about being a Python novice.

**Fixed as a separate, clearly-labeled one-character patch, not folded
into the "pure move" claim above:** `cli_commands/bulk_research.py`,
`%` -> `%%` in the `mine-patterns` help string (the standard argparse
escape for a literal percent sign in help text). Verified in the same
sandbox mock: bare `--help` now exits 0, all 16 commands still list
correctly, `mine-patterns`' line still renders as a single `%` to the
user (escaping doesn't leak into the displayed text). Applied for real
to the file on disk, re-verified by re-reading it back.

**Added a new check to the combined `run_this.py` handoff** --
`check_e4001_bare_help_renders()` -- specifically for this case, so it
stays caught going forward instead of being a one-off fix.
