# WO-P400-E3.010 -- spec Cache Miss on APPROVED_WITH_CAUTION / APPROVED_WITH_SEVERE_WARNING (Exact-String Gate Regression of E3.009)

**Status:** CODE FIX BUILT (2026-07-25) -- regression-verified via PEH (10/10 known-bugs tests pass); live Verify criterion below still outstanding (needs a real APPROVED_WITH_CAUTION and APPROVED_WITH_SEVERE_WARNING symbol through evaluate -> spec, same session)
**Owner:** P_400
**Affects:** none -- internal P_400 only
**Depends On:** WO-P400-E3.009 (spec cache mechanism this regresses)
**Acks:** N/A

## WHY

Found live 2026-07-24 running MRCY through STEP 4-6. `evaluate` returned
`APPROVED_WITH_SEVERE_WARNING` (RISK role POSITION_COUNT warning, book at
8/8 -- SEVERE_WARNING can never block per the 2026-07-20 Council change).
`spec` then failed: `[ERROR] No valid v2 packet found for MRCY` -- the
packet had already been archived by `evaluate`'s unconditional end-of-run
archive call, and no cache existed for `spec` to fall back on.

Root cause: `application/commands.py` `cmd_evaluate`, stock-only branch
(added by WO-P400-E3.009):

```python
if result.verdict == "APPROVED":
    ...
    cache_spec_text(result.symbol, spec_text, stock_fields)
else:
    write_eval_cache(result.symbol, stock_fields)
```

The gate is an exact string match on `"APPROVED"`. `APPROVED_WITH_CAUTION`
and `APPROVED_WITH_SEVERE_WARNING` both fall into the `else` branch --
`write_eval_cache()` only, no spec text cached -- even though both verdict
tiers are meant to proceed to STEP 6 (SIP: CAUTION "state each caution,
wait for confirm, STEP 6"; SEVERE_WARNING carries the same expectation,
RISK cannot block). Grep confirms no other branch handles either string;
this was a plain oversight in E3.009 -- SEVERE_WARNING as a tier postdates
that WO (added 2026-07-20), CAUTION was already broken before AND after,
just not hit until now (Tony had been confirming CAUTION cases with a
fresh symbol/day, not back-to-back same-session).

**Workaround used this session:** manual `ZipFile` restore of
`2026-07-24_MRCY_v2.0.json` from `2607_ProcessedJson.zip`, then `spec`
re-run -- worked, but produced a duplicate zip entry (same known,
non-harmful `UserWarning: Duplicate name` pattern from E3.009's Issue 2,
resolved via existing `Select-Object -Last 1` retrieval convention).

## Fix Direction (BUILT 2026-07-25)

`cmd_evaluate`'s stock-only branch should cache spec text for any
verdict that reaches STEP 6 in the SIP -- `APPROVED`, `APPROVED_WITH_CAUTION`,
`APPROVED_WITH_SEVERE_WARNING` -- not just the literal `"APPROVED"` string.
Suggest a set/tuple constant (e.g. `SPEC_CACHEABLE_VERDICTS` in config.py)
rather than another inline string comparison, so a future verdict tier
addition doesn't reproduce this same gap a third time.

mentioning `APPROVED_WITH_CAUTION` without also mentioning
