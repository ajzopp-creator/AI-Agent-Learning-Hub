## WHY

peh-handoff v1.5's "Rule -- generated files" mandates, for any generated file:

```
1. Build it in the Linux sandbox (bash_tool), not on Windows.
2. Validate there: py_compile AND compile(...) under -W error::SyntaxWarning
3. sha256sum and byte-count the validated source.
4. Transfer as base64 (base64 -w0).
5. Decode with [System.Convert]::FromBase64String + WriteAllBytes.
6. Verify Get-FileHash -Algorithm SHA256 matches the sandbox hash.
```

Steps 1 and 4-6 exist to defend against a failure mode that only occurs when
file content is carried inside a **PowerShell command string**:

- base64 (step 4) exists because raw content in a PowerShell command needs
  escaping and corrupts UTF-8.
- chunking (implied by step 4 in practice) exists because a Windows command
  line has a hard length cap -- a ~12KB payload raises
  `FileNotFoundError: [WinError 206] The filename or extension is too long`.
- SHA-256 comparison (step 6) exists because chunked here-string appends
  silently merge line boundaries (v1.5's `ranking.py` case, 2026-08-05).

None of those three failure modes can occur when file content is passed as a
**tool parameter** rather than embedded in a shell command. Two such tools are
connected to Claude Desktop sessions today and were not being used:

| Tool | Notes |
|---|---|
| `filesystem:write_file` | `content` + `path` params. Create/overwrite. |
| `windows-mcp:FileSystem` (mode=write) | Same, plus `append=True` mode. |

## EVIDENCE -- live test, 2026-08-09, Tony's machine

Run in a P_020 session after a 5-file deployment cost ~37 tool calls and an
estimated 15-20K tokens of pure transport under the current rule.

**Test 1 -- non-ASCII integrity.** Wrote a markdown file via
`filesystem:write_file` containing em-dash (U+2014), en-dash, plus-minus,
arrows, box-drawing, curly quotes, 4-byte emoji, currency symbols, markdown
pipe tables, and Windows backslash paths inside a fenced code block. One call.

Verified from the Windows side by reading raw bytes:
- Size 822 bytes; first three bytes `23 20 54` (`# T`) -- i.e. **UTF-8 with no
  BOM**, not `EF BB BF`. This is the encoding requirement the "never use
  PowerShell string writes" rule exists to protect.
- Every non-ASCII codepoint present and correct, including the astral-plane
  emoji.
- `tests\test_x.py` backslash path preserved literally.

**Test 2 -- Python integrity at realistic size.** Wrote a 103-line / 3,754-byte
Python module via `filesystem:write_file` containing, deliberately, all four
constructs v1.5 records as having shipped broken:
1. Content spanning what would have been a chunk boundary
2. Windows paths inside a raw docstring (invalid-escape bait)
3. A reference to the triple-quote terminator that previously self-closed a
   docstring
4. Non-ASCII in comments, string literals, and assertions

Compiled and executed with `C:\Users\Trader\.conda\envs\p140\python.exe`
under `-W error::SyntaxWarning`. Result: `PASS -- all constructs survived
transit`, stderr empty, first attempt.

**Measured cost delta (the 5-file P_020 E1.011 deployment, same session):**

| | Current rule | Direct write |
|---|---|---|
| Tool calls (transport) | ~27 | 5 |
| Tool calls (incl. build + validate) | ~37 | ~7 |
| Payload | 30,620 base64 chars, pasted twice | source once |
| Est. transport tokens | 15-20K | ~6K |

Base64 is 1.33x larger than its source, and each chunk is rendered twice (read
out of the sandbox, then written into a PowerShell call), so transport costs
roughly 2.7x the raw file size in tokens before any thinking happens.

## ROOT CAUSE

v1.5 was written 2026-08-05 in response to three genuinely corrupt files, and
its diagnosis was correct. Its remedy was scoped to the only write path the
authoring session was using -- PowerShell command strings -- and was then
written as an unconditional rule for all generated files. Nothing in the rule
distinguishes *transport mechanism*, so a session reading it follows the
base64 path even when a direct-write tool is connected and idle.

Secondary observation: the sandbox's only contribution to this workflow is
`py_compile`. The p140 interpreter on Windows does that natively, on the
machine where the code will actually run, against the real interpreter version.
Building Python in a Linux sandbox to validate it for Windows execution, then
paying a network crossing to deliver it, inverts the correct order.

## SCOPE

1. **`peh-handoff` SKILL.md -- rewrite "Rule -- generated files."**
   - New default: write directly to the Windows path via
     `filesystem:write_file` (or `windows-mcp:FileSystem` mode=write when
     append semantics are needed). No sandbox build step, no base64, no
     chunking, no cross-machine hash comparison.
   - Validation moves to Windows: compile with p140 under
     `-W error::SyntaxWarning` before the file is declared good. The
     warnings-as-errors requirement is UNCHANGED -- syntax-only checking
     remains insufficient (v1.5's finding stands).

   Test-Path + Length/line-count confirmation after any write still applies:

## NOTE ON THE ONE UNTESTED BOUNDARY

Direct write is proven to 194 lines / 10,155 bytes in a single call -- this WO
file itself, written that way. The Hub's hard file-size limit is 300 lines
(~10-12KB), so the proven range now covers essentially the whole permitted
range; a tool parameter has no equivalent of the command-line length cap that
forced chunking. Remaining gap is small: 194-300 lines is untested but
unremarkable. The implementing session should still write one 250-300 line
file as part of acceptance, and if it ever fails, that is exactly the case the
retained fallback exists for.
