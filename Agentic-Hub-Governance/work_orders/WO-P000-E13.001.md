**Finding 1 -- the convention is already established.** Seven of eight projects
holding tests place them in `tests\`. `python-project-architecture` SKILL.md's
folder diagram specifies the same. There is no ambiguity to resolve; there is
one project to bring back in line.

**Finding 2 -- P_400 is the outlier, not a variant design.** 32 of its 33 test
files sit at top level. During the 2026-08-05 session Claude initially read this
as an intentional two-tier system (unit tests top-level, regression guard in
`tests\`) and recommended keeping it. That recommendation was wrong and is
recorded here so it is not repeated: the header of
`P_400\python\tests\test_p400_known_bugs.py` supplied a plausible rationale for
the one file in `tests\`, and that rationale was over-generalized into a design
intent for the other 32. Tony directed the Hub-wide audit that disproved it.

**Finding 3 -- zero pytest config Hub-wide.** No `pytest.ini`, `pyproject.toml`,
`setup.cfg`, or `conftest.py` in any project. Every run depends on cwd plus a
manually-exported PYTHONPATH. This is the root cause of Finding 4, and fixing it
is what makes the Scope 2 migration safe rather than risky.

**Finding 4 -- P_400's regression guard violates two Completion Gate rules.**
`P_400\python\tests\test_p400_known_bugs.py`:
- line 29 hardcodes `ROOT = Path(r"C:\Users\Trader\...")` -- the architecture
  skill forbids hardcoded drive letters (use `HUB_ROOT`).
- lines 32-33 call `sys.path.insert()` twice -- WO_COMPLETION_GATE lists
  "No sys.path side-channels introduced" as a checklist item.
Both exist because there is no pytest config (Finding 3) to make imports work
without them. Symptom, not carelessness.

**Finding 5 -- the guard does not run under pytest.** Its own header directs
`python.exe test_p400_known_bugs.py`, and it uses a custom `RESULTS`/`check()`
harness rather than assertions. When the 2026-08-05 session ran
`pytest test_council.py` and reported 30/30 passing, this file did not execute.
The guard covering every previously-fixed P_400 bug is invisible to the normal
test flow.

**Finding 6 -- one live desync, created 2026-08-05.** That session added an
E2.016 row to the Bugs Already Fixed table in `p400-project-context` SKILL.md
and put the matching assertion in top-level `test_council.py`. But
`tests\test_p400_known_bugs.py` is the file that mirrors that table. The table
now carries a row with no corresponding guard entry -- exactly the desync the
guard exists to prevent, introduced by the session that was closing the WO.
## SCOPE

separate approval point -- this WO does not authorize running all four

### Phase 1 -- Ratify the standard (documentation only, zero code)

1. Confirm `projects\P_XXX\python\tests\test_<module>.py` as the Hub standard.
   This documents what 7 of 8 projects already do; it invents nothing.
