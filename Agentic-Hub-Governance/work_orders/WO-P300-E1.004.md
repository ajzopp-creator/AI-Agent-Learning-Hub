# WO-P300-E1.004 -- signal_emitter Silent Under --clean + mean_ret Scale Bug in Rationale

**Status:** CLOSED -- 2026-08-10, independent review (fresh session). Real 8/10 batch confirms rationale mean_ret renders in correct percent scale on all 8 packets. Affects:P_400 checkbox closed on the same cosmetic-only basis as E1.002.
**Owner:** P_300
**Affects:** P_400 (rationale field is audit-trail context on every SIGNAL_V2 packet -- cosmetic only, guideline_entry/stop/target unaffected, but every packet's mean-return context has been wrong since Enhancement 1)

**Acks:** N/A

## WHY (two bugs, same investigation, 2026-07-04)

**Bug 1 -- visibility.** `daily_evaluate_pipeline.py main()` calls
`logging.disable(logging.WARNING)` for the entire `--clean` run, restored
only in `finally` after `run_daily_evaluate()` returns. `signal_emitter.
emit_signal_packet()` reports success (`logger.info`) and failure
(`logger.warning`) only via the logging module -- both are swallowed
under `--clean`. Unlike `write_signal_to_obsidian.py` (fixed under M-043
for the identical failure shape), `signal_emitter` has no print-based
fallback. Result: today's real `--clean` batch produced 10 vault notes
(5 BUY/5 WATCH) but only 3 signals/ JSON packets (ICE, MSTR, VTR) with
zero trace anywhere of what happened to the other 7 (CUBE, KR, RIOCF,
WFG, FTI, IMO, NYT).

**Diagnosed via PEH (2026-07-04):** replayed Stages 1-5 for the 7 missing
symbols outside `--clean`, calling `emit_signal_packet()` directly. All 7
emitted OK -- `write_to_vault` was never the problem; the emitter worked
correctly every time. The only bug is that `--clean` hides the outcome
either way. This diagnostic run itself delivered the 7 missing packets
for real (dated 2026-07-05 per P_800's emission-timestamp file-naming
convention; `session_date` inside each packet correctly reads 2026-07-02).

**Bug 2 -- unit scale, found while verifying the diagnostic's output.**
`_build_signal_v2_packet()`'s `rationale` string formats `mean_ret` as
`{mean_ret:+.2f}%`, assuming `mean_ret` already arrives as a percent
(e.g. `4.92`). It doesn't -- `aggregated_horizon.mean_return_pct` (or the
value passed into `emit_signal_packet`) is a raw fraction, so the
rationale renders `+0.05%` for a real `+4.92%` move. Confirmed
pre-existing and unrelated to the diagnostic: today's real (non-replayed)
MSTR packet (`2026-07-04_MSTR_v2.0.json`, emitted by the actual `--clean`
batch) shows `"mean return +0.20% at h=7"` where the source report shows
a materially larger value. Cosmetic only -- `guideline_stop`/
`guideline_target` derive from ATR, not `mean_ret` -- but wrong in every
SIGNAL_V2 packet emitted since Enhancement 1 (2026-06-08).

---

## RECOMMENDED FIX

- Bug 1: add a `print()`-based status line in `emit_signal_packet()`
  (mirroring the Obsidian writer's `[OK]`/`[SKIP]` pattern from the M-043
  fix) so success/failure survives `logging.disable`, whether called
  under `--clean` or not.
- Bug 2: find where the fraction-vs-percent mismatch enters -- either
  `aggregator.py` returns `mean_return_pct` as a fraction and every
  caller downstream needs `* 100`, or `signal_emitter.py`'s format string
  is wrong. Fix at the source, not by patching the format string if the
  underlying value is mislabeled elsewhere. Confirm `confidence_level`
  (`_confidence_level(wr)`) isn't fed the same wrong unit -- `wr` is
  scaled `*100` explicitly at the call site in `daily_evaluate_pipeline.py`,
  so likely fine, but verify directly.

## ACCEPTANCE CRITERIA

- A forced rejection (e.g. temporarily point `write_to_vault` at an
  invalid path) still prints a visible failure line under `--clean`.
- A successful `--clean` batch prints a visible per-symbol confirmation
  line for every BUY/WATCH emit, matching the count of vault notes
  written in the same run.
- Re-emit one known symbol (e.g. CUBE, h=5, mean_ret=+4.92%) and confirm
  the rationale string reads `+4.92%`, not `+0.05%`.
- All SIGNAL_V2 packets already in `signals/` are cosmetically wrong
  (rationale text only) -- no re-emission of historical packets required
  since `guideline_entry/stop/target` were never affected.
