## Background

Tony currently runs INIT (SIP-style session initialization — account params, risk/market posture, work-order review, lessons.md) manually, one claude.ai Project chat at a time, during morning lulls across the Hub's active projects (P_115, P_300, P_400, P_800, P_010, P_020, etc.). This is sequential and repetitive — one browser tab, one INIT, per project.

Raised in a P_115 session 2026-09-04 after a windows-mcp relay stall (one hung PowerShell call, ~4 min, followed by a spontaneous crash/restart cycle with no user action — see P_115 tasks/lessons.md pending entry, not yet written). Tony asked whether Cowork (Claude Desktop's background-agent tab) could generalize/batch this instead of one project at a time.

## What Cowork Offers (per Anthropic docs, checked 2026-09-04)

- Runs as a background agent in Claude Desktop, pointed at a local folder — not a claude.ai Project. Could point directly at Hub root and read each project's docs/ folder + skill files without a Project-attached-knowledge search.
- Reads skills the same way Claude Code does — plausibly the same `.claude\skills\` folder this Hub already treats as canonical (per system-doc-initializer Protocol B), meaning p115-project-context, work-order-governance, peh-handoff etc. may just work unmodified.
- Runs up to 3 tasks in parallel — could run 3 project INITs at once instead of sequentially.
- Supports `/schedule` for a recurring weekday-morning trigger.
- Can use MCP connectors and Claude in Chrome.

## Open Questions (unresolved, must be answered by pilot, not assumed)

1. Does a Cowork task's tool context actually reach the windows-mcp local MCP server the same way a normal Claude Desktop chat does? Nothing in Anthropic's docs confirms this for local/stdio MCP servers specifically.
2. Does Cowork read the Hub's actual `.claude\skills\` files, or a separate skill store that would need duplicating?
3. Reliability: Cowork is still labeled research preview as of the docs checked — Anthropic's own material warns of destructive file actions and prompt-injection exposure from file/web content. Given this Hub's existing zero-tolerance data-integrity stance and windows-mcp's own known instability (this WO's trigger incident), STEP 2 signal emission and any file-writing action must stay excluded from Cowork automation until proven safe in read-only pilots.
4. Does the folder-scoped model preserve the per-project knowledge boundary Tony relies on today (P_115 session shouldn't pull P_400 context unintentionally, etc.)?

## Proposed Phase 1 Pilot (read-only, no file writes)

Point one Cowork task at the Hub root. Prompt:
> "Run the P_115 INIT sequence per docs/SESSION_INITIALIZATION_PROMPT.md and the p115-project-context skill. Report back. Write nothing."

**Success criteria:**
- windows-mcp confirmed reachable from Cowork's tool context (or confirmed NOT reachable — either answer resolves Question 1).
- Cowork's Step 4 session summary matches the format/values a manual claude.ai INIT produces in the same window (account balance, risk_mode, WO list).
- No file writes occurred (verified via file mtimes in the work_orders/ and config/ folders before and after).

**Out of scope this WO:** STEP 2 signal emission via Cowork, scheduling, running Cowork against more than one project, or any file-writing action — until Phase 1 passes cleanly.
