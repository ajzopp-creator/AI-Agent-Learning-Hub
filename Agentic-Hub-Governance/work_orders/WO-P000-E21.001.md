## Background

Tony currently runs INIT (SIP-style session initialization — account params, risk/market posture, work-order review, lessons.md) manually, one claude.ai Project chat at a time, during morning lulls across the Hub's active projects (P_115, P_300, P_400, P_800, P_010, P_020, etc.). This is sequential and repetitive — one browser tab, one INIT, per project.

Raised in a P_115 session 2026-09-04 after a windows-mcp relay stall (one hung PowerShell call, ~4 min, followed by a spontaneous crash/restart cycle with no user action — see P_115 tasks/lessons.md pending entry, not yet written). Tony asked whether Cowork (Claude Desktop's background-agent tab) could generalize/batch this instead of one project at a time.

## What Cowork Offers (per Anthropic docs, checked 2026-09-04)

- Runs as a background agent in Claude Desktop, pointed at a local folder — not a claude.ai Project. Could point directly at Hub root and read each project's docs/ folder + skill files without a Project-attached-knowledge search.
- Reads skills the same way Claude Code does — plausibly the same `.claude\skills\` folder this Hub already treats as canonical (per system-doc-initializer Protocol B), meaning p115-project-context, work-order-governance, peh-handoff etc. may just work unmodified.
- Runs up to 3 tasks in parallel — could run 3 project INITs at once instead of sequentially.
- Supports `/schedule` for a recurring weekday-morning trigger.
- Can use MCP connectors and Claude in Chrome.

## Open Questions (as originally filed 2026-09-04)

1. Does a Cowork task's tool context actually reach the windows-mcp local MCP server the same way a normal Claude Desktop chat does? Nothing in Anthropic's docs confirms this for local/stdio MCP servers specifically.
2. Does Cowork read the Hub's actual `.claude\skills\` files, or a separate skill store that would need duplicating?
3. Reliability: Cowork is still labeled research preview as of the docs checked — Anthropic's own material warns of destructive file actions and prompt-injection exposure from file/web content. Given this Hub's existing zero-tolerance data-integrity stance and windows-mcp's own known instability (this WO's trigger incident), STEP 2 signal emission and any file-writing action must stay excluded from Cowork automation until proven safe in read-only pilots.
4. Does the folder-scoped model preserve the per-project knowledge boundary Tony relies on today (P_115 session shouldn't pull P_400 context unintentionally, etc.)?

**Out of scope this WO (as originally filed):** STEP 2 signal emission via Cowork, scheduling, running Cowork against more than one project, or any file-writing action — until Phase 1 passes cleanly.

## Findings — Cowork Path (2026-09-09, desk research; Phase 1 pilot above was NOT run)

Answers Open Question 1 without needing to run the Phase 1 pilot:

- Cowork sessions execute inside an isolated VM sandbox, even on Windows. Desktop-extension / stdio-type MCP servers -- exactly what windows-mcp is -- have a documented, recurring pattern of not being forwarded into that VM. One tracker report shows the VM's `--mcp-config` including only SDK-type servers (e.g. Claude in Chrome) while desktop-extension servers are completely absent, despite session metadata correctly listing them as enabled -- the VM process spawner ignores them when building the config.
- A separate, more recent Windows-specific report shows newly created Cowork sessions failing to attach the device bridge entirely after an app update (no file access, no computer use, no project memory in the new session), while sessions created before the update kept working fine on the same machine -- same failure class (local tool access silently dropped), different trigger.
- Cowork for Windows only shipped 2026-02-10 -- still working through platform-specific issues as of this check.

**Conclusion:** running the Phase 1 pilot as scoped would very likely reproduce a known, unresolved bug class, not generate new information. Not worth the pilot cost right now. Revisit if/when Anthropic ships a fix for MCP-forwarding into Cowork VM sessions.

## Findings — Parallel Claude Desktop Chat Windows (2026-09-09)

Raised by Claude as an alternative to Cowork; challenged directly by Tony ("I don't believe starting multiple chats works ... when switching from Chat A to Chat B, A stops processing"). Checked against filed reports -- Tony's observation is correct and matches known, current issues, not something specific to his setup:

- Claude Desktop is a single-window app. A "New Window" option existed briefly in an earlier build and was removed in a later update -- running "multiple chats" today means switching sessions in one window's sidebar, not independent OS windows.
- A filed, confirmed regression (reported Feb 2026, matching current build behavior): navigating to a different Project/conversation while a response is generating interrupts and discards the in-progress response. The report states this makes concurrent work across sessions impossible and effectively serializes everything -- exactly Tony's description.

**Conclusion:** not viable right now either -- same underlying failure class as Cowork (work that isn't in the foreground isn't reliably kept alive).

## Pivot — Hub-Wide WO Status Scanner (built + live-tested 2026-09-09)

Most of the actual time cost in a per-project INIT is the mechanical WO-status/gate-check pull, not reasoning -- and that part doesn't need a Claude session at all. The ledger already holds every project's WOs in one folder (`WO-P###-...` naming convention).

**Built:** `Agentic-Hub-Governance\utils\hub_wo_status_scan.ps1`

- Scans the full ledger in one pass, all projects, one PowerShell process -- no Claude session, no Cowork, no tab-switching.
- Canonical-filename regex excludes backups/drafts/scratch files by construction.
- Groups by project, sorts by Phase+Seq ascending (numeric, not lexicographic -- E9 sorts before E10).
- Excludes COMPLETE/CLOSED; surfaces BLOCKED and PENDING with markers.
- Extends the INIT Daily Check Hub-wide, in the same pass: orphaned DRAFT files, OWNER_DONE WOs missing a Completion Gate block, open WOs missing `Affects:`.
- Flags any WO whose `Status:` line doesn't match the canonical vocabulary (PENDING/IN_PROGRESS/BLOCKED/OWNER_DONE/COMPLETE/CLOSED) as NONSTANDARD instead of silently misclassifying it.
- Writes a timestamped Markdown report to `Agentic-Hub-Governance\verify\` and prints it to console.

**Live-tested against the real ledger, 2026-09-09:** 30 open WOs across 9 projects (P_000/P_010/P_020/P_025/P_115/P_300/P_400/P_800/P_820). 0 BLOCKED, 9 PENDING, 6 NONSTANDARD-status, 2 missing `Affects:` (WO-P025-EN.001, WO-P115-E6.001), 0 Completion Gate violations on current OWNER_DONE WOs.

v1.0 had a `Get-Content` encoding bug that garbled em-dashes on read (mojibake in output) -- fixed in v1.1 with explicit `-Encoding UTF8`; re-verified clean on a second live run. v1.0 also truncated multi-word status text to its first token, which would have silently mis-bucketed P_300/P_400 WOs using freeform status phrases (`MERGED into ...`, `BOTH PARTS CLOSED`, `CODE FIX BUILT`, `P_800 ACK RECEIVED`) -- fixed by capturing full status text and flagging non-canonical phrasing instead of guessing.

**Out of scope this WO:** wiring this into a scheduled/automatic trigger, and the full INIT redesign Tony flagged in the same session ("we probably need to rethink INIT's in their entirety") -- that's a separate, larger scope and belongs in its own WO once Tony's ready to define it.
