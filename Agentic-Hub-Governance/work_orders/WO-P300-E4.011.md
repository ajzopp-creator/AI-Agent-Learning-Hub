## WHY

Real evidence (not the log file -- see below) from the 2026-07-24-anchored,
2026-07-25 18:10-18:29 DailyEval batch (21 symbols) shows the Chaikin
enrichment step succeeded for 18 of 19 actionable (BUY/WATCH) symbols, and
silently dropped exactly one: **CDPYF** (correctly classified WATCH, correctly
included in the batch's `$actionable` symbol list, confirmed via the log's own
`SIGNAL REPORT CDPYF WATCH` line).

**How this was found (real artifacts, not the log):** `P_300_DailyEval_Messages.txt`
contains zero mentions of "Chaikin" anywhere -- by design, WO-P300-E4.009's fix
only writes to that log on a DETECTED failure; a success (or an undetected
partial miss) never appears there at all. Checked the actual vault notes
instead: 18 of 19 have a real `## Chaikin Power Gauge` section with real data,
mtimes clustered 18:30:21-18:36:00 (sequential, ~20-30s apart, all after the
eval loop's own "Run complete: 18:29:26"). CDPYF's note mtime is 18:17:24 --
matching its own original daily-evaluate write, never touched again. No error,
no log line, no console record survives anywhere identifying why CDPYF
specifically was skipped.

**Why WO-P300-E4.009 didn't catch this:** that fix's detection is whole-batch
text-matching against `claude -p --chrome`'s ENTIRE response (login wall,
disconnected extension -- both confirmed real failure modes that take down the
whole batch). A batch that succeeds for 18/19 symbols and quietly drops one
(a per-ticker scrape miss, a Chaikin-side 404, a timeout on that one page,
etc.) very likely still returns an overall response that reads as broadly
successful -- no registered failure phrase fires, because the failure, if any
was even stated in prose, was scoped to one ticker inside an otherwise-normal
summary. This is a different failure shape than E4.009 was built for, not a
regression in it.

## WHAT'S PROPOSED (not yet designed in detail -- Tony's call on approach)

Two independent layers, either or both:

1. **Detection:** after the Chaikin batch runs, check the vault notes for every
   symbol in `$actionable` for a `## Chaikin Power Gauge` section. Any
   actionable symbol missing it gets a loud line (console + `$LOG`, unlike
   E4.009's console-only success path) naming the specific ticker(s) missed.
   Cheap, real, checks the actual outcome instead of parsing Claude's prose --
   more reliable than phrase-matching for this specific failure shape.
2. **Recovery:** optionally, a standalone re-run mechanism for just the missed
   ticker(s) (`P_300_RunChaikinBatch.ps1` already exists as the standalone
   re-run path per the p300-project-context SKILL's Critical Paths table --
   may already cover this without new code; check before building anything
   new).

**Recommendation:** build #1 only for now (detection). #2 is likely already
covered by the existing standalone script -- confirm that during build rather
than assuming, then decide if it's still worth a dedicated one-command
"re-run just the missed ones" flow.
