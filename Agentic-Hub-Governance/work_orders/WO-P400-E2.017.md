# WO-P400-E2.017 -- test_screen.py Uses Hardcoded Absolute Dates, Breaks as Calendar Advances
**Status:** OPEN
**Owner:** P_400
**Affects:** (none -- test-only, no production logic defect)
**Depends On:** None
**Acks:** N/A

---

## WHY

`test_screen.py` fixtures hardcode `signal_date_str="2026-06-12T..."` as a
"fresh" signal. `domain\screen.py` computes signal age as
`(date.today() - signal_date).trading_days`. As the real calendar advances
past `SIGNAL_AGE_MAX_TRADING_DAYS` relative to the hardcoded fixture date,
previously-passing tests start failing -- not because of a code regression,
but because the fixture's "fresh" date is no longer fresh.

Discovered 2026-06-30 (system date) running the full suite after unrelated
WO-P400-E3.004 schema work:

  test_screen.py::test_clean_signal_passes FAILED (PASS -> WARN)
  test_screen.py::test_pass_rr_exactly_at_minimum FAILED (PASS -> WARN)
  test_screen.py::test_fresh_signal_no_stale_warn FAILED (SIGNAL_STALE present)
  test_screen.py::test_screen_all_pass_first FAILED (PASS -> WARN)

All four failures are explained entirely by signal age crossing the
staleness threshold between when the fixture date was chosen and today.
Confirmed not a regression from same-session work: test_sizing.py,
test_council.py, test_evaluate_signal.py, test_options_council.py,
test_options_sizer.py, test_spread_sizer.py, test_e2002.py, test_e2003.py,
test_read_signals.py all 100% green in the same pytest run (120 passed,
1 skipped, only test_screen.py affected).

screen.py's production behavior is CORRECT here -- a signal dated
2026-06-12 genuinely is stale by 2026-06-30. The bug is in the test
fixtures, not the deterministic core.

---

## SCOPE

Replace hardcoded absolute date strings in `test_screen.py` fixtures with
dates computed relative to `date.today()` at test-run time (e.g.
`(date.today() - timedelta(days=1)).isoformat()` for "fresh", and an
explicit offset beyond `SIGNAL_AGE_MAX_TRADING_DAYS` for "stale" test
cases), so the suite stays green regardless of when it's run.

## OUT OF SCOPE

- Any change to `screen.py` staleness logic itself -- it is correct.
- Re-running screen-all live -- today's live screen-all run already
  correctly flagged the 06-22 batch (ACHR/STEM/TE/GRWG/CBT) as
  SIGNAL_STALE; that live behavior is proof the production logic works.

## ACCEPTANCE CRITERIA
