## WHY

`peh-handoff` v1.3 states the durable-signal principle correctly: a call
returning without error is not proof of work; the only durable signal is a
file confirmed on disk. But the rule sits under a section titled "Job
persistence," is framed around Start-Job / Get-Job, and the skill scope line
reads "Applies to all Python execution under ...\projects\."

Non-Python MCP file writes -- `Set-Content` / `Add-Content` / `New-Item` for
markdown and config -- are therefore outside the written scope while
exhibiting the identical failure mode.

Observed this session: a `Set-Content` writing `tasks\lessons.md` stalled for
the full 4-minute ceiling and returned "No result received." A later
`Get-ChildItem` confirmed the file had never been created -- not truncated,
absent. The stall was reported to Tony as unknown-state rather than assumed
either way, which was correct, but only because the operator generalized a
rule the skill does not actually make.

The existing ping-first rule (v1.3, lines 30-33) then worked exactly as
written: a fast subsequent call proved the relay, not the work, had stalled;
a fresh retry succeeded. No change needed there.

---

## SCOPE BOUNDARY -- READ BEFORE STARTING

This WO broadens the *scope* of an existing rule. It does not add a new one.

**Explicitly out of scope: any payload-size or chunking threshold.**

The operator proposed in-session that MCP writes be chunked under ~4KB. That
inference is not supported and must not be documented as a rule. Evidence
from the same session, in order:

| Write | Bytes | Result |
|---|---|---|
| `tasks\todo.md` (Set-Content) | 4,112 | success |
| `tasks\lessons.md` (Set-Content) | ~5,000 | stalled, file never created |
| `tasks\lessons.md` chunk 1 (Set-Content) | 3,061 | success |
| `tasks\lessons.md` chunk 2 (Add-Content) | 1,981 | success |

One failure, with a 4KB success minutes before it and no controlled retry of
the 5KB payload after the relay recovered. n=1, confounded by a relay stall
that v1.3 already explains. Record it as an observation so a second
occurrence can promote it; do not encode a byte count.
