WO-P300-E5.001 step 2 -- the actual import-linter audit
Date: 2026-09-10

WHAT THIS IS:
This is different from every other verify\ script today. Batches 1
and 2 verified that MY edits didn't break anything -- the goal there
was always "eventually prints PASS." This script is the first real
run of the contract itself, against a codebase that's only ever been
grep-checked by hand before now. It might find something real. That
is not a failure of this script.

WHAT IT DOES:
  1. Installs import-linter into p140 (pip, --break-system-packages,
     same convention as everything else in this Hub).
  2. Runs `python -m importlinter --version` as a sanity check.
  3. Runs `lint-imports --config python/.importlinter` for real and
     prints the FULL raw output -- no interpretation, no summarizing.

THE CONTRACT (python/.importlinter), for context:
Layer order bottom-to-top: domain -> utilities -> infrastructure ->
(application | tools, independent -- neither may import the other) ->
cli_commands. schemas*.py and config.py are deliberately left out of
root_packages -- they're single .py files, not packages (no
__init__.py), and every layer is meant to import them freely, so
there's nothing to enforce there. cli.py (the thin entry-point shim)
is also left out -- nothing imports it, so there's nothing to check.

HOW TO READ THE RESULT:
  - Exit code 0 from lint-imports, "PASS" printed = contract holds.
    Done -- paste the output back, nothing else to do.
  - Non-zero exit code = the contract is broken somewhere. This could
    mean three different things and they need different responses:
      (a) A REAL violation Batches 1+2 and the whole design
          conversation missed. This is the useful case -- it's exactly
          what step 2 of this WO exists to surface. Don't fix it
          yourself; paste the output back so the actual violation gets
          looked at properly rather than patched around blind.
      (b) A typo or wrong assumption in the .importlinter file itself
          (a package name, a layer that doesn't actually have an
          __init__.py, etc.) -- possible, this config was written from
          documentation, not from a working run, since I can't execute
          python directly this session. If the error is clearly about
          the CONFIG FILE ITSELF (e.g. "could not find package X",
          "invalid contract") rather than an actual import chain
          violation, that's this case.
      (c) The `application | tools` independent-siblings syntax, or
          the layers-can-import-any-lower-layer-not-just-adjacent
          semantics, behaving differently than the docs described --
          possible for the same reason as (b).
  - Whichever it is, paste the FULL console output back rather than
    trying to diagnose or fix it here. The distinction between (a)
    real violation and (b)/(c) config problem matters for what happens
    next, and that's easier to tell from the actual violation chain
    lint-imports prints than from guessing.

Do not edit .importlinter, and do not edit any production file, before
pasting the output back.
